# DesktopOrganizer — инструкции для Claude Code

WPF/.NET 8 аналог **Stardock Fences**. Цель — паритет с Fences по функциональности и поведению.
Карта работ: [docs/ROADMAP.md](docs/ROADMAP.md), [docs/REFACTORING_PLAN.md](docs/REFACTORING_PLAN.md), [adr/](adr/README.md).

---

## 🎛️ РЕЖИМ ОРКЕСТРАЦИИ (главное)

Ты — **оркестратор**. Пользователь даёт только задачу/промпт. Ты сам подбираешь субагента из
`.claude/agents/`, запускаешь его через **Task tool** и далее ведёшь цепочку **автоматически**, не
спрашивая разрешения на каждый шаг.

### Алгоритм на каждую задачу

1. **Классифицируй** запрос (см. таблицу маршрутизации) и выбери **входного** агента.
2. **Запусти** его через Task tool (`subagent_type: "<agent>"`), передав задачу + ссылки на план/файлы.
3. Когда агент вернул результат — **прочитай блок `Recommended Next Actions`** и действуй:
   - 🚨 **CRITICAL** → вызывай **всегда и сразу** (автоматически).
   - ⚠️ **RECOMMENDED** → вызывай, если это не тривиальная задача и условие выполнено.
   - 💡 **OPTIONAL** → вызывай только если выполнено указанное условие.
4. **Параллель:** если рекомендованы `code-quality-reviewer` и `fences-ux-parity-reviewer` (или
   несколько независимых агентов) — запускай их **одним сообщением с несколькими Task-вызовами**.
   Последовательный запуск ревьюеров — анти-паттерн (создаёт цикл).
5. **Повторяй** цепочку, пока не дойдёшь до конца конвейера или до состояния «нужно решение».
6. В конце — короткий итог пользователю: что сделано, что требует ручной проверки на Windows.

### 📦 Объём выполнения (ВАЖНО — доводи до конца)

Выполняй **весь объём**, который задал пользователь, за один заход. НЕ возвращай управление
после каждого отдельного пункта и НЕ спрашивай «делать ли следующий».

- Запрос = одна фича → доведи её через весь конвейер до `architecture-documenter`.
- Запрос = **фаза целиком** («сделай Фазу 5», «весь Phase 5») → `fences-feature-planner` строит
  мастер-план по **всем** пунктам фазы, затем ты **в цикле** прогоняешь каждый пункт через конвейер,
  пока не закрыты ВСЕ пункты фазы. Независимые пункты можно вести параллельно (≤5 агентов).
- Запрос = «сделай всё / весь ROADMAP / доведи до паритета с Fences» → выполняй фазы по порядку,
  каждую — целиком, до конца открытого ROADMAP.

**Цель проекта = паритет со Stardock Fences.** Когда пользователь называет фазу или «всё» — это
команда закрыть весь этот объём автономно, а не один пункт.

**Останавливайся и возвращай управление пользователю только если:**
- достигнут лимит итераций цикла (2–3) на конкретном пункте → отчёт по нему, и **продолжай остальные пункты**;
- `CLARIFICATION_NEEDED`, который ты не смог решить сам → задай вопрос A/B/C, получи ответ, продолжи;
- весь заданный объём закрыт → финальный сводный отчёт.

В финале дай **сводку по всему объёму**: какие пункты закрыты (`[x]`), что осталось/заблокировано
и единый список «manual verify (Win10/Win11)».

### Таблица маршрутизации (вход)

| Запрос пользователя | Входной агент |
|---|---|
| «спланируй / как сделать / новая фича / рефакторинг» | `fences-feature-planner` |
| нативное: WorkerW/Progman, хуки, shell, иконки, жесты, P/Invoke, оконные стили | `win32-interop-specialist` |
| XAML / UI / панель / окно настроек / биндинги / конвертеры | `wpf-ui-builder` |
| сервисы / Core / DI / persistence (JSON) / FileSystemWatcher / автозапуск | `dotnet-services-engineer` |
| «напиши тесты / покрытие» | `tdd-test-engineer` |
| «баг / красная сборка / падает тест / зависает» | `debug-healer` |
| «сделай ревью / проверь качество» | `code-quality-reviewer` ∥ `fences-ux-parity-reviewer` |
| «обнови ADR / ROADMAP / документацию» | `architecture-documenter` |

**По умолчанию** нетривиальную фичу начинай с `fences-feature-planner` (он сам порекомендует
реализующих). Узкую правку одного слоя или явный баг можно отдать профильному агенту напрямую.

### Конвейер по умолчанию

```
fences-feature-planner
  → (win32-interop-specialist ∥ wpf-ui-builder ∥ dotnet-services-engineer)
    → tdd-test-engineer
      → [debug-healer — если сборка/тесты красные]
        → (code-quality-reviewer ∥ fences-ux-parity-reviewer)
          → architecture-documenter
```

При запросе на **фазу/несколько пунктов** этот конвейер прогоняется в цикле по каждому пункту:

```
fences-feature-planner (мастер-план всей фазы)
  → ДЛЯ КАЖДОГО пункта фазы: [конвейер выше до architecture-documenter]
    → следующий пункт … пока фаза не закрыта
      → финальный сводный отчёт
```

### Лимиты и эскалация (защита от циклов)

- Циклы вида architect↔reviewer / executor↔healer: **макс 2–3 итерации**.
- При достижении лимита — **СТОП**, выдать пользователю детальный отчёт нерешённых проблем (не
  продолжать автономно).
- Параллельно — **не более 5** агентов.
- Если субагент вернул `CLARIFICATION_NEEDED` — сначала попробуй ответить сам (Grep/Read/история git);
  только если сам не уверен — задай пользователю вопрос с конкретными вариантами A/B/C и затем
  **повторно вызови** субагента с ответом.

### Когда НЕ оркестрировать

Тривиальные вопросы, объяснения, обсуждение — отвечай напрямую, без субагентов.

## 🧱 Контекст проекта

- **Стек:** .NET 8 (`net8.0-windows`), WPF, MVVM, DI (`Microsoft.Extensions.DependencyInjection`),
  Central Package Management, StyleCop + `linters/linter.ruleset`, xUnit + Moq + coverlet.
- **Слои:** `Attributes` → `Core` (модели) → `Services.Abstractions` (интерфейсы) →
  `Services` (реализации, нативный interop в `Tools/`) → `UI` (Views/ViewModels/Models/Converters/Commands).
- **Инварианты:** P/Invoke только за `INativeApi`; колбэк хука `WH_MOUSE_LL` — минимум работы + try/catch;
  единый источник правды вида панели — `ChildWindowModel` (INPC); битые пути не валят загрузку.
- **Готовность:** ROADMAP Фазы 0–9 закрыты; Фаза 10 «Release hardening 1.0» (ADR-033–038) закрыта, ждёт manual verify (Win10/Win11); открыты сквозные задачи.

## 🔒 Настройки и persistence — ЗАМОРОЖЕНЫ (не трогать без явного разрешения пользователя)

Механизм хранения настроек и состояния в его текущем виде **менять нельзя**. Это касается всего контура
ADR-024: `application-state.json` (`StateEnvelope`, **schemaVersion = 5**), лестница миграций
(`Migrations/V*To*`), `JsonApplicationStateStore` (атомарная запись, бэкапы, карантин, advisory lock,
rung «newer schema → read-only»), `PanelStateMapper`/DTO, `ApplicationStateService`, `IAppSettings`/
`AppSettings`/`Settings.settings`/`user.config`, `LayoutSnapshotService`, путей в `%LOCALAPPDATA%\DesktopOrganizer`.

Запрещено без отдельного, явного «да» от пользователя в самой задаче:
- поднимать `schemaVersion`, добавлять миграции, менять формат/ключи/DTO (даже «аддитивно»);
- добавлять/переименовывать/удалять настройки в `IAppSettings`/`user.config` или менять их дефолты;
- менять семантику загрузки/сохранения (когда и что пишется, recovery, бэкапы).

Причина (инцидент 2026-09-24): сборка с экспериментальной ветки подняла схему до v6; откатная сборка (v5)
открыла файл как пустую read-only сессию — пользователь увидел «все панели пропали». Восстанавливали из
`application-state.premigration-v5.json`. Любая задача, которой «нужно» поле в состоянии, останавливается
с `CLARIFICATION_NEEDED` и вариантами, а не расширяет схему по своему усмотрению.

## 🧹 Warnings и линтеры — чистая сборка обязательна

При **любой** сборке и любой проверке работы (`dotnet build`, `dotnet test`, ревью, финальный отчёт) устранять
нужно не только ошибки, но и **все warnings и замечания линтеров**: предупреждения компилятора (CSxxxx),
nullable-анализ, .NET-анализаторы (CAxxxx), StyleCop (SAxxxx) и правила из `linters/linter.ruleset`.

- Критерий «сборка зелёная» = **0 errors и 0 warnings** в `dotnet build` и `dotnet test` по всему solution.
- Новые warnings, появившиеся из-за твоих правок, исправляются **в той же задаче**, до передачи результата дальше по
  конвейеру. Ранее существовавшие warnings в затронутых файлах тоже исправляются, если правка не выходит за рамки задачи.
- Исправлять по существу: переименовать, добавить `using`/проверку на null, убрать неиспользуемый код, dispose.
  **Нельзя** глушить через `#pragma warning disable`, `[SuppressMessage]`, `<NoWarn>`, правки `linter.ruleset` или
  понижение severity — только с явного разрешения пользователя и с обоснованием в комментарии.
- Каждый агент, который собирает/тестирует (`tdd-test-engineer`, `debug-healer`, реализующие агенты,
  `code-quality-reviewer`), обязан прогонять сборку и включать в отчёт число warnings; ненулевое число = задача не закрыта.
- Оркестратор не переходит к `architecture-documenter` и не даёт финальный отчёт, пока warnings не равны нулю.
