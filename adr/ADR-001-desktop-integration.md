# ADR-001: Desktop Integration — как рисовать панели на рабочем столе

**Статус:** Accepted  
**Дата:** 2026-06-16

---

## Контекст

DesktopOrganizer отображает панели с файлами на рабочем столе Windows. Чтобы поведение соответствовало Stardock Fences и DeskFrame, панели должны:

- находиться **под** обычными окнами приложений
- находиться **над** обоями
- не появляться в панели задач и Alt+Tab
- корректно работать при смене обоев, переключении виртуальных рабочих столов и multi-monitor

Сейчас `ChildWindow` — это обычное `Window` WPF, которое рендерится поверх всего. Это неприемлемо для продукта-аналога Fences.

---

## Рассмотренные варианты

### Вариант 1: `SetParent(GetDesktopWindow())`

Делает панель дочерним окном рабочего стола (`HWND` рабочего стола).

**Плюсы:**
- Простая реализация — один P/Invoke вызов
- Панель гарантированно за всеми окнами

**Минусы:**
- При смене обоев (через `SystemParametersInfo(SPI_SETDESKWALLPAPER)`) некоторые версии Windows пересоздают desktop HWND — дочерние окна исчезают
- WPF окно теряет стандартный message loop в некоторых сценариях
- Ненадёжно на Windows 11

---

### Вариант 2: `SetWindowPos(HWND_BOTTOM)` + `WS_EX_TOOLWINDOW`

Помещает окно в самый низ Z-order и убирает из панели задач.

**Плюсы:**
- Панель остаётся самостоятельным окном (не дочерним) — нет проблем с message loop
- Убирается из Alt+Tab через `WS_EX_TOOLWINDOW`

**Минусы:**
- При клике по любому приложению Z-order может восстановиться (окно всплывёт наверх)
- Нужен дополнительный механизм для возврата в низ Z-order (таймер или хук)
- Не гарантирует позицию "над обоями" — только "под остальными окнами"

---

### Вариант 3: Хак через `Progman` / `WorkerW` (подход DeskFrame и большинства desktop widget утилит)

1. Найти HWND `Progman` (процесс рабочего стола)
2. Отправить сообщение `0x052C` — это заставляет Windows создать `WorkerW` окно между обоями и иконками
3. Сделать `SetParent(workerWHwnd)` — панель рендерится в этом слое

**Плюсы:**
- Единственный подход, дающий точный слой "над обоями, под иконками"
- Используется DeskFrame, Lively Wallpaper, RainWallpaper и другими популярными утилитами
- Стабильно работает на Windows 10 и 11
- Не исчезает при смене обоев

**Минусы:**
- Undocumented Windows API — теоретически Microsoft может изменить поведение в будущих обновлениях
- Немного сложнее реализация (нужен `EnumWindows` для поиска `WorkerW`)

---

## Решение

**Выбран Вариант 3 (Progman/WorkerW).**

Это де-факто стандарт для desktop widget приложений на Windows. Стабильность подтверждена годами использования в open source проектах (DeskFrame, Lively Wallpaper). Риск breaking change со стороны Microsoft приемлем — такие изменения происходят крайне редко и всегда имеют workaround.

### Дополнительные флаги окна

Вместе с Progman/WorkerW применить:
- `WS_EX_TOOLWINDOW` — убирает из панели задач
- `WS_EX_NOACTIVATE` — панель не перехватывает фокус при клике (остаётся на рабочем столе)
- `WindowStyle=None`, `AllowsTransparency=True` в XAML — убирает стандартный Windows chrome

### Место реализации

`NativeApi` (уже существует) — добавить методы:
- `FindProgmanWindow()` — `FindWindow("Progman", null)`
- `SendMessageToProgman(hwnd)` — `SendMessage(hwnd, 0x052C, 0, 0)`
- `FindWorkerW(progmanHwnd)` — `EnumWindows` для поиска `WorkerW`
- `SetWindowParent(childHwnd, parentHwnd)` — `SetParent`
- `SetWindowExStyle(hwnd, style)` — `SetWindowLong(GWL_EXSTYLE)`

Логику инициализации вынести в отдельный сервис `IDesktopIntegrationService` / `DesktopIntegrationService`, вызывать из `ChildWindow.OnSourceInitialized`.

---

## Последствия

- `ChildWindow` перестаёт быть стандартным WPF окном с точки зрения Z-order
- Drag & Drop на уровне WPF может потребовать дополнительной настройки (WorkerW меняет родителя HWND)
- Тестировать на Windows 10 и Windows 11 отдельно
- При обновлениях Windows следить за поведением WorkerW хака

## Ревизия для боковой панели (ADR-019 / ADR-020, 2026-09-02)

Оригинальное решение выше (**Вариант 3, Progman/WorkerW**) остаётся в силе без изменений для
fence-панелей (`ChildWindow`) — их это не касается.

Для **боковой панели** (`SystemIconsPanel`) историю пришлось пройти дважды:

1. ADR-019 обнаружил, что «Вариант 3» физически несовместим с задачей «панель на конкретном
   виртуальном столе» — `WorkerW` это один общий слой на все столы, менеджер столов такое окно вообще
   не отслеживает (`GetWindowDesktopId` → `GUID_NULL`). Панель стала top-level окном с
   `Topmost="True"`, чтобы не потерять reachability (без `WorkerW`-подложки и с `WS_EX_NOACTIVATE`
   у окна не было иного способа подняться в Z-order после перекрытия).
2. ADR-020 сознательно **вернул к жизни ровно тот «Вариант 2» («`SetWindowPos(HWND_BOTTOM)` +
   `WS_EX_TOOLWINDOW`»), что был отклонён здесь в 2026-06-16**, но только для этого одного окна:
   виртуальная-десктоп-трекуемость (то, ради чего боковая панель вообще ушла с `WorkerW` в ADR-019)
   перевесила Z-order-риски «Варианта 2» — риски, которые в 2026-06-16 были достаточной причиной
   отклонить его для fence-панелей, где `WorkerW` не создавал таких противоречий.

   Причина отклонения из 2026-06-16 — «не гарантирует позицию «над обоями» — только «под остальными
   окнами»» — оставалась в силе и в 2026-09-02: `HWND_BOTTOM` в буквальном смысле не даёт такой
   гарантии. Это не было замечено при первой реализации ADR-020 (изначально `HWND_BOTTOM` внедрили
   слепо, полагаясь на то, что на этой машине результат визуально совпадает с ожидаемым) — всплыло
   на ревью именно как ссылка на этот раздел ADR-001. Исправление — не отказ от «Варианта 2», а
   явный якорь: `SetWindowPos` вставляет окно не «в самый низ», а **сразу над `Progman`**
   (`GetWindow(FindWindow("Progman"), GW_HWNDPREV)`), с fallback на `HWND_BOTTOM` только если
   `Progman` не найден. Это делает «над обоями» свойством самого вызова, а не случайным совпадением
   порядка Z-order на конкретной сборке Windows — подробности спайка и обоснование см. ADR-020.

   На машине разработки (Windows 11 build 10.0.26200) `HWND_BOTTOM` и «вставка над Progman» дали
   одинаковый результат — `Progman` там и так оказался в самом низу Z-order. Это совпадение, а не
   гарантия: причина отклонения 2026-06-16 остаётся валидной сама по себе (на других сборках/шеллах
   `HWND_BOTTOM` мог бы посадить окно под `Progman`), поэтому явный якорь сохранён, а не заменён
   обратно на слепой `HWND_BOTTOM` задним числом.

- **Fence-панели не затронуты этой ревизией** — остаются на «Варианте 3» (`WorkerW`) без изменений.
- Не проверено на Windows 10 — только на текущей машине разработки. См. ADR-020, раздел Manual verify.
