# ADR-003: Десктоп-жесты и захват иконок рабочего стола

**Статус:** Accepted
**Дата:** 2026-06-23

---

## Контекст

Фаза 4 добавляет фирменные возможности Stardock Fences:

1. **Скрытие/показ иконок рабочего стола** по двойному клику по пустому десктопу.
2. **Создание панели лассо** — правый клик + протяжка по десктопу рисует область, на её месте появляется новая панель.
3. **Захват иконок рабочего стола** — панель показывает реальное содержимое рабочего стола.

Приложение само не является рабочим столом: панели встроены в слой `WorkerW` (ADR-001),
а иконки живут в `SHELLDLL_DefView` → `SysListView32`, размещённом в `Progman` (или в отдельном `WorkerW`)
внутри процесса `explorer.exe`. Поэтому для жестов и для управления иконками нужны нативные приёмы.

---

## Решения

### 1. Скрытие иконок — `ShowWindow` над `SHELLDLL_DefView`

Находим контейнер иконок (`Progman` → `SHELLDLL_DefView`; если там нет — перебором `WorkerW`)
и переключаем его видимость через `ShowWindow(SW_HIDE / SW_SHOW)`.

**Почему так:** обратимо, не трогает реестр, не требует перезапуска explorer, мгновенно.
Альтернатива (реестр `HideIcons` + рассылка `WM_SETTINGCHANGE`) тяжелее и мигает.

Реализация: `IDesktopIconsService` / `DesktopIconsService`. Доступно из трея и из жеста двойного клика.

### 2. Жесты — глобальный low-level mouse hook (`WH_MOUSE_LL`)

Накрывать десктоп прозрачным окном нельзя — оно перехватит клики по самим иконкам.
Поэтому ставим `WH_MOUSE_LL` (как Fences, Lively): хук **наблюдает** мышь, не блокируя её.

- **Двойной клик по пустому десктопу** → событие `DesktopDoubleClicked` → тоггл иконок.
- **Правый drag по десктопу** (right-down → move > порога → right-up) → `LassoCompleted(Rect)` → новая панель.

Определение «над десктопом»: `WindowFromPoint` + `GetClassName`, классы
`SysListView32` / `SHELLDLL_DefView` / `WorkerW` / `Progman`. Клик по нашей панели вернёт класс WPF-окна,
поэтому жесты на панелях не срабатывают.

**Пустой десктоп vs иконка.** Двойной клик не должен срабатывать поверх иконки (иначе она запустится
И спрячутся значки). Проверяем попадание кросс-процессным `LVM_SUBITEMHITTEST`:
`OpenProcess(explorer)` → `VirtualAllocEx` под `LVHITTESTINFO` → `WriteProcessMemory(point)` →
`SendMessage` → `ReadProcessMemory` → если `iItem < 0`, клик по пустому месту.

**Контекстное меню при лассо.** Чтобы правый-drag не открывал меню десктопа, при состоявшемся drag
проглатываем именно `WM_RBUTTONUP` (возврат `1` из хука). Обычный правый клик (без drag) меню оставляет.

**Безопасность хука:** колбэк выполняется на UI-потоке (там есть message loop); тяжёлую работу
(создание окна, перечисление папки) выносим в `Dispatcher.BeginInvoke`, в колбэке — минимум.
Хук обязательно снимается в `Dispose`.

Реализация: `IDesktopGestureService` / `DesktopGestureService` (самодостаточный P/Invoke, т.к. нужен
живой делегат и кросс-процессные вызовы — отдельно от общего `NativeApi`).

### 3. Захват иконок — панель-портал папки `Desktop`

Вместо переноса нативного icon-view внутрь панели используем уже готовый механизм панелей (Фаза 1–3):
панель умеет показывать файлы и запускать их. Добавляем `SourceFolderPath` в `ChildWindowModel`:
если он задан, панель наполняется содержимым этой папки.

«Собрать значки» = создать панель с `SourceFolderPath = <Desktop>` + скрыть реальные иконки (п.1).
Это даёт эффект Fences малой кровью и переиспользует существующий код.

Живое отслеживание изменений папки (`FileSystemWatcher`) и автоправила — Фаза 5; пока загрузка
при открытии/создании.

## Последствия и риски

- Нативные приёмы недокументированы/чувствительны; всё тестировать на Windows 10 и 11 вживую
  (собрать в среде разработки нельзя — проект WPF/Windows-only).
- Кросс-процессный `LVM_HITTEST` зависит от прав и разрядности; при сбое детекции пустоты
  откатываемся к «тоггл только из трея».
- `WH_MOUSE_LL` глобален: ошибка в колбэке тормозит ввод всей системы — держим колбэк лёгким.
- Захват иконок через папку не прячет оригиналы сам по себе — за это отвечает скрытие иконок (п.1).

## Дополнение 2026-09-05: жёсткий тайм-бюджет `SendMessageTimeout` в `LVM_HITTEST`-проверке + консолидация P/Invoke

Закрывает риск «`LVM_HITTEST` зависит от... при сбое» и риск «ошибка в колбэке тормозит ввод» выше — в
исходной реализации оба риска были не только теоретическими: `NativeApi.IsListViewPointEmpty`
(кросс-процессный `LVM_HITTEST` в чужой процесс Explorer, п.2 выше) вызывал синхронный
`SendMessageW` **без какого-либо таймаута**, из `WH_MOUSE_LL`-хука, на каждый двойной клик по десктопу.
Если `explorer.exe` завис — блокировался ввод мыши во всей системе, не только детекция пустоты.
Найдено аудитом рефакторинга 2026-09-05 (`docs/REFACTORING_PLAN.md` §5.2, CRITICAL) и исправлено в
рамках исполнения §5.5 п.3 (детали коммитов — §7.3 там же).

**Решение:**

- `SendMessageW` → `SendMessageTimeoutW` с флагами `SMTO_ABORTIFHUNG | SMTO_BLOCK`: если процесс-адресат
  завис, вызов гарантированно возвращается по таймауту, а не блокируется бессрочно; `swallow`/детекция
  пустоты в этом случае деградирует к «не пусто» (безопасный fail-safe — двойной клик просто не
  сработает, а не подвесит систему).
- **Тайм-бюджет — 50мс** (`NativeApi.NativeMethods.HitTestTimeoutMs`), не 200мс, как в первой версии
  фикса. Первый заход этой же сессии взял 200мс интуитивно («короткий таймаут»); код-ревью
  (`code-quality-reviewer`) поймало, что это опасно близко к дефолту `LowLevelHooksTimeout` ОС
  (реестр `HKCU\Control Panel\Desktop`, по умолчанию **300мс**): весь вызов `IsListViewPointEmpty`
  происходит ИЗНУТРИ `WH_MOUSE_LL`-хука, и если суммарное время обработки сообщения в хуке превышает
  `LowLevelHooksTimeout`, Windows **тихо перестаёт вызывать хук** (без ошибки, без события — приложение
  просто перестаёт получать события мыши). 200мс сам по себе не оставлял запаса под остальные шаги
  того же вызова (`OpenProcess`/`VirtualAllocEx`/`WriteProcessMemory`/`ReadProcessMemory` вокруг
  `SendMessageTimeoutW`, см. п.2 выше) — суммарный путь мог легко подойти к границе 300мс на медленной
  машине или под нагрузкой. 50мс оставляет кратный запас.

**Зафиксированный инвариант (для будущего кода, не только для этого вызова):** любой код, достижимый из
`WH_MOUSE_LL`-колбэка (сейчас — всё, что реализует `IDesktopGestureEnvironment`, и конкретно
`INativeApi.IsListViewPointEmpty`), обязан укладываться в жёсткий бюджет по времени с явным запасом от
дефолтного `LowLevelHooksTimeout` (300мс), а не просто «стараться быть быстрым». Любой новый
синхронный межпроцессный/блокирующий вызов, добавляемый в путь хука, обязан либо иметь собственный
явный таймаут с запасом от 300мс, либо быть вынесен за пределы синхронного пути колбэка (см.
[ADR-012](ADR-012-performance-and-resilience-hardening.md) Решение 2 — тот же принцип «чистая логика
вне P/Invoke-обвязки», применённый здесь к самому таймингу, а не только к структуре кода).

**Заодно (тот же коммит, тот же корневой инвариант CLAUDE.md «P/Invoke только за `INativeApi`»):**
приватные `NativeMethods`-классы в `DesktopGestureService` (~17 `DllImport`) и `MonitorService`
(~12 `DllImport`) удалены; всё объявление P/Invoke перенесено в `NativeApi.cs`, оба сервиса переведены
на конструкторную инъекцию `INativeApi`. До этого момента это были единственные два места в `src/`,
кроме `NativeApi.cs`, где вообще был `DllImport` — прямое нарушение инварианта и источник тройного
дублирования сигнатур одних и тех же Win32 API (см. `docs/REFACTORING_PLAN.md` §6.5).
