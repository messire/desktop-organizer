# ADR-006: Избирательное скрытие иконок рабочего стола — идентификация по метке и LVM_SETITEMPOSITION

**Статус:** Rejected (2026-07-26)  
**Дата:** 2026-06-28

---

> ⚠️ **Отклонено 2026-07-26.** Ни на момент принятия, ни позже этот ADR не был реализован в коде —
> аудит проекта не нашёл ни одного из описанных ниже методов/структур ни на одной ветке git.
> Пользователь решил не делать выборочное скрытие (файлы/ярлыки отдельно от папок, а тем более
> отдельный режим «оставить только системные иконки») и оставить только простой переключатель
> «показать/скрыть все значки рабочего стола» (`IDesktopIconsService.SetIconsVisible()`/`Toggle()`,
> уже реализован и работает). Документ ниже сохранён как есть — как история рассмотренного и
> отклонённого решения, реализовывать по нему больше не планируется.

---

## Контекст

Функция «Скрыть только файлы рабочего стола (оставить папки)» требует:

1. Прочитать список иконок из `SysListView32` процесса Explorer.
2. Определить, какие из них являются файлами (не папками).
3. Скрыть только файлы, оставив папки видимыми.
4. Впоследствии восстановить файлы на их прежние позиции.

Существующий `IDesktopIconsService` умел только показывать/скрывать весь `SHELLDLL_DefView`
целиком (`ShowWindow`). Расширение потребовало кросс-процессного взаимодействия с `SysListView32`
на уровне отдельных элементов.

---

## Решения

### Решение 1: Кросс-процессное чтение SysListView32 через VirtualAllocEx/WriteProcessMemory/ReadProcessMemory

Для чтения текста иконок (`LVM_GETITEMTEXT`) буфер для `LVITEM` и строки должен находиться
в адресном пространстве процесса Explorer. Единственный корректный способ без COM/Accessibility —
выделить память в Explorer через `VirtualAllocEx`, записать структуру `LVITEM` через
`WriteProcessMemory`, отправить `LVM_GETITEMTEXT`, затем прочитать строку обратно через
`ReadProcessMemory` и освободить память.

**Почему так:** `LVM_GETITEMTEXT` с буфером в адресном пространстве своего процесса возвращает
пустую строку или AV (разная разрядность либо UIPI). Это единственный надёжный подход для
чтения SysListView32 без инъекции DLL.

**Альтернатива A:** UI Automation (`AutomationElement`). Зависит от провайдера доступности
Explorer; в некоторых конфигурациях Windows 11 возвращает неполный список и работает медленнее.

**Альтернатива B:** Shell namespace / `SHGetDesktopFolder`. Не даёт текущие позиции иконок.

**Trade-off:** код требует `SeDebugPrivilege` (или достаточно стандартных прав текущего
пользователя при одинаковом SID), чувствителен к разрядности (x64 DesktopOrganizer — x64 Explorer).
Буфер обнуляется между итерациями `LVM_GETITEMTEXT`, чтобы избежать чтения остатков предыдущего
имени при укороченном ответе.

---

### Решение 2: LVM_SETITEMPOSITION как механизм скрытия (перемещение в «слепую зону»)

Иконки-файлы перемещаются в позицию `(-30000, -30000)` за пределы видимой области экрана
через `LVM_SETITEMPOSITION`. Это делает их визуально невидимыми, не удаляя из списка ListView.

**Почему так:** `LVM_DELETEITEM` необратим — восстановление потребовало бы полного пересоздания
элементов Shell, что нарушает целостность Shell-namespace. Перемещение безопасно: Explorer хранит
настоящую позицию иконок в реестре (`HKCU\...\IconLayouts`), а возврат на место возможен без
обращения к реестру — достаточно перечитать актуальные позиции.

**Альтернатива:** `LVM_SETITEMSTATE` с `LVIS_CUT` (иконка становится полупрозрачной, но
остаётся видимой) — не подходит как «скрытие».

**Trade-off:** иконки реально присутствуют в `SysListView32` и доступны для кликов в зоне
`(-30000,-30000)`. Риск минимален: зона за пределами любого монитора.

---

### Решение 3: Идентификация по метке (label), не по LV-индексу

`_hiddenItems: Dictionary<string, (int X, int Y)>` хранит сохранённую позицию, ключ — label
иконки (`OrdinalIgnoreCase`). При восстановлении метод ре-перечисляет актуальные индексы
и сопоставляет их с ключами словаря.

**Почему так:** LV-индексы нестабильны. Любое добавление, удаление или сортировка иконок
в период, пока файлы скрыты, сдвигает индексы. Метки файлов рабочего стола — уникальные
строки в рамках одного десктопа и не меняются без явного переименования пользователем.

**Альтернатива:** сохранять индексы. Сломается при появлении/исчезновении других файлов
или после автоарранжа.

**Trade-off:** если пользователь переименует скрытый файл, его label не совпадёт при restore
и иконка останется в `(-30000,-30000)` до следующего перезапуска Explorer. Принято как
приемлемый edge-case.

---

### Решение 4: Auto-arrange detect — abort при первом неудачном LVM_SETITEMPOSITION

Перед массовым перемещением делается попытка переместить первую иконку. Если `LVM_SETITEMPOSITION`
возвращает `false` (LVM авто-арранж включён — Desktop имеет `LVS_AUTOARRANGE`), метод
немедленно выходит без изменений и без записи в `_hiddenItems`.

**Почему так:** при авто-арранже позиции игнорируются Explorer-ом — иконки вернутся на место
сами, но `_hiddenItems` будет заполнен, и последующий `RestoreAll` запишет некорректные
позиции. Graceful degradation предпочтительнее тихой ошибки.

**Trade-off:** пользователь получает no-op без явного сообщения (выводится только в лог).
Полноценный UI-диалог — вне scope данного ADR.

---

### Решение 5: BuildDesktopNameSets — единый O(n) проход для классификации файл/папка

Метод `BuildDesktopNameSets()` делает один проход по каталогу Desktop (`Directory.GetFileSystemEntries`),
формируя два `HashSet<string>` (OrdinalIgnoreCase): для файлов и для папок. Классификация каждой
LV-иконки — `O(1)` lookup по метке.

**Почему так:** без предварительного набора классификация требовала бы вызова `File.Exists` /
`Directory.Exists` на каждую иконку внутри цикла `LVM_GETITEMTEXT` — O(n²) по I/O при
n иконках.

**Trade-off:** `BuildDesktopNameSets` делает снимок FS в момент вызова; иконки, появившиеся
после начала итерации, не войдут в наборы (несущественно для интерактивного use-case).

---

### Решение 6: Два отдельных пункта меню трея вместо одного переключателя

`TrayIconManager` получил отдельные пункты:
- «Скрыть / показать все значки» — существующий тоггл через `ShowWindow(SHELLDLL_DefView)`.
- «Скрыть только файлы (оставить папки)» — новый `ToggleFilesOnly()`.

**Почему так:** два режима скрытия несовместимы по состоянию — «скрыть всё» не знает о
`_hiddenItems`, а «только файлы» не трогает `SHELLDLL_DefView`. Один тоггл потребовал бы
отслеживания комбинированного состояния и нетривиальной логики перехода.

**Trade-off:** меню трея растёт на один пункт. При дальнейшем росте функций трея стоит
ввести подменю «Значки рабочего стола».

---

## Последствия

- `INativeApi` расширен двумя методами (`GetDesktopListItems`, `SetDesktopItemPosition`);
  все реализации (включая моки в тестах) должны их реализовать.
- `IDesktopIconsService` расширен методами `HideFilesOnly()`, `RestoreAll()`, `ToggleFilesOnly()`,
  свойством `AreFilesHidden`. `RestoreAll()` теперь также вызывается из существующего `ShowIcons()`
  для корректного сброса `_hiddenItems` при полном показе.
- Кросс-процессный код требует ручного тестирования на Windows 10 и Windows 11 (разные версии
  Explorer могут иметь разные классы `SysListView32`).
- При включённом авто-арранже функция «скрыть только файлы» является no-op (см. Решение 4);
  пользователю рекомендуется отключить «Автоматически упорядочить значки» в контекстном меню
  рабочего стола.
