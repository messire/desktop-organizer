# ADR-009: Drag&drop в панель — Move-семантика через managed storage + JSON-manifest

**Статус:** Accepted
**Дата:** 2026-07-07

---

## Контекст

Ранний фикс (2026-06-28, см. ROADMAP Фаза 1) ввёл `IPanelItemStorageService`/`PanelItemStorageService`,
который при drag&drop **копировал** перетащенный файл/папку в приватное хранилище приложения
(`%LocalAppData%\DesktopOrganizer\PanelItems`), оставляя оригинал на рабочем столе нетронутым. Это
решило регрессию «ярлык в панели ломается, если пользователь вручную удаляет исходный файл», но не
соответствовало ни ожидаемому поведению Fences, ни цели приложения «очистить рабочий стол»: после
Copy на столе оставался дубликат, который пользователь должен был удалять вручную сам.

Эта работа (план [docs/PLANS/drag-drop-move-semantics.md](../docs/PLANS/drag-drop-move-semantics.md))
эволюционирует Copy в **Move**: drop перемещает оригинал, а «Убрать из панели» возвращает файл на
исходное место. Ниже фиксируются решения, которые не являются самоочевидным продолжением исходного
Copy-фикса и требуют явной архитектурной записи.

---

## Решения

### Решение 1: Managed-copy в `%LocalAppData%` с GUID-суффиксами, а не in-place repositioning иконки

Move реализован как перемещение файла в приватное хранилище приложения (`File.Move`/copy-then-delete)
с последующей ссылкой панели на managed-путь, а не как визуальное перемещение/скрытие иконки на месте
(то, что вероятно делает сам Stardock Fences — по внешнему поведению по крайней мере часть его функций
похожа на репозиционирование записи в `SysListView32` десктопа без физического перемещения файла).

**Почему так:** этот выбор был сделан ещё на более ранней сессии (см. ROADMAP Фаза 1, пункт про
папки при drop) при рассмотрении «честного» скрытия иконки на месте через `LVM_SETITEMPOSITION`
(тот же механизм, что и `ADR-006` для скрытия файлов рабочего стола) как альтернативы копированию.
Вариант отклонён: `LVM_SETITEMPOSITION` в `ADR-006` работает в рамках одного `SysListView32`
(десктоп), а панель — независимое WPF-окно с собственным списком, не строка в чужом ListView;
«переместить иконку в панель без копирования файла» потребовало бы либо (a) кросс-процессной
манипуляции чужим `SysListView32` десктопа для скрытия оригинальной иконки combined with собственным
WPF ItemsControl для отображения — двойной источник правды о позиции одного и того же файла, либо
(b) полного отказа от собственного UI панели в пользу второго `SysListView32`-подобного list-view,
что меняет весь UI-стек панелей. Оба варианта — существенно больший и рискованный объём нативного
Win32-кода, непроверяемый в среде разработки без GUI Windows (см. ограничения окружения в CLAUDE.md).
Managed-copy-подход, напротив, использует только `System.IO` (`File.Move`/`File.Copy`/`Directory.Move`)
— без нового P/Invoke, полностью тестируемый юнит-тестами.

**Альтернатива A (honest-hide через LVM_SETITEMPOSITION):** отклонена по причинам выше.

**Альтернатива B:** оставить Copy-семантику (файл дублируется, пользователь сам чистит десктоп) —
отклонена, т.к. не соответствует цели приложения и явно противоречит ожиданиям пользователя от
drag&drop-паритета с Fences.

**Trade-off (осознанно принят):** физический механизм отличается от вероятного реального механизма
Fences. Наблюдаемое поведение для пользователя эквивалентно (файл перемещён в панель, десктоп
очищен, «убрать из панели» возвращает файл), но managed-copy создаёт собственный класс рисков —
осиротевшие копии при сбое restore, необходимость manifest для хранения original path (Решение 2),
GUID-суффиксы в именах managed-файлов на диске (не видны пользователю, но занимают
`%LocalAppData%`). Признано приемлемым: пользователь не взаимодействует с managed storage напрямую,
а надёжность копирования выше надёжности кросс-процессной манипуляции чужим ListView.

### Решение 2: Original path — в собственном JSON-manifest сервиса, а не в `FileItem`/персистентной схеме панели

Original path (нужен, чтобы `Restore` знал, куда вернуть файл при «Убрать из панели») хранится в
персистентном JSON-manifest **внутри** `PanelItemStorageService`
(`%LocalAppData%\DesktopOrganizer\PanelItems\.manifest.json`, `managed path → original path`,
атомарная запись write-temp + `File.Replace`), а не как новое поле `FileItem` (Core) и не как
изменение персистентной схемы `ChildWindowModel.FilePaths : List<string>`.

**Почему так:**

- **Инкапсуляция слоёв.** Original path — деталь механизма Move внутри Services, а не свойство файла,
  нужное UI. `FileItem` намеренно тонкий и UI-ориентированный (`Path`, `Icon`, `Exists`, `IsDirectory`,
  `IsShortcut`); добавление `OriginalPath` протекало бы механику storage в доменную модель, которую
  видят и Folder Portals, и `LoadFromModel`, где это поле бессмысленно.
- **Стабильность персистентной схемы.** Альтернатива потребовала бы менять
  `ChildWindowModel.FilePaths : List<string>` → `List<PanelFileEntry>`, что ломает формат JSON
  сериализации настроек, требует миграции и затрагивает `SyncToModel`/`GetSourceFiles`/`LoadFromModel`.
- **Единая точка владения.** `PanelItemStorageService` уже единственный владелец storage root и
  единственный, кто знает, что такое managed path — manifest логически принадлежит ему одному.

**Альтернатива (отклонена):** расширить `FileItem`/`ChildWindowModel` полем `OriginalPath`,
персистировать его вместе с остальным состоянием панели.

**Trade-off:** manifest — отдельный источник состояния, который может рассинхронизироваться со
storage (managed-файл есть, записи в manifest нет, или наоборот — например, при ручном
редактировании файлов пользователем на диске). Обрабатывается деградацией (Решение 3): нет записи →
`RestoreOutcome.OriginalPathUnknown` → caller (`ChildWindowViewModel.RemoveFileItem`) деградирует до
старого поведения `Release` (удаление managed-копии без восстановления).

---

### Решение 3: Обратная совместимость через `RestoreOutcome`, а не миграцию старых панелей

Панели, сохранённые до этого изменения (managed-копии из Copy-режима без записи original path в
manifest), не мигрируются принудительно. `Restore(storedPath)` возвращает результат-код
(`RestoreOutcome`: `Restored` / `OriginalPathUnknown` / `NotManaged` / `Failed`), и вызывающая
сторона сама решает, как деградировать.

**Почему так:** любая попытка «угадать» original path для legacy-записей (например, по имени файла
без GUID-суффикса) ненадёжна и рискует переместить файл не туда. Явный отказ (`OriginalPathUnknown`)
с деградацией до безопасного `Release` — предсказуемее и безопаснее тихой попытки восстановления
вслепую.

**Trade-off:** пользователи со старыми панелями не получают Restore-поведение для уже
перенесённых файлов, пока не пересоздадут элемент — принято как приемлемое, т.к. поведение для них
не хуже, чем было (идентично сегодняшнему Copy/Release).

---

### Решение 4: Коллизия имён при restore — Explorer-паттерн, без перезаписи

`Restore` никогда не перезаписывает существующий файл/папку на исходном месте: при коллизии имени
подбирается первое свободное имя по паттерну Explorer (`name (2).ext`, `name (3).ext`, …). Логика —
в Services (`PanelItemStorageService`), не в UI.

**Почему так:** тихая перезапись — риск необратимой потери данных пользователя (другого файла на
исходном месте, появившегося за время, пока managed-копия жила в панели). Explorer-паттерн — знакомое
пользователю поведение из проводника Windows.

**Trade-off:** нет.

---

### Решение 5: Восстановление недостающей родительской директории, без fallback на Desktop

Если исходная директория original path удалена к моменту restore, `PanelItemStorageService`
воссоздаёт её (`Directory.CreateDirectory` по родителю), а не откатывается к какому-то дефолтному
месту (например, Desktop).

**Почему так:** предсказуемость — файл возвращается именно туда, откуда был взят. Fallback на Desktop
отклонён, т.к. Services.Tools не должен знать о «Desktop» как концепте (это UI/shell-уровень), и
«файл появился не там, откуда его брали» — хуже для пользователя, чем воссозданная папка.

**Trade-off:** если воссоздание родителя тоже падает (нет прав, диск недоступен), `Restore`
возвращает `Failed`; managed-копия остаётся на месте (не теряется), но элемент всё равно убирается
из UI-списка панели (см. известное ограничение ниже) — managed-копия временно осиротевает до
ручной проверки лога/диска.

---

### Решение 6: Cross-volume — copy-then-delete-after-verified-success (и для `MoveIn`, и для `Restore`)

И перемещение в панель, и восстановление обратно, при пересечении границы тома, реализованы как
copy-then-delete: оригинал удаляется **только** после подтверждённого успеха копии (существование +
сверка размера), а не одновременно с ней. Safety-cap (2 ГиБ / 20 000 файлов) применяется только к
cross-volume перемещению **папок**, не файлов, и не применяется к same-volume `Directory.Move`
(атомарный rename, ничего физически не копируется, cap не нужен и вреден бы удобству).

**Почему так:** цена ошибки — реальная потеря пользовательских файлов. Same-volume `File.Move`/
`Directory.Move` атомарны и не нуждаются в safety-net. Cross-volume путь физически копирует байты,
поэтому нуждается в верификации перед удалением источника и защите от неограниченного использования
диска/времени на огромных папках.

**Trade-off:** cross-volume перемещение больших папок ограничено лимитом — сверх него `MoveIn*`
возвращает `null`, и `ChildWindowViewModel.AddDroppedFiles` деградирует до referencing-поведения
(панель ссылается на оригинал напрямую, без Move) — тот же trade-off, что был у Copy-режима для
превышающих лимит папок.

## Последствия

- `IPanelItemStorageService`: `Import`/`ImportDirectory` (Copy-API) удалены, заменены на
  `MoveIn`/`MoveInDirectory`/`Restore` + `RestoreOutcome`. `Release`/`IsManaged` сохранены —
  `Release` нужен для ADR-B-деградации (`OriginalPathUnknown`) и для будущей очистки осиротевших
  копий.
- `ChildWindowViewModel.AddDroppedFiles` вызывает `MoveIn*`; `RemoveFileItem` вызывает `Restore`,
  деградируя до `Release` при `OriginalPathUnknown`. `ChildWindow.xaml.cs` показывает курсор
  `DragDropEffects.Move` вместо `Copy` для не-портальных панелей.
- Персистентная схема `ChildWindowModel.FilePaths : List<string>` **не изменилась** — полная
  обратная совместимость settings.
- **Известное ограничение (принятый технический долг):** если `Restore` возвращает `Failed` (сбой ФС
  при возврате файла на исходное место), элемент всё равно убирается из UI-списка панели, а
  managed-копия остаётся в storage без активной ссылки на неё — «осиротевшая» копия. Очистка таких
  копий (и копий, осиротевших при полном удалении панели, см. ROADMAP Фаза 1) — отдельная будущая
  задача, не реализована.
- **Известный тестовый пробел:** cross-volume fallback внутри `Restore` (copy-then-delete при
  `IOException` от `File.Move`/`Directory.Move` через тома) реализован, но не покрыт автотестом —
  в отличие от `MoveIn`/`MoveInDirectory`, у `Restore` нет внутреннего `forceCrossVolume`-хука для
  форсирования этого пути в юните. Задокументировано в
  `tests/DesktopOrganizer.Tests/Unit/Tools/PanelItemStorageServiceTests.cs` (комментарий у блока
  «M2: known test gap»); рекомендация — добавить такой хук в будущей итерации.
- **Открытый UX-риск (повышенный приоритет, не просто OPTIONAL):** one-time хинт при первом
  Move-drop, поясняющий пользователю, что файл физически перемещается (а не копируется), и как
  вернуть его назад, не реализован — план предлагал его как рекомендацию, `wpf-ui-builder` оценил
  как выходящий за scope этого шага. `fences-ux-parity-reviewer` считает риск непонимания
  пользователем Move-семантики (в отличие от привычного Copy) реальным и существенным (MAJOR), не
  просто «приятным плюсом». Временный компромисс — `ToolTip` на пункте контекстного меню
  «Убрать из панели» (`src/DesktopOrganizer.UI/Resources/Templates.xaml`), поясняющий, что элемент
  вернётся на исходное место. Полноценный one-time хинт остаётся открытым пунктом для будущей фазы
  с повышенным приоритетом (см. ROADMAP, сквозные задачи).

## Amendment (2026-09-22, P08 icon loading fix cycle)

**Контекст.** P00 baseline-аудит (`docs/PLANS/workspace-grid-00-baseline.md`, часть C) обнаружил на
реальном state: 20 из 26 элементов панелей указывают на **исходные** (pre-Move) пути на рабочем
столе, а не на managed-копии — вероятно, из-за первого legacy-импорта в установленной сборке, читающего
`user.config` до того, как Move переместил файлы (H2a), либо из-за restore старого снапшота (H2b). Для
19 из 20 в `.manifest.json` есть запись original→managed, managed-копия существует и даёт рабочую
иконку — но ничего в коде никогда не смотрело на манифест в этом (обратном) направлении: манифест
проектировался только для `Restore` (managed→original, Решение 2 выше).

**Решение.** Добавлен `IPanelItemStorageService.TryFindManagedPath(originalPath, out managedPath)` —
**чистое чтение** уже закешированного в памяти манифеста (ADR-012 Решение 4) в обратную сторону,
возвращающее managed-путь только если он **действительно существует на диске** (защита от «одна
битая ссылка вместо другой», если managed-копия сама была удалена в обход сервиса). Никаких записей
в манифест или на диск не производится.

Вызывается из `ChildWindowViewModel.LoadFromModel` (`ResolveManagedReplacements`): при загрузке панели
любой путь из `ChildWindowModel.FilePaths`, который не существует, но резолвится через
`TryFindManagedPath`, заменяется на managed-путь **до** построения `FileItem` — то есть и иконка, и
будущий запуск (`OpenFileCommand`) сразу используют реальный, текущий путь, а не мёртвый.
Самоисцеление становится постоянным только когда панель в следующий раз сохраняется: обратная
синхронизация `ChildWindow.xaml.cs` (`_model.FilePaths = AllItems.Select(f => f.Path)`) персистирует
уже исправленный путь. До первого сохранения после фикса поведение идентично старому при перезапуске
без сохранения — деградация отсутствует, только улучшение.

**Почему не сильнее.** Рассмотрены и отклонены:
- **Автоматическая миграция всех сохранённых состояний при апгрейде** — потребовала бы отдельного
  прохода миграции (в духе ADR-024) специально ради путей файлов, что смешивает две разные вещи
  (schema-версионирование JSON и specific-to-icons путевую эвристику); при этом `ResolveManagedReplacements`
  и так покрывает тот же случай на каждом обычном `LoadFromModel`, без миграции.
- **Запись managed-пути обратно в `Model.FilePaths` немедленно** (а не через обычный save-cycle) —
  отклонено: `LoadFromModel` — чтение, а не запись; принудительный `SaveWindowsStateNow()` отсюда
  нарушил бы существующую debounce/immediate-политику (ADR-012 Решение 1) ради узкого кейса. Обычный
  цикл сохранения панели (частое действие — drag/resize/rename/FilesChanged) и так подхватит
  исправленный путь в разумное время.
- **Расширение публичной персистентной схемы** (например, полем `OriginalPath` на элементе) — не
  требуется: чтение обратного направления полностью покрывается уже существующим манифестом
  (Решение 2 выше), новое поле добавило бы v4→v5-миграцию (ADR-024) ради того, что уже решается без неё.

**Известное ограничение.** 1 из 20 путей в реальном state (Public Desktop) не имеет записи в
`.manifest.json` вообще (см. baseline) — для него `TryFindManagedPath` корректно возвращает `false`,
и элемент остаётся видимым серым с исходным (битым) путём, как и было. Это не регрессия — до фикса
такой элемент был и невидим (прозрачный placeholder), и не резолвился; после фикса он как минимум
**виден** (непрозрачный placeholder, см. `IconFactory`-фикс в этом же цикле), просто без иконки цели.

## Amendment 2 (2026-09-22, P08 fix cycle 1 — findings C1/M1)

Ревью Amendment (2026-09-22) выше нашёл два новых риска в самом фиксе, оба закрыты в этом цикле.

### C1 — тихая потеря данных: решение read-time-only без немедленной записи создавало окно рассинхронизации

**Проблема.** Amendment (2026-09-22) выше сознательно отклонил немедленную запись managed-пути
обратно в `Model.FilePaths` («Решение принято... `LoadFromModel` — чтение, а не запись»). Это создавало
окно: между `LoadFromModel` (remap виден только в ViewModel/`AllItems`) и следующим `SyncToModel()`
(remap попадает в `Model.FilePaths`) любой код, читающий `Model.FilePaths` напрямую, видел устаревший
(pre-remap) путь. Конкретный сценарий: пользователь удаляет панель сразу после старта, до первого
сохранения — `MainWindowViewModel.RemovePanel`/`PageManagerService.RemovePage` проверяли
`FilePaths.Any(IsManaged)` **на stale-пути** (`IsManaged(O) == false`) → показывали нейтральный диалог
«ничего не потеряется» → но `WindowManager.RemoveChildWindow` тут же вызывает `SyncToModel()` (который
подхватывает уже remap-нутый managed-путь из живого ViewModel) и затем `Release()` — реально стирая
managed-файл мимо Корзины, без предупреждения, которое пользователь должен был увидеть (нарушение
ADR-010 Решение 2).

**Решение (два взаимодополняющих фикса, не один):**

1. **`MainWindowViewModel.RemovePanel`/`PageManagerService.RemovePage`** теперь вызывают
   `IWindowManager.SyncAllWindowsToModels()` **до** вычисления `hasManagedFiles` — решение
   «предупреждать или нет» принимается по актуальному, только что синхронизированному состоянию, а не
   по тому, что было в момент открытия окна настроек. `PageManagerService.RemovePage` ранее не
   спрашивал подтверждения вообще ни при каких обстоятельствах — тот же паттерн предупреждения (условный
   `MessageBoxImage.Warning` только когда есть что терять), что уже есть у `RemovePanel` (ADR-010
   Решение 2), добавлен и туда, поскольку удаление страницы разрушает управляемые копии тем же
   механизмом (`releaseManagedItems: true`).
2. **`ChildWindowViewModel.LoadFromModel`** пересматривает прежнее «read-time-only» решение Amendment
   (2026-09-22) выше: когда `ResolveManagedReplacements` реально что-то заменил (не портал), новый
   путь **сразу** записывается в `model.FilePaths` в памяти, и поднимается `FilesChanged` — тот же
   событие, на который уже подписан `ChildWindow.xaml.cs` (`_viewModel.FilesChanged += (_, _) =>
   _windowManager.SaveWindowsState();`), т.е. это **debounced** сохранение (`SaveWindowsState()`, не
   `SaveWindowsStateNow()`) — ADR-012 Решение 1 не нарушается, никакой синхронной записи на путь
   загрузки не добавлено. Отклонённая ранее альтернатива «запись немедленно» была отклонена именно
   из опасения нарушить debounce-политику; выяснилось, что раздельные «запись в память» и «синхронная
   запись на диск» — разные вещи, и первое можно сделать безопасно, оставив второе как раньше
   (debounced).

Фикс (1) закрывает конкретный отчёт C1 напрямую (диалог теперь видит актуальное состояние); фикс (2) —
защита в глубину для ЛЮБОГО другого кода, читающего `Model.FilePaths` напрямую между `LoadFromModel` и
следующим `SyncToModel()` (не только `RemovePanel`/`RemovePage`).

### M1 — владение managed-копией: манифест не проверял конфликты между панелями

**Проблема.** `TryFindManagedPath` брал **первую** живую запись манифеста для данного original-пути по
порядку перечисления словаря — если бы манифест (в реальности через сторонний скрипт, ручное
редактирование `.manifest.json`, либо баг где-то ещё) когда-либо содержал два разных managed-пути с
одинаковым записанным original-путём, метод произвольно выбирал один. Отдельно от этого — метод в
принципе не мог знать, ссылается ли выбранный кандидат уже на путь, **напрямую** перечисленный в
`FilePaths` какой-то другой (или той же) панели, поскольку `PanelItemStorageService` не имеет
видимости в состояние панелей.

**Решение:**

1. `IPanelItemStorageService.TryFindManagedPath` теперь возвращает `true` только когда для original-пути
   существует **ровно один** живой кандидат — при 2+ живых кандидатах явно отказывает (`false`),
   вместо произвольного выбора (тот же принцип «явный отказ лучше угадывания», что уже применён к
   `RestoreOutcome.OriginalPathUnknown`).
2. Новый read-only метод `IPanelItemStorageService.FindManagedCandidates(originalPath)` возвращает
   **все** живые кандидаты — нужен вызывающему коду, у которого есть видимость сразу во все панели, для
   исключения уже занятых другой панелью кандидатов перед проверкой на однозначность.
3. Новый `WindowManager.ResolveStalePanelPaths` (internal static, вызывается из `LoadWindowsState`
   **до** конструирования любой панели) строит across-panel множество «уже занятых» managed-путей
   (любой путь, напрямую перечисленный как есть в `FilePaths` любой панели, включая ту же самую —
   покрывает и cross-panel owner-ship, и внутрипанельный дедуп) и remapит stale-путь только когда
   среди кандидатов `FindManagedCandidates` остаётся **ровно один** незанятый — немедленно добавляя
   его в множество «занятых», чтобы вторая панель с тем же (по случайности) единственным кандидатом
   не получила его тоже.

**Почему централизованно в `WindowManager`, а не в `ChildWindowViewModel.LoadFromModel`.**
`ChildWindowViewModel.LoadFromModel` резолвит панели по одной — `CreateEachIsolated` вызывает его для
каждой панели независимо, и на момент обработки панели N панели N+1..last ещё не существуют. Определить
«не занят ли этот кандидат другой панелью» требует видимости **во все** панели одновременно — то есть
до того, как хоть одна из них сконструирована. `ChildWindowViewModel.LoadFromModel` сохранён
неизменным в остальном (по-прежнему вызывает `ResolveManagedReplacements`/`TryFindManagedPath` для
любого пути, который централизованный проход `WindowManager` не тронул) — это осознанная защита в
глубину для путей, добавленных вне `LoadWindowsState` (новая панель через `AddPanel` — модель без
`FilePaths`, риска нет), у которых нет доступа к состоянию остальных панелей заранее; `TryFindManagedPath`'s
собственный uniqueness-фикс (пункт 1 выше) всё ещё защищает и этот путь от неоднозначного манифеста,
просто не от cross-panel ownership. **Restore layout-снапшота** (`LayoutSnapshotService.Restore`) был
таким же непокрытым путём до P08 fix cycle 2 — закрыто там же, см. Amendment 3 ниже (MAJOR-1).

**Тесты:** `PanelItemStorageServiceTests` (неоднозначный манифест → `FindManagedCandidates` возвращает
оба, `TryFindManagedPath` отказывает; один из двух «призрачный» → однозначно резолвится в живой),
`WindowManagerTests` (единственный незанятый кандидат → remap; неоднозначные кандидаты → без изменений;
кандидат уже занят другой панелью → без изменений; кандидат уже присутствует в этой же панели → без
дублирования; две панели конкурируют за один кандидат — **поведение изменено в fix cycle 2, см.
Amendment 3**: ни одна панель его не получает, а не «выигрывает первая по порядку обработки»).

## Amendment 3 (2026-09-22, P08 fix cycle 2 — MINOR-2 tie-break rule, MAJOR-1 snapshot-restore parity)

Второй ревью-проход (`docs/fix-prompts/08-icons.md`, fix cycle, iteration 2 of max 2) нашёл два
оставшихся риска в области, которую сам Amendment 2 выше уже описывал: один — в собственном поведении
`ResolveStalePanelPaths` (тай-брейк по кандидату), другой — в том, что `LayoutSnapshotService.Restore`
никогда не получил тот же централизованный проход, который `LoadWindowsState` получил в Amendment 2.

### MINOR-2 — тай-брейк «первая панель выигрывает» заменён на «явный отказ обеим»

**Проблема.** Amendment 2's `ResolveStalePanelPaths` (single-pass реализация) обрабатывала панели по
порядку и **немедленно** добавляла успешно разрешённый кандидат в множество «занятых» — так что если
ДВЕ РАЗНЫЕ stale-записи (в одной или в разных панелях) независимо и однозначно резолвились в один и
тот же единственный живой кандидат, первая по порядку панель молча забирала его, а вторая оставалась
stale. Само по себе разрешение оставить вторую stale — верно; проблема в том, ЧТО именно определяло,
какая из двух панелей «первая»: чистая случайность порядка перечисления/итерации, не отражающая
никакого реального различия между двумя записями. Это противоречит принципу «явный отказ лучше
угадывания», которым обоснован весь остальной дизайн Решения 3 (`RestoreOutcome.OriginalPathUnknown`)
и самого `TryFindManagedPath` (Amendment 2, пункт 1) — там неоднозначность отклоняется целиком, а не
разрешается произвольным выбором.

**Решение.** `ResolveStalePanelPaths` теперь работает в два прохода:

1. **Discovery-проход** — для каждой stale-записи (без мутации `FilePaths`) вычисляется её единственный
   незанятый кандидат (если он однозначен по прежним правилам — Решение 1 выше), и ведётся счётчик:
   сколько РАЗНЫХ stale-записей во всём проходе (по всем панелям) сошлись на одном и том же кандидате.
2. **Apply-проход** — remap применяется только для записей, чей кандидат в счётчике встретился РОВНО
   один раз. Если кандидат «контестится» двумя и более независимыми stale-записями, НИ ОДНА из них его
   не получает — обе (или больше) остаются stale, деградируя до видимого серого placeholder или
   generic-by-extension иконки (`IconProvider`'s missing-path fallback, UX P1 fix cycle 1) — не тихо
   неверной иконки.

**Trade-off:** в редком (и уже само по себе аномальном — два оригинала не должны честно указывать на
одну и ту же managed-копию) случае состязания обе панели остаются stale вместо того, чтобы хотя бы одна
получила рабочую иконку. Признано приемлемым: пользователь всё ещё видит и может опознать оба элемента
(placeholder/generic-иконка, не пустой слот), и это тот же trade-off, что уже принят для неоднозначного
манифеста (Amendment 2, Решение 1) — здесь просто источник неоднозначности другой (два предложения от
РАЗНЫХ stale-записей, а не два кандидата от ОДНОЙ).

**Тесты:** `WindowManagerTests.ResolveStalePanelPaths_TwoPanelsCompetingForTheSameSingleCandidate_BothRefuseTheAmbiguousClaim`
(переименован и переписан из cycle 1's `..._OnlyTheFirstWins` — старое имя и ассерт теперь описывали
поведение, признанное дефектом) + новый `..._UncontestedCandidateAlongsideAContestedOne_StillRemapsTheUncontestedOne`
(регрессия: контест по одному кандидату не должен коллатерально повредить не связанный с ним
однозначный remap в том же батче).

### MAJOR-1 — `LayoutSnapshotService.Restore` теперь тоже проходит через `ResolveStalePanelPaths`

**Проблема.** Amendment 2 (и последующая правка Amendment 2 выше) явно документировали restore
layout-снапшота как путь, СОЗНАТЕЛЬНО не покрытый централизованным cross-panel проходом — панели там
создавались по одной, `Restore` десериализовывал JSON и сразу вызывал `IWindowManager.CreateChildWindow`
внутри того же цикла. Две панели снапшота с разными stale-оригиналами, однозначно (по прежним,
single-panel правилам) ведущими к одной и той же managed-копии, обе бы её присвоили — тот же класс
cross-panel-ownership бага, что M1 (Amendment 2) уже закрыл для `LoadWindowsState`, но здесь он
оставался открытым, потому что централизованный проход туда просто никогда не был подключён.

**Решение.** `LayoutSnapshotService.Restore` теперь десериализует ВСЕ панели снапшота в промежуточный
список `List<ChildWindowModel>` (включая присвоение свежего `Id` каждой) ДО вызова
`IWindowManager.CreateChildWindow` для любой из них, затем вызывает
`WindowManager.ResolveStalePanelPaths(models, storage)` один раз для всего списка — дословно то же,
что `LoadWindowsState` уже делает — и только потом создаёт панели в цикле. Конструктор
`LayoutSnapshotService` получил новую зависимость `IPanelItemStorageService` (уже зарегистрирована в DI
контейнере — `DesktopOrganizer.Services`'s `DiConfig.cs` — никаких новых регистраций не потребовалось).

**Почему не другой подход.** Дублировать логику `ResolveStalePanelPaths` внутри `LayoutSnapshotService`
отдельным методом отклонено — тот же алгоритм (discovery+apply два прохода, claimed-set, MINOR-2
тай-брейк) обслуживал бы два места, расходясь при следующем изменении. Существующий метод уже
`internal static` именно для переиспользования между классами в сборке `DesktopOrganizer.UI`
(комментарий на самом методе это явно предусматривает).

**Тесты:** `LayoutSnapshotServiceTests` — `Restore_SinglePanelWithUnambiguousStaleOriginal_RemapsToManagedCopyBeforeCreating`
(базовый случай: `Restore` вообще выполняет резолюцию — раньше не выполнял никакой, полагаясь на код
пути `LoadWindowsState`, которого `Restore` никогда не вызывает), `..._TwoPanelsWithDifferentStaleOriginalsResolvingToTheSameSingleCandidate_NeitherClaimsIt`
(сам MAJOR-1 сценарий + MINOR-2 тай-брейк вместе), `..._StaleOriginalCandidateAlreadyReferencedByAnotherPanel_LeavesItUntouched`
(cross-panel ownership, не тай-брейк: кандидат уже прямо используется другой панелью снапшота).
