# ADR-010: Очистка managed-копий при удалении панели — разделение «закрыть» vs «удалить навсегда»

**Статус:** Accepted — Amended 2026-09-27 (ADR-035: «удалить» всегда через Корзину, fail-visibly); Amended 2026-09-27 ×2 (ADR-040: команда «Убрать из панели» удалена); Amended 2026-09-29 (ADR-045: третье правило релиза — дублирование). **Действующий свод правил судьбы managed-файлов — [ADR-048](ADR-048-panel-item-lifecycle-release-rules.md); таблица вызывающих мест в Решении 1 ниже — историческая, актуальная — в ADR-048 и в разделе «Amendment 2026-10-09».**
**Дата:** 2026-07-26

---

## Контекст

[ADR-009](ADR-009-drag-drop-move-semantics.md) ввёл Move-семантику: drop перемещает файл в приватное
managed-хранилище приложения (`%LocalAppData%\DesktopOrganizer\PanelItems`), а «Убрать из панели»
возвращает его обратно (`Restore`). ADR-009 зафиксировал как принятый технический долг, что при
**полном удалении панели** (`RemovePanelCommand`) managed-копии её файлов не подчищались — со
временем в `PanelItems` накапливались файлы без активной ссылки на них ни из одной панели.

Задача (`docs/prompts/outstanding-followups.md`, пункт 3) — решить, как отличать «панель просто
закрывается» от «панель удаляется навсегда» (до этой правки оба пути вели в один и тот же
`ChildWindow.Dispose()`), и на основе этого добавить очистку осиротевших managed-копий.

---

## Решения

### Решение 1: `RemoveChildWindow(Guid, bool releaseManagedItems)` — явный флаг у единственной точки удаления, а не эвристика в `Dispose()`

`WindowManager.RemoveChildWindow` получил перегрузку `RemoveChildWindow(Guid windowId, bool
releaseManagedItems)`. Существующая сигнатура `RemoveChildWindow(Guid windowId)` сохранена как
тонкая обёртка над новой с `releaseManagedItems: false` (безопасный default). Очистка managed-копий
(`ReleaseManagedItemsIfRequested` → `ReleaseManagedItems`, вызывает `IPanelItemStorageService.Release`
для каждого managed-пути в `ChildWindowModel.FilePaths`) происходит **внутри `RemoveChildWindow`**,
не в `ChildWindow.Dispose()`/`OnClosing` — те продолжают вызываться при обычном закрытии окна
(панели должны переживать перезапуск приложения), поэтому релиз managed-копий там стирал бы данные
при каждом обычном завершении работы. `RemoveChildWindow` — единственная точка, где приложение
принимает осознанное решение «эта панель удаляется навсегда», и только там уместно спрашивать
`releaseManagedItems`.

**Три реальных вызывающих места, с разной семантикой:**

| Вызывающая сторона | Сценарий | `releaseManagedItems` |
|---|---|---|
| `MainWindowViewModel.RemovePanel` | Пользователь явно удаляет одну панель через UI («Удалить панель») | `true` |
| `PageManagerService.RemovePage` | Пользователь удаляет страницу целиком — уничтожает все панели на ней | `true` |
| `LayoutSnapshotService.Restore` | Удаляет текущий набор панелей, чтобы тут же пересоздать его из JSON layout-снапшота с теми же managed-путями | `false` |

Первые два — перманентное удаление: managed-файлы этих панелей больше никогда не будут нужны ни
одной панели, их нужно освободить (иначе они осиротевают в `PanelItems`, тот же класс проблемы, что
`Restore.Failed` в ADR-009). Третий — **не удаление, а замена**: снапшот восстанавливает панели,
ссылающиеся на **те же** managed-пути, что и удаляемые сейчас панели.

**Почему это важно задокументировать явно:** первая версия этой реализации не делала такого
разделения (`releaseManagedItems` не существовало, либо вызывался безусловно) и содержала
**критический баг потери данных** — восстановление layout-снапшота удаляло из `PanelItems`
managed-файлы, на которые тут же пытались сослаться пересоздаваемые из снапшота панели, оставляя их
битыми. Баг был найден ревью **до мержа**, не после — это тот тип регрессии, на который эта же
область кода уже наступала раньше (ADR-009, Copy→Move: первая итерация исправляла один баг с
битыми ссылками и почти сразу вводила другой класса рисков). Инвариант «`releaseManagedItems: true`
— только для перманентного удаления, `LayoutSnapshotService.Restore` всегда `false`» должен
сохраняться при любых будущих изменениях вызывающих мест `RemoveChildWindow`.

**Альтернатива (отклонена):** эвристика в `Dispose()`/`OnClosing`, различающая «закрытие» и
«удаление» по какому-то косвенному признаку (например, флаг на модели). Отклонена — `Dispose()`
вызывается из общего кода жизненного цикла окна и не имеет естественного места для явного
пользовательского намерения; отдельный explicit-параметр в публичном API вызывающей стороны надёжнее
скрытого состояния.

**Trade-off:** три вызывающих места должны согласованно передавать правильное значение — если в
будущем появится четвёртое место, вызывающее `RemoveChildWindow`, разработчику придётся осознанно
решить, какой семантике оно соответствует (см. таблицу выше и XML-doc на методе в
`WindowManager.cs`).

### Решение 2: Confirm перед удалением панели — только если есть что терять

`MainWindowViewModel.RemovePanel` перед вызовом `RemoveChildWindow(..., releaseManagedItems: true)`
запрашивает подтверждение через `IConfirmationService.Confirm`. Текст и иконка диалога зависят от
того, есть ли у панели managed-файлы (`_selectedPanel.FilePaths.Any(_itemStorage.IsManaged)`):

- **Есть managed-файлы** → предупреждение с иконкой `MessageBoxImage.Warning` и явным текстом о том,
  что файлы, перемещённые в панель, будут удалены с диска безвозвратно (без возможности
  восстановления через Корзину).
- **Нет managed-файлов** (все элементы — прямые ссылки/Folder Portal) → нейтральный текст без
  предупреждения — панель просто перестаёт существовать, ничего пользовательского не теряется.

**Почему так:** удаление панели с managed-файлами — единственное действие в приложении, которое
физически стирает файлы пользователя мимо Корзины (см. открытый вопрос ниже). Условный текст
предупреждения даёт точный сигнал риска именно тогда, когда он есть, не приучая пользователя
игнорировать диалог, который в большинстве случаев (панели без managed-файлов, Folder Portals)
ничего не удаляет по-настоящему.

**Альтернатива (отклонена):** одинаковый нейтральный confirm для всех панелей — недостаточно явно
предупреждает о потере данных. Одинаковое строгое предупреждение для всех — создаёт «усталость от
диалогов» там, где реальной потери данных нет.

**Trade-off:** нет — стоимость проверки `IsManaged` на несколько путей пренебрежимо мала.

## Последствия

- `IWindowManager.RemoveChildWindow(Guid)` сохранён без изменений сигнатуры для обратной
  совместимости вызывающего кода; новая перегрузка `RemoveChildWindow(Guid, bool)` — единственное
  место, откуда осмысленно передавать `true`.
- `WindowManager.ReleaseManagedItems`/`ReleaseManagedItemsIfRequested` — `internal static`,
  тестируются напрямую (без реального WPF `ChildWindow`) в
  `tests/DesktopOrganizer.Tests/Unit/Services/WindowManagerTests.cs` (или аналогичном файле).
- Технический долг ADR-009 «managed-копии не подчищаются при удалении панели» — закрыт.
- **Открытый архитектурный вопрос для бэклога (НЕ решено, зафиксировано для будущего обсуждения с
  пользователем):** в эталонном Stardock Fences удаление fence никогда не уничтожает файлы — fence
  чисто визуальная группировка, иконки остаются на рабочем столе. В этом приложении из-за
  архитектуры `IPanelItemStorageService` (файлы физически перемещаются при попадании в панель,
  ADR-009 Решение 1) удаление панели с managed-файлами — единственный сценарий в приложении, где
  реально стираются пользовательские файлы мимо Корзины. Confirm-диалог (Решение 2 выше) митигирует
  риск неожиданности, но не устраняет само расхождение с духом Fences. Более точная по паритету
  реализация — «удалить панель = вернуть все managed-файлы на рабочий стол» (переиспользуя
  `IPanelItemStorageService.Restore`, как уже делает «Убрать из панели» для одного элемента) вместо
  «удалить панель = стереть managed-файлы». Не реализовано сейчас — см. `docs/ROADMAP.md`, раздел
  «Сквозные задачи».

## Amendment (2026-09-27, release polish 1.0 — ADR-040)

Контекст и Решение 1 выше упоминают «Убрать из панели» как существующую WPF-команду контекстного меню
(`Restore` для одного элемента) в качестве прецедента для гипотетического «удалить панель = вернуть все
managed-файлы» (открытый архитектурный вопрос ниже). [ADR-040](ADR-040-native-shell-context-menu.md)
(2026-09-27, тот же релизный цикл) удалил собственное WPF-меню файла целиком — «Убрать из панели» как
*команда меню* больше не существует, заменена нативным shell-меню (drag-out, [ADR-036](ADR-036-panel-item-drag-out.md),
для перемещения элемента без удаления; перехваченное «Удалить» для managed-элемента, вызывающее тот же
`Restore` перед отправкой в Корзину). Аналогия в открытом вопросе ниже («переиспользуя
`IPanelItemStorageService.Restore`, как уже делает «Убрать из панели» для одного элемента») остаётся верной
по существу — `Restore` как раз и переиспользован ADR-040 для одиночного managed-элемента — само название
исторической команды меню в приложении больше не встречается.

Отдельно: [ADR-035](ADR-035-panel-deletion-recycle-bin.md) (тот же день, ранее в этом цикле) уже закрыл
открытый вопрос ниже про «удаление панели стирает managed-файлы мимо Корзины» — panel-/page-level удаление
теперь всегда идёт через Корзину, не через прямое `File.Delete`/`Directory.Delete`. Буквальный
Fences-паритет («вернуть файлы на рабочий стол» вместо recycle) по-прежнему не реализован для panel-/
page-level удаления — см. ADR-035's собственное «Known limitation».

## Amendment (2026-09-29, бэклог 1.x пункт 8 — ADR-045)

[ADR-045](ADR-045-panel-clone-to-page.md) добавляет ещё одного явного вызывающего для управляемого
хранилища — «Скопировать на страницу», у которого своё, отличное от «удаления панели»/«закрытия панели»
правило релиза: **дублирование**, не освобождение. `IPanelItemStorageService.CopyManaged`
(новый метод, не пересматривает `Release`/`Restore`/`IsManaged`) создаёт независимую копию элемента в
своём собственном новом `PanelItems\{guid}\`, никогда не касаясь оригинала. Откат неудавшегося
клонирования (`DiscardCopies`) удаляет только эти свежесозданные копии напрямую — это не третий случай
«закрыть vs удалить», а операция над контентом, который ещё не стал частью ни одной видимой пользователю
панели (см. также amendment к [ADR-035](ADR-035-panel-deletion-recycle-bin.md) выше). Инвариант вызывающих
мест (таблица в Решении 1) для `RemoveChildWindow`/`releaseManagedItems` не меняется — клонирование не
вызывает ни `Release`, ни `RemoveChildWindow` вовсе.

## Amendment (2026-10-09, ADR-audit WP-E / ADR-048): актуальная таблица вызывающих мест

Таблица в Решении 1 устарела (после ADR-035 `Release(string)` удалён, «удалить» = Корзина, а
`PageManagerService.RemovePage` больше не передаёт `true`). Сверено с кодом
(`WindowManager.RemoveChildWindow`, `PageManagerService.RemovePage`, `LayoutSnapshotService.Restore`,
`MainWindowViewModel.RemovePanel`, `WindowManager.ClonePanelToPage`):

| Вызывающая сторона | Сценарий | `releaseManagedItems` | Что происходит с managed-файлами |
|---|---|---|---|
| `MainWindowViewModel.RemovePanel` | Пользователь удаляет одну панель | `true` | `RemoveChildWindow` сам делает один batch `IPanelItemStorageService.ReleaseToRecycleBin` из хранилища; при остатке — `PanelRemovalResult.Blocked`, панель остаётся (all-or-kept) |
| `PageManagerService.RemovePage` | Пользователь удаляет страницу | `false` (`deferSave: true`) | **Сам** собирает managed-пути всех панелей страницы и делает один batch `ReleaseToRecycleBin` **до** удаления панелей; при остатке страница и все панели остаются; затем `RemoveChildWindow(..., releaseManagedItems: false, deferSave: true)` — файлы уже в Корзине |
| `LayoutSnapshotService.Restore` | Замена набора панелей из снапшота | `false` (`deferSave: true`) | Ничего — пересоздаваемые панели ссылаются на те же managed-пути |
| `WindowManager.ClonePanelToPage` (откат) | Неудавшееся клонирование | не вызывается | `DiscardCopies` удаляет только свежие копии напрямую; панель-клон снимается из `_childWindows` и закрывается напрямую (не через `RemoveChildWindow(true)`) |

Инвариант Решения 1 уточнён: `releaseManagedItems: true` допустим только для перманентного удаления **одной
панели** (`RemovePanel`); при массовом удалении (страница) вызывающий сам делает batch-recycle и передаёт
`false`. Одноаргументная `RemoveChildWindow(Guid)` (эквивалент `false`) не имеет вызывающих в `src/`.
«Закрытие» окна панели (`ChildWindow.OnClosing`/`Dispose` при завершении приложения) managed-файлы не
трогает: панель переживает перезапуск, файлы остаются в хранилище.

Подтверждение в `RemovePanel` (Решение 2) по-прежнему зависит от наличия managed-файлов, но текст больше не
говорит «безвозвратно, мимо Корзины» — после ADR-035 файлы уходят в Корзину.
