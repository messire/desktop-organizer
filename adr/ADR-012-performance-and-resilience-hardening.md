# ADR-012: Фаза 7 — Persistence-дебаунс, вынос машины состояний хука, Freeze()-инвариант, авторитетный кеш манифеста

## Решение 1: Двухуровневая политика persistence — debounced `SaveWindowsState` vs синхронный `SaveWindowsStateNow`

**Проблема (аудит п.8, 11):** `WindowManager.SaveWindowsState` полностью сериализовала все панели и
писала `Properties.Settings.Default.Save()` (весь `user.config`) на каждое мелкое действие без
дебаунса и без `try/catch` — сбой записи (диск полон, файл залочен) вылетал необработанным на самом
обычном действии пользователя.

**Решение:**

- `IWindowManager` получил два метода с разной семантикой:
  - `SaveWindowsState()` — **планирует** отложенную запись через новый `SaveScheduler`
    (`src/DesktopOrganizer.UI/Services/SaveScheduler.cs`): повторные вызовы внутри окна **500 мс**
    (`WindowManager.SaveDebounceWindow`) схлопываются в одну запись.
  - `SaveWindowsStateNow()` — отменяет ожидающий отложенный вызов и пишет **синхронно, немедленно**.
- Таймер дебаунса абстрагирован за `IDebounceTimer`/`DispatcherDebounceTimer`
  (`src/DesktopOrganizer.UI/Services/IDebounceTimer.cs`, `DispatcherDebounceTimer.cs`) и тикает на UI-потоке
  (`Application.Current.Dispatcher`), т.к. запись синхронизирует живые WPF-окна (`SyncToModel`). Если
  `Application.Current == null` (тесты/headless/поздний shutdown) — `SaveScheduler.Request()`
  деградирует до немедленной синхронной записи, а не теряет запрос молча.
- Сама запись (`WindowManager.PersistWindowsState`) обёрнута в `try/catch`, никогда не пробрасывает
  исключение; sync живых окон изолирован по элементу (`SyncEachIsolated`) — падение одной панели не
  срывает запись остальных.
- Дополнительно: запись пропускается целиком, если сериализованный JSON идентичен последнему
  сохранённому (`_lastSavedJson`) — сравнение строки перед `Settings.Save()`.
- Загрузка (`LoadWindowsState`) получила ту же изоляцию по элементу: `CreateEachIsolated` создаёт
  панели по одной под собственным `try/catch`, битая панель логируется и пропускается, остальные
  грузятся; ловится не только `JsonException`, но и любое исключение десериализации.
- **Бэкап битого состояния (C4, взято):** если загрузка была неполной (не распарсился JSON целиком
  или пропущена хотя бы одна панель), следующая же запись сначала сохраняет исходный сырой payload в
  `%LocalAppData%\DesktopOrganizer\ChildWindowsState.corrupt-<yyyyMMdd-HHmmss>.json`, прежде чем
  перезаписать `ChildWindowsState` урезанным восстановленным набором — иначе полная раскладка
  пользователя терялась бы безвозвратно на первом же автосохранении после сбоя.

**Список call-site'ов — какой метод когда использовать:**

| Вызывающий код | Метод | Почему |
|---|---|---|
| `ChildWindow.xaml.cs` (перемещение, ресайз, roll-up, коммит переименования, смена вида/фильтра — 5 мест), `FilesChanged`-обработчик там же | `SaveWindowsState()` (debounced) | Частые мелкие действия — не структурные изменения набора панелей |
| `MainWindowViewModel.cs:428` (правка выбранной панели из окна настроек) | `SaveWindowsState()` (debounced) | Правка одной панели вживую, не создание/удаление |
| `WindowManager.OnMonitorsChanged` | `SaveWindowsState()` (debounced) | Массовый re-clamp панелей при смене конфигурации мониторов, не единичное структурное событие |
| `App.OnExit` | `SaveWindowsStateNow()` | Структурное/финальное: должно писаться **до** `_serviceProvider.Dispose()`, иначе последнее действие пользователя перед выходом теряется |
| `App.CreateLassoPanel` | `SaveWindowsStateNow()` | Создание новой панели — структурное изменение |
| `WindowManager.RemoveChildWindow(id, releaseManagedItems)` (обычное удаление одной панели) | `SaveWindowsStateNow()` | Структурное; при `deferSave: true` (см. ниже) вызывающий сам обязан флашнуть после цикла |
| `LayoutSnapshotService.Restore` | `SaveWindowsStateNow()` | Массовое пересоздание набора панелей из снапшота — структурное, и debounced-запись рискует не успеть до следующего действия пользователя |
| `PageManagerService.RemovePage` | `SaveWindowsStateNow()` | Удаление страницы уничтожает несколько панелей разом — структурное |

`RemoveChildWindow` получил перегрузку с `bool deferSave` специально для *bulk*-циклов (снапшот-рестор,
удаление страницы): внутри цикла удаления используется `deferSave: true` (просто планирует запись,
не пишет N раз подряд), а сам вызывающий код обязан один раз вызвать `SaveWindowsStateNow()` после
цикла. Одиночное удаление одной панели всегда использует `deferSave: false` по умолчанию.

**Trade-off (осознанно принят):** окно потери состояния при жёстком завершении процесса (kill, BSOD)
внутри 500 мс дебаунса. Ограничено самим окном и тем, что все структурные операции и выход всегда
синхронны — теряться может максимум последнее «частое» действие (drag/resize/rename) прямо перед
крашем, не весь layout.

## Решение 2: Вынос чистой машины состояний жеста из нативного хука — паттерн, расширяющий прецедент ADR-011

**Проблема (аудит п.9):** `DesktopGestureService.HookCallback` (`WH_MOUSE_LL`) не был обёрнут в
`try/catch` целиком — исключение подписчика (`DesktopDoubleClicked`/`LassoCompleted`) улетало наружу
прямо из системного хука, что по инварианту проекта («ошибка в колбэке хука тормозит ввод системы»)
недопустимо.

**Решение:**

- `HookCallback` теперь — минимальный диспетчер: `nCode < 0` → сразу `CallNextHookEx`; иначе всё тело
  обёрнуто в `try/catch (Exception)`, `CallNextHookEx` вызывается **на всех путях** (в т.ч. на пути
  исключения), а при исключении `swallow` всегда `false` — баг подписчика никогда не превращается в
  «пропавший правый клик» по всей системе.
- Реальная логика вынесена в `ProcessMessage` (маршалинг `lParam`, вызов машины состояний, уведомление
  подписчиков внутри собственного `try/catch`, чтобы падение подписчика не влияло на решение о
  `swallow`).
- **Сама машина состояний жеста вынесена в отдельный чистый класс** —
  `src/DesktopOrganizer.Services/Tools/DesktopGestureStateMachine.cs`, без единого P/Invoke, без
  событийной обвязки. Она принимает `(message, x, y)` и внешнюю среду через интерфейс
  `IDesktopGestureEnvironment` (`TickCount`, `DoubleClickTime`, `IsDesktopPoint`, `IsEmptyDesktopPoint`)
  и возвращает immutable-решение `DesktopGestureDecision { Swallow, RaiseDoubleClick, Lasso }`.
  `DesktopGestureService` реализует `IDesktopGestureEnvironment` сам на себе (та же P/Invoke-обёртка,
  что и раньше) и просто скармливает сообщения машине.
- Порядок сброса состояния критичен: `HandleRightUp` сбрасывает `_rightDown`/`_rightDragging`
  **до** формирования решения о `Lasso`, а не после — исключение у подписчика `LassoCompleted` больше
  не может оставить машину состояний «залипшей» во взведённом правом клике.
- Это прямое расширение прецедента **ADR-011** (`GridSnap` — чистый статический helper без WPF/P/Invoke
  рядом с `GridMetrics`): там паттерн применён к вычислению позиции при драге панели, здесь — впервые
  к самому нативному хук-колбэку. Общий принцип для проекта: **любая логика принятия решения внутри
  нативного колбэка, которую в принципе можно отделить от P/Invoke-обвязки, должна жить в отдельном
  чистом классе**, тестируемом без Windows-GUI (`DesktopGestureStateMachineTests.cs`,
  `GridSnapTests.cs` — оба в среде без реального хука/окна).
- **Осознанное решение (подтверждено ревью): кто решает про `swallow`.** Решение о подавлении события
  (`Swallow`) принимает исключительно машина состояний — оно фиксируется **до** вызова подписчиков и
  не зависит от того, как отработала их доставка (`RaiseSubscribers` — отдельный `try/catch`, не
  влияющий на уже вычисленный `decision.Swallow`). Альтернатива («не глотать up, если подписчик
  упал») отклонена: `swallow` — это факт про завершённый нативный жест (лассо состоялось), а не про
  успех доставки события внутри процесса; смешение этих двух вещей сделало бы поведение хука зависимым
  от кода подписчиков, которых у события в перспективе может быть несколько.

**Не входит:** смена типа хука, перенос на отдельный поток, изменение порогов `DragThreshold`/
`DoubleClickSlop` — эти инварианты сохранены 1:1 с поведением до рефакторинга.

## Решение 3: Инвариант — все `ImageSource`, покидающие Services-слой, обязаны быть `Freeze()`-нуты

**Проблема (аудит п.1, 3 — попутно):** `IconFactory.CreateBitmap(IntPtr)` не вызывал `Freeze()`, хотя
аналогичный код в `NativeApi.cs:128` для системных иконок уже это делал — несогласованность в одном и
том же слое.

**Решение:** зафиксирован явный инвариант — **любой `ImageSource`, создаваемый в
`DesktopOrganizer.Services` и возвращаемый наружу (в кеш `IconProvider` или напрямую в UI через
`IIconProvider`/`IIconFactory`), обязан быть заморожен (`.Freeze()`) до возврата.** Реализовано во всех
трёх точках создания:

- `NativeApi.cs:128` — уже соответствовал (прецедент, аудит зафиксировал как образец).
- `IconFactory.CreateBitmap(IntPtr iconHandle)` — `bitmap.Freeze()` добавлен.
- `IconFactory.CreateBitmap()` (плейсхолдер) — `bitmap.Freeze()` уже стоял, плюс сам плейсхолдер
  теперь создаётся лениво и переиспользуется как единственный инстанс (см. Решение 5) — заморозка
  делает переиспользование безопасным при обращении не с UI-потока.

**Почему это инвариант, а не точечный фикс:** `IconProvider`'s LRU-кеш (Решение 5) — общий,
долгоживущий кеш, раздающий один и тот же `ImageSource` многим панелям одновременно; незамороженный
`Freezable` несёт привязку к потоку-создателю и обвалился бы при любом обращении не с исходного
потока. Любой будущий код, добавляющий новый путь создания `ImageSource` в Services, обязан вызывать
`Freeze()` перед возвратом — иначе кеш/переиспользование этого объекта в другом потоке/панели по
умолчанию небезопасны.

## Решение 4: `PanelItemStorageService` — авторитетный кеш манифеста в памяти, единственный владелец storage root в рамках процесса

**Проблема (аудит п.7):** `WriteManifestEntry`/`ReadManifestEntry`/`RemoveManifestEntry` читали и
перезаписывали **весь** `.manifest.json` на каждую операцию — drop N файлов давал N чтений + N записей.

**Решение (Вариант A из мастер-плана; Вариант B «batch-scope» и Вариант C «append-only журнал»
рассмотрены и отклонены — см. план, Блок F):**

- Манифест загружается с диска **лениво и один раз** за время жизни экземпляра сервиса
  (`EnsureManifestCacheUnlocked`, под `_manifestLock`) и дальше живёт как `Dictionary<string,string>`
  в памяти (`_manifestCache`) — единственный источник правды для `ReadManifestEntry`/`IsManaged` на
  всю сессию. Файл на диске после первой загрузки **только пишется** (write-through), никогда не
  перечитывается повторно.
- `WriteManifestEntry`/`RemoveManifestEntry` мутируют кеш и сразу пишут на диск (атомарный swap через
  temp-файл + `File.Move(overwrite: true)`, как и раньше). Итог для drop 10 файлов: было 10 чтений +
  10 записей → стало 1 чтение + 10 записей.
- **Защита от отравления кеша транзиентным сбоем чтения:** если чтение манифеста с диска бросает
  (например, временная sharing violation от антивируса сразу после атомарного `File.Move` записи),
  `_manifestCache` **намеренно не выставляется** — возвращается одноразовый пустой словарь с флагом
  `Trusted = false`. Следующий вызов повторит попытку чтения с нуля. Если бы вместо этого кешировался
  пустой словарь как «настоящий», следующая же запись переписала бы реальный файл манифеста пустым —
  необратимая потеря всех original-path записей.
- **Защита от продолжения деструктивного шага при сбое самой записи:** в `MoveIn`/`MoveInDirectory`
  запись в манифест теперь делается **до** `File.Move`/`File.Delete` оригинала (а не после, как
  раньше) — `destPath` известен заранее. Если `WriteManifestEntry` вернула `false` (кеш недоверенный
  ИЛИ сама запись на диск не удалась) — метод **прерывается до какого-либо деструктивного шага**,
  оригинал остаётся нетронутым. Если сама запись прошла, но последующее перемещение/копирование не
  удалось — запись манифеста откатывается (`RemoveManifestEntry`) в `catch`/ветке неудачи. Это
  устраняет реальный сценарий потери данных, описанный в [ADR-009](ADR-009-drag-drop-move-semantics.md)
  «Известное ограничение»: раньше крах процесса между перемещением файла и записью манифеста терял
  original path и превращал будущее «убрать из панели» в безвозвратное удаление вместо восстановления.

**Инвариант, фиксируемый этим решением:** `PanelItemStorageService` — **единственный владелец своего
storage root в рамках одного процесса**. Правки `.manifest.json` вне процесса (вручную или другим
экземпляром приложения) после первой загрузки кешем не подхватываются до перезапуска.

**Известный открытый риск (не устранён в этой фазе, зафиксировать в бэклоге):** межпроцессной
синхронизации/single-instance guard **нет**. Если пользователь запустит два экземпляра приложения
одновременно, оба процесса независимо загрузят один и тот же `.manifest.json` в свой кеш и оба будут
писать write-through в один и тот же файл — младшая по времени запись побеждает, старший процесс
работает с устаревшим кешем до своего следующего перезапуска. До этой фазы риск был меньше
(перечитывалось на каждую операцию — рассинхронизация была короче по времени, но конфликты записи всё
равно были возможны); write-through-кеш делает «один процесс = единственный источник правды в рамках
своей сессии» более несущим инвариантом, чем раньше. Единственная существующая защита сегодня —
поведенческая (приложение не предполагает нескольких одновременных запусков), не техническая.
**Рекомендация:** добавить single-instance guard (именованный mutex/pipe) отдельным пунктом, не в
этой фазе.

## Дополнительно (мелкие решения этой фазы, одним разделом)

- **Замороженные bounded-кеши кистей в конвертерах** (`HexBrushConverter`, `ColorOpacityBrushConverter`):
  `Convert` возвращает переиспользуемую замороженную `SolidColorBrush` вместо новой на каждый вызов;
  кеш ограничен константой (`HexBrushConverter.MaxCachedBrushes = 256`, поднято с изначальных 64 по
  результатам ревью — один драг слайдера прозрачности сам по себе создаёт до 256 разных значений
  альфа), простая стратегия «переполнение → очистить весь кеш» вместо LRU (оправдано малым размером).
  Ключ нормализуется (`Trim().ToUpperInvariant()`), невалидный hex по-прежнему даёт
  `Brushes.Transparent` (уже заморожен фреймворком). **Осознанный trade-off:** замороженная кисть
  неизменяема — если в будущем понадобится анимировать цвет кисти напрямую (а не пересозданием через
  биндинг, как сейчас), это решение придётся пересмотреть.
- **Ограниченный LRU-кеш иконок** (`IconProvider`, аудит п.1): `ConcurrentDictionary` без границ
  заменён на `Dictionary` + `LinkedList` под `lock` с ёмкостью **1024** и вытеснением по LRU.
  Freshness-check (перечитать иконку при изменении `LastWriteTimeUtc`) применяется **только** к
  расширениям, чья иконка вшита в сам файл (`.exe`, `.dll`, `.ico`, `.lnk`, `.cur`, `.url`) — для папок
  `LastWriteTimeUtc` меняется на каждое добавление/удаление дочернего элемента, что при наивной
  проверке свежести срывало бы кеш на каждый ресинк Folder Portal. `IIconProvider` не расширен API
  инвалидации — вытеснение по LRU и freshness-check закрывают оба сценария аудита (удалённый файл,
  закрытая панель) без протекания деталей кеширования в UI-слой.
- **`Reset`-уведомление вместо `Clear()` + N×`Add()`** (`ObservableRangeCollection<T>.ReplaceAll`,
  аудит п.6): используется в `BaseViewModel.OnSourceChanged`/`ReplaceFileItems` и
  `ChildWindowViewModel.ApplyFilter`. Один `NotifyCollectionChangedAction.Reset` + одно уведомление
  `FileCountText` на всю перестройку вместо N+1 отдельных событий.
- **Регистронезависимая дедупликация путей** (`BaseViewModel._allItemPaths`, аудит п.5): O(1)-индекс
  `HashSet<string>(StringComparer.OrdinalIgnoreCase)` заменяет `_allItems.Any(...)`; дедупликация
  осознанно переведена с ordinal на `OrdinalIgnoreCase` — согласуется с уже регистронезависимым
  `RemoveFileByPath` и корректна для путей Windows.
- **Отписка от `Model.PropertyChanged`** (`ChildWindowViewModel`, аудит п.2): подписка перенесена в
  сеттер `Model` (отписаться от старого, подписаться на новый), `Dispose()` отписывается идемпотентно.
  `LoadFromModel` теперь делает `ReplaceAll` вместо `AddFiles` при загрузке файлов — иначе повторный
  `LoadFromModel` (переподключение VM к другой модели) копил файлы старой модели поверх новой.

## Amendment 2026-09-30 ([ADR-046](ADR-046-background-icon-loading.md))

Инвариант Решения 3 («любой `ImageSource`, создаваемый в `DesktopOrganizer.Services` и возвращаемый наружу,
обязан быть заморожен») распространён на **межпоточную передачу**: с ADR-046 иконки создаются на
выделенном STA-воркере фоновой очереди и пересекают границу поток-воркер → UI-поток через
`SynchronizationContext.Post`. Граница доставки несёт **явную рантайм-проверку** (`!icon.IsFrozen` →
`Outcome = Failed` + событие лога `IconResultNotFrozen`), а не только полагается на то, что каждая точка
создания сама вызвала `.Freeze()` — в .NET 8 `Debug.Assert` без отладчика валит процесс, поэтому нарушение
инварианта должно деградировать, а не падать. Сам факт «каждый `ImageSource` из Services заморожен перед
возвратом» не изменился — добавлена вторая, независимая линия защиты на стороне потребителя.

## Последствия

- `IWindowManager` расширен `SaveWindowsStateNow()` и третьей перегрузкой `RemoveChildWindow` с
  `deferSave` — все существующие тесты/моки (`Mock<IWindowManager>`) продолжают работать без правок.
- Новые тестируемые чистые типы: `SaveScheduler`, `DesktopGestureStateMachine`,
  `ObservableRangeCollection<T>` — расширяют список чистых helper-классов проекта рядом с `GridSnap`/
  `GridMetrics` (ADR-005, ADR-011).
- `IIconProvider`/`IPanelItemStorageService` — публичные контракты **не изменились**; оба решения (LRU
  кеш, авторитетный манифест) — целиком внутренние детали реализации.
- Формат `.manifest.json` и формат `ChildWindowsState` в `user.config` — не изменились, полная обратная
  совместимость.
- **Известный открытый риск (см. Решение 4):** нет single-instance guard между процессами — write-through
  кеш манифеста делает «один экземпляр приложения на storage root» несущим инвариантом сильнее, чем
  раньше, но технической защиты от двойного запуска по-прежнему нет.
- **Известный побочный эффект (не регрессия, см. Решение 5):** `Reset`-уведомление сбрасывает
  выделение/позицию скролла списка при перестройке `FileItems` — это поведение существовало и до
  фазы (`Clear()` давал тот же эффект), но стало заметнее теперь, когда перестройки происходят чаще
  без видимого фриза UI. Рекомендован отдельный тикет на точечный diff (Add/Remove вместо Reset), если
  ревью на реальном Windows покажет, что это ощутимая UX-проблема.
- **Найденный, но не относящийся к этой фазе дефект (зафиксировать отдельно):** `linters/linter.ruleset`
  не резолвится ни в одном `.csproj` (относительный путь ломается в зависимости от того, откуда идёт
  сборка — `MSB3884`), т.е. StyleCop фактически не применяется repo-wide. Обнаружено ревью в процессе
  Блока F, не является следствием изменений этой фазы — задокументировано как pre-existing техдолг,
  требует отдельного фикса.

**Manual verify** — блоки A–F выполнены пользователем на Windows 11 24H2 2026-09-27, признаны достаточными;
Windows 10 не проверяется — см. [docs/ROADMAP.md](../docs/ROADMAP.md) (строки 6–8, 1328–1331).
Исторический чек-лист — `docs/PLANS/phase-7-performance-hardening.md`, «Сводный список manual verify»
(особое внимание блоку B — глобальный хук, единственный блок с риском подтормаживания ввода системы при
регрессии).
