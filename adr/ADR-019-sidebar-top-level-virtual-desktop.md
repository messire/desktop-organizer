# ADR-019: Боковая панель как top-level окно вместо WorkerW-child

**Статус:** Accepted — Amended 2026-09-02 (ADR-020: раздел «Trade-off Topmost» ниже **пересмотрен**, см.
[ADR-020](ADR-020-sidebar-zorder-back-without-topmost.md); top-level-окно и вся virtual-desktop-логика
этого документа остаются в силе); Amended 2026-09-27 (ADR-034: `ReassertAfterShellRestart` переиспользует
anchor-логику после рестарта Explorer); Amended 2026-10-09 (ADR-audit WP-E: действующий контракт COM `IVirtualDesktopManager` продублирован из ADR-016)
**Дата:** 2026-09-02
**Пересматривает:** [ADR-016](ADR-016-virtual-desktop-visibility.md) (механизм — **Superseded by ADR-019**)
**Уточняет:** [ADR-007](ADR-007-system-icons-panel-window-type.md) (пункт «Z-order» — для `SystemIconsPanel`
это решение больше не действует, для fence-панелей действует без изменений)
**Пересмотрено (частично):** [ADR-020](ADR-020-sidebar-zorder-back-without-topmost.md) — `Topmost="True"`
убран по итогам пользовательской проверки, панель вернулась «на задний план» через периодический якорь
на `Progman`. Раздел ниже сохранён как исторический контекст: он объясняет, почему `Topmost` вообще
появился, и какую проблему reachability решал.

## Контекст

### Баг

Чекбокс «Show on all virtual desktops» на боковой панели (`SystemIconsPanel`) не давал эффекта в обе
стороны: панель была видна на **всех** виртуальных столах Windows независимо от положения чекбокса.

Причина оказалась не в логике опроса (реализованной в ADR-016), а в подложке окна:

- `SystemIconsPanelWindow.OnSourceInitialized` вызывал `IDesktopIntegrationService.EmbedInDesktop`,
  который делает `SetParent(hwnd, workerW)` — тот же механизм встраивания в слой рабочего стола,
  что используют fence-панели (`ChildWindow`, ADR-001/ADR-007).
- `WorkerW` — **один общий слой рабочего стола на все виртуальные столы**, а не по слою на стол. Любой
  его child виден на каждом столе безусловно, вне зависимости от того, что делает менеджер виртуальных
  столов.
- Менеджер виртуальных столов такое окно вообще не отслеживает: после `SetParent` `GetWindowDesktopId`
  возвращает `S_OK` + `GUID_NULL`, а `MoveWindowToDesktop` на таком окне — `S_OK`-тихий no-op (измерено
  ещё в ADR-016 §E0.2).

Следствие: механизм «follow-me» из ADR-016 (`DispatcherTimer` + `IVirtualDesktopManager`) не мог
работать по построению — он опрашивал и двигал окно, которое API виртуальных столов физически не
видит. Ошибка была не в коде тика, а в неверном допущении о том, к какому окну этот код применяется.

### Уточняющие вопросы постановщику и принятые решения

Три развилки были явно поставлены постановщику задачи и решены до начала реализации (см.
`docs/PLANS/sidebar-virtual-desktop-redesign.md` §2, §4.3, §12 «Решения, требующие подтверждения»):

1. **Трогать ли fence-панели (`ChildWindow`)?** — **Нет.** Fence-панели остаются встроенными в
   `WorkerW` без изменений; их видимость на всех столах — не баг, а следствие архитектуры ADR-001/007,
   и она вне области действия чекбокса боковой панели. Инвариант проверен: diff этой работы не
   затрагивает `ChildWindow*`/`WindowManager*`/`ChildWindowModel*`.
2. **Как боковая панель должна вести себя относительно Z-order других окон, если она перестаёт быть
   `WorkerW`-child?** — Принят trade-off «панель поверх обычных окон» (`Topmost="True"`) вместо
   прежнего «панель позади окон, поверх обоев». Обоснование и последствия — см. раздел «Trade-off
   Topmost» ниже.
3. **Что означают ВКЛ/ВЫКЛ для чекбокса «Show on all virtual desktops» на top-level окне?**
   — **ВКЛ** = панель следует за активным виртуальным столом с задержкой до ~1 с через переиспользованный
     poll-механизм ADR-016 (тот же код тика, но теперь применяемый к окну, которое API реально
     отслеживает).
   — **ВЫКЛ** = панель закрепляется на «Desktop 1» через новый anchor-механизм, а не через настоящие
     дубли окна на каждый стол. Причина: документированный `IVirtualDesktopManager` не умеет
     перечислять столы или получать «первый/дефолтный» стол — только принимает уже известный HWND;
     единственный способ перечисления — недокументированный `IVirtualDesktopPinnedApps`/
     `IServiceProvider` на `CLSID_ImmersiveShell`, который уже был отклонён в ADR-016 (вариант E-B) как
     нестабильный между сборками Windows (плавающий IID). Постановка задачи прямо запрещает
     возвращаться к E-B.

## Spike R0 — ключевая находка: порядок применения оконных стилей решает всё

По аналогии со spike E0 (ADR-016) перед кодом был выполнен диагностический spike (throwaway, вне
`src/`), протокол — `docs/PLANS/sidebar-virtual-desktop-redesign.md` §3.2.1. Ограничения соблюдены:
активный стол пользователя не переключался, фокус не отнимался, `0x052C` в `Progman` не отправлялось,
столы не создавались/не удалялись.

**Исходная гипотеза плана** (сформулированная по аналогии с измерением ADR-016 §E0.2 «top-level окно
со стилями `TOOLWINDOW|NOACTIVATE`, показанное на экране → отслеживается менеджером столов») **не
воспроизвелась при перепроверке**. Матрица фактических измерений (Windows 11 Home SL, build
10.0.26200, x64, 2 виртуальных стола):

| Конфигурация окна | `GetWindowDesktopId` |
|---|---|
| raw `CreateWindowEx`, `TOOLWINDOW\|NOACTIVATE\|TOPMOST` | не отслеживается (`TYPE_E_ELEMENTNOTFOUND`) |
| WPF-окно панели, стили `TOOLWINDOW\|NOACTIVATE` выставлены в `SourceInitialized` (**прежнее продакшн-размещение**) | `S_OK` + `GUID_NULL` — **не отслеживается** |
| то же окно, стили выставлены **сразу после `Show()`**, тот же виток UI-потока | `S_OK` + реальный GUID — **отслеживается** |
| то же окно, стили выставлены в `Loaded` или `Dispatcher.BeginInvoke(Loaded)` после `Show()` | отслеживается |

**Вывод:** любой из битов `WS_EX_TOOLWINDOW` / `WS_EX_NOACTIVATE`, присутствующий в момент **первого
показа** окна, навсегда исключает его из учёта менеджера виртуальных столов — независимо от того, что
происходит с окном дальше. Применение точно тех же стилей **после** первого `Show()` работает
корректно и стабильно (проверено дважды). Это означало, что предписанная изначально реализация —
поставить `ApplyDesktopWindowStyles` в `OnSourceInitialized` вместо `EmbedInDesktop` — воспроизвела бы
исходный баг в новой форме: панель снова была бы невидима для API виртуальных столов.

**Полная проверка переезда** (на окне, стилизованном сразу после `Show()`) дополнительно подтвердила
не только трекинг, но и фактический межстольный переезд:

```
after Show(), before styles       S_OK {b6b25d05-…}  tracked=True
after TOOLWINDOW|NOACTIVATE       S_OK {b6b25d05-…}  tracked=True
MoveWindowToDesktop({dad5fc31-…}) hr=S_OK -> GetWindowDesktopId={dad5fc31-…}, IsOnCurrent=0
                                  => РЕАЛЬНЫЙ МЕЖСТОЛЬНЫЙ ПЕРЕЕЗД ПОДТВЕРЖДЁН
focus preserved throughout: True
```

Переключение стола вживую (визуальное наблюдение) в этой сессии **не проверялось** — это остаётся
manual-verify пунктом; сделанные измерения — COM/API-уровня, не визуальные.

**Следствие для реализации (зафиксировано в XML-doc `IDesktopIntegrationService.
ApplyDesktopWindowStyles`, не осталось устным допущением):**

```csharp
_window.Show();
_desktopIntegration.ApplyDesktopWindowStyles(new WindowInteropHelper(_window).Handle);
// только теперь окно и стилизовано, и отслеживается менеджером столов
```

Окну также нужен `ShowActivated="False"` — иначе между `Show()` и установкой `NOACTIVATE` окно на миг
отняло бы фокус (в spike с `ShowActivated=false` фокус не терялся ни разу). Прокачка очереди сообщений
между `Show()` и установкой стилей не требуется.

## Решение

`SystemIconsPanelWindow` перестаёт вызывать `IDesktopIntegrationService.EmbedInDesktop`
(`SetParent`-встраивание в `WorkerW`) и становится обычным top-level окном:

- **XAML:** `Topmost="True"`, `ShowActivated="False"` — добавлено. `WindowStyle=None`,
  `ShowInTaskbar=False`, `AllowsTransparency=True` и остальное — без изменений.
- **Стили окна:** `IDesktopIntegrationService` получил новый публичный член
  `void ApplyDesktopWindowStyles(IntPtr hwnd)` — бывший приватный метод, поднятый в публичный API;
  `EmbedInDesktop` вызывает его первой строкой, так что поведение `EmbedInDesktop` (используемого
  fence-панелями) не изменилось ни на байт. Вызывается **строго после `_window.Show()`**, из
  `SystemIconsPanelManager.OpenPanel` (не из `OnSourceInitialized` окна) — см. находку R0 выше.
- **Re-embed-логика убрана.** Блок в `PollVirtualDesktopOnce`, который на каждом тике проверял
  `IsEmbedded(hwnd)` и при необходимости заново звал `EmbedInDesktop`, удалён вместе с `EmbedInDesktop`
  из `OnMonitorsChanged`. Эта логика была специфична для сценария «панель — child `WorkerW`, parenting
  может слететь при переезде между столами»; на top-level окне её сохранение вызывало бы `EmbedInDesktop`
  (синхронный `SendMessage 0x052C` + `EnumWindows`) **на каждом тике** (`IsEmbedded` у top-level окна
  всегда `false`), что мгновенно вернуло бы панель в `WorkerW` и воспроизвело бы исходный баг заново
  (находка V-R11 плана). Регресс закрыт тест-гардом (`Times.Never` на `EmbedInDesktop` из любого пути
  менеджера).
- **`IsEmbedded(IntPtr)`** удалён из `IDesktopIntegrationService`/`DesktopIntegrationService` вместе с
  тестами: единственный продакшн-потребитель — снятый блок re-embed.

### Инвариант P/Invoke и COM виртуальных столов (действующий контракт, перенесён из ADR-016)

Эта работа продолжает опираться на `IVirtualDesktopManager`, введённый в [ADR-016](ADR-016-virtual-desktop-visibility.md)
(тот помечен `Superseded by ADR-019` по подложке, но механизм и контракты остаются действующими). Инвариант
проекта «P/Invoke только за `INativeApi`» формально **не нарушается** активацией COM-объекта: `IVirtualDesktopManager`
активируется в `VirtualDesktopService` через `Type.GetTypeFromCLSID` + `Activator.CreateInstance` с приватным
`[ComImport]`-интерфейсом, объявленным внутри самого класса, — это не `[DllImport]`/`[LibraryImport]`. Решение —
**не выносить это объявление за `INativeApi`**: граница абстракции здесь `IVirtualDesktopService`, он играет для
COM ту же роль изоляции, что `INativeApi` для P/Invoke, и COM-интерфейс не «протекает» наружу. Настоящие P/Invoke,
нужные этому механизму (`GetForegroundWindow`, `GetParent`/`GetClassName`), живут в `INativeApi`/`NativeApi`. Контракт
`IVirtualDesktopService`: все члены вызываются **только со STA-потока** (UI-поток); `IsWindowOnCurrentDesktop`
возвращает `true` при неопределимом состоянии (не трогать окно при неизвестности);
`TryMoveWindowToCurrentDesktop() == true` означает «вызов принят», а не «окно переехало» (`MoveWindowToDesktop`
отвечает `S_OK` как no-op на нетрекаемых окнах); RCW не освобождается принудительно (`Dispose` обнуляет поле).
Любой новый COM-интерфейс за пределами `INativeApi` обязан иметь такую же единственную обёртку-реализацию.

### Поведенческая матрица (ON/OFF)

| Состояние | Что делает менеджер |
|---|---|
| Панель выключена | Окна нет; таймер остановлен; якорь не трогается |
| **ON** (`ShowOnAllVirtualDesktops=true`) | `DispatcherTimer` 1 с (переиспользован из ADR-016, теперь работает по назначению): `IsWindowOnCurrentDesktop` → при `false` `TryMoveWindowToDesktop` на GUID текущего стола → проверка эффекта → circuit breaker `MaxIneffectiveMoves=3` как safety net |
| **OFF** (`ShowOnAllVirtualDesktops=false`) | Таймера нет. Однократный `EnforceAnchorDesktopOnce` при: (1) `Show()` в `OpenPanel`; (2) переключении чекбокса в OFF; (3) `OnMonitorsChanged` |
| ON → OFF | Таймер останавливается, `EnforceAnchorDesktopOnce` возвращает панель на якорный стол |
| OFF → ON | Circuit breaker сбрасывается, таймер запускается, немедленный первый тик (без ожидания 1 с) |
| `IsSupported == false` | Обе ветки — no-op; панель работает штатно; настройка сохраняется, но эффекта не даёт |

## Trade-off: `Topmost="True"` (пересмотрено — см. ADR-020)

> **Статус раздела: пересмотрено 2026-09-02, см. [ADR-020](ADR-020-sidebar-zorder-back-without-topmost.md).**
> По итогам визуальной проверки пользователем `Topmost="True"` признан неприемлемым для боковой панели
> (панель перекрывала обычные окна) и убран. Reachability-проблема, ради которой `Topmost` был принят
> (см. ниже), решена не подъёмом панели наверх, а обратным путём — периодическим якорем панели сразу
> над `Progman`, так что она больше не нуждается в подъёме над окнами, которые её перекрыли. Раздел
> сохранён целиком как исторический контекст.

Со снятым `SetParent` окно остаётся `WS_EX_NOACTIVATE`: клик по нему **никогда** не активирует его и
не поднимает в Z-order. Без `Topmost` панель, однажды перекрытая любым приложением, становится
недостижимой навсегда — нет пользовательского жеста, который бы её поднял. Это функциональный дефект,
не вопрос вкуса, поэтому принят `Topmost="True"`.

**Принятая цена:** панель теперь **поверх** других приложений, включая полноэкранные не-DirectX окна
(презентации, видеозвонки, полноэкранные документы) — раньше она была позади них, поверх обоев. Это
осознанный trade-off постановщика; авто-скрытие при полноэкранном режиме — вне области этой работы,
кандидат в ROADMAP отдельным пунктом.

**Находка `fences-ux-parity-reviewer`, зафиксированная как известное ограничение (не устранена
кодом):** `WS_EX_NOACTIVATE` означает, что клик по панели никогда не поднимает её в Z-order. Если
поверх панели встанет **другое** topmost-окно (плавающее окно видеозвонка, Task Manager с «Always on
Top», любой другой always-on-top оверлей), панель окажется погребена под ним **без какого-либо
способа вернуть её на передний план**, кроме закрытия или снятия topmost-режима у того окна. Обычные
top-level окна с `Topmost` в Windows не имеют встроенного механизма «побеждать» другие topmost-окна —
порядок среди нескольких topmost-окон определяется порядком активации/создания, а `NOACTIVATE`
исключает панель из этой борьбы навсегда. Авто-переподъём Z-order (например, периодическая
`SetWindowPos(HWND_TOPMOST, …)`) был рассмотрен и отклонён как хрупкий и потенциально вызывающий
мерцание/state thrashing с другими always-on-top окнами — вместо кода это задокументировано здесь и в
Manual verify (п. 7) как известное ограничение.

## Трёхуровневая anchor-логика и реестровый зонд R2

Публичный `IVirtualDesktopManager` не даёт способа перечислить столы или узнать GUID «первого»/
«дефолтного» стола — только методы, оперирующие уже известным HWND. Поэтому «Desktop 1» разрешается
чистой (unit-тестируемой) функцией-политикой:

```
ResolveAnchorDesktopId(persisted: Guid?, systemDefault: Guid?, panelCurrent: Guid?) -> Guid?
  1. systemDefault ≠ null      -> systemDefault   (авторитетный источник; перезаписывает persisted)
  2. persisted     ≠ null      -> persisted       (последнее известное значение)
  3. panelCurrent  ≠ null      -> panelCurrent    (эвристика первого захвата)
  4. иначе                     -> null            (ничего не двигаем — никогда не гадаем)
```

- **R1 (базовый, всегда доступный)** — `panelCurrent = GetWindowDesktopId(panelHwnd)`, снятый после
  `Show()`. Персистится и переживает перезапуск. Слабое место: если панель впервые запускается, когда
  пользователь уже не на Desktop 1, эвристика зафиксирует текущий стол как «Desktop 1».
- **R2 (уточняющий, гейт — зелёный по итогам spike)** — read-only чтение
  `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\VirtualDesktops\VirtualDesktopIDs`
  (порядок столов оболочки) и текущего стола (сначала `SessionInfo\<SessionId>\…`, затем legacy-путь).

**Почему это принципиально другой профиль риска, чем отклонённый в ADR-016 вариант E-B**
(недокументированное COM-перечисление столов через `IServiceProvider`/`CLSID_ImmersiveShell`):

| | E-B (отклонён в ADR-016) | R2 (принят здесь) |
|---|---|---|
| Тип доступа | Активация недокументированного COM-интерфейса | Read-only чтение реестра |
| Стабильность между сборками | IID меняется между сборками Windows, требует таблицы build→IID | Формат ключа реестра стабилен эмпирически на проверенных сборках |
| Поведение при ошибке/дрейфе | Непредсказуемый сбой активации/каста | **Обнаруживается кросс-валидацией** (см. ниже) и тихо деградирует до R1 |
| Побочные эффекты | COM-активация, потенциальные исключения | Нет — чистое чтение байт |

Кросс-валидация: значение «текущий стол» из реестра сверяется с документированным
`GetWindowDesktopId(GetForegroundWindow())`, и «первый» GUID должен присутствовать в списке
`VirtualDesktopIDs`. Если что-либо не совпадает — раскладка/семантика реестра на этой сборке не та,
что ожидалась, и метод возвращает `null` (тихий откат на R1), а не бросает исключение или отдаёт
неверный GUID. Результат не кешируется на время жизни процесса и не вызывается из таймера (только при
открытии панели/переключении чекбокса) — пользователь может переупорядочить столы в рантайме.

**Самоизлечение якоря.** Если якорный стол удалён пользователем, попытка `TryMoveWindowToDesktop` не
даст эффекта; политика — однократный (не циклический) перезахват якоря от текущего стола панели, если
якорь пришёл не из R2, с записью нового значения в persistence. Порог введён по итогам ревью (M3, ниже)
— перезахват срабатывает только после `SelfHealMinConsecutiveFailures` подряд явных отказов, не с
первой попытки.

## Закрытые находки ревью (M1–M5)

Реализация прошла несколько раундов ревью (`code-quality-reviewer` ∥ `fences-ux-parity-reviewer`),
которые нашли и закрыли 5 MAJOR-проблем:

- **M1** — OFF-путь (`EnforceAnchorDesktopOnce`) ошибочно мог взвести
  `VirtualDesktopFeatureIneffective` — предупреждение, спроектированное для ON-режимного circuit
  breaker'а (ADR-016). Исправлено: OFF-путь никогда не поднимает этот флаг; регресс закрыт тестом на
  10 подряд неудач без взведения флага.
- **M2** — OFF-путь не сбрасывал счётчик неудачных попыток при успехе, ломая инвариант «N **подряд
  идущих** неудач» (счётчик мог накапливаться через разделённые успехами неудачи и ложно сработать).
  Исправлено: успешная проверка «панель уже на якоре» или успешный переезд сбрасывают счётчик.
- **M3** — self-heal якоря был недостижим в сценарии, для которого писался (одна неудача не давала
  достаточно сигнала для перезахвата), и одновременно опасен там, где всё же срабатывал (перезахват от
  одного случайного сбоя API). Исправлено: self-heal требует `SelfHealMinConsecutiveFailures` подряд
  явных отказов переезда, прежде чем перезахватывать якорь.
- **M5** — OFF-путь игнорировал `IsSupported`, то есть мог обращаться к реестру/COM даже когда сервис
  виртуальных столов недоступен. Исправлено: `EnforceAnchorDesktopOnce` немедленно выходит при
  `IsSupported == false`, симметрично ON-пути.

(M4 в нумерации ревью не привёл к отдельному коммиту в проде — вопрос был снят на этапе обсуждения;
здесь не описывается отдельно, чтобы не документировать не-изменение).

Добавлено 24 unit-теста (780 → 804, все зелёные), покрывающих `ResolveAnchorDesktopId` (таблица
истинности, 8 комбинаций), `EnforceAnchorDesktopOnce` (zero-handle, `IsSupported=false`, уже-на-якоре,
успешный переезд, все источники `null`, self-heal, `Save()` вызывается только при реальном изменении
якоря, отсутствие вызовов `EmbedInDesktop` как regression-guard на V-R11, тихая деградация при
исключении из сервиса) и persistence якоря (round-trip, отсутствующий ключ, мусорное значение не
ломает остальные настройки панели).

## Non-goals

- **Fence-панели (`ChildWindow`) не затронуты.** Остаются встроенными в `WorkerW`, видны на всех
  виртуальных столах безусловно — как и раньше, это не входит в область действия чекбокса боковой
  панели.
- **«Настоящие» дубли окна панели на каждый виртуальный стол** — не реализованы и не рассматривались:
  документированный `IVirtualDesktopManager` не умеет перечислять столы, а единственный способ
  получить такой список — недокументированный COM с плавающим между сборками Windows IID, уже
  отклонённый в ADR-016 (вариант E-B). Вместо этого OFF-режим закрепляет **одно** окно на «Desktop 1»
  через anchor-механизм.
- **Авто-скрытие при полноэкранном режиме** (митигация trade-off `Topmost`) — вне области, кандидат в
  ROADMAP отдельным пунктом. *(Частично снято ADR-020: без `Topmost` панель больше не перекрывает
  полноэкранные приложения — см. ADR-020.)*
- **Авто-переподъём Z-order против других topmost-окон** — рассмотрен и отклонён как хрупкий; см.
  раздел «Trade-off Topmost». *(Устарело вместе с самим `Topmost` — ADR-020 решает reachability не
  подъёмом, а тем, что панели больше некуда подниматься: она снова осела на задний план.)*

## Manual verify (Win10 / Win11)

> **Статус:** выполнена на Windows 11 24H2 2026-09-27, признана достаточной; Windows 10 не проверяется — см.
> [docs/ROADMAP.md](../docs/ROADMAP.md) (строки 6–8, раздел «Полировочный батч polishing/ui-1»). Список
> ниже оставлен как исторический чек-лист (пп. 7–8 неактуальны после ADR-020, см. пометки).

Перенесено из `docs/PLANS/sidebar-virtual-desktop-redesign.md` §11/§14 (дополнено находками ревью).
Интерактивная сессия с ≥3 виртуальными столами.

1. **ON, переключение стола.** Панель появляется на новом столе в течение ~1 с (задержка ожидаема —
   poll-интервал, не дефект).
2. **ON, несколько переключений подряд.** Панель не дублируется, не мерцает, не «застревает»;
   `VirtualDesktopFeatureIneffective` не взводится.
3. **OFF, панель остаётся на Desktop 1.** Уйти на Desktop 3, вернуться — панель на Desktop 1,
   отсутствует на Desktop 2/3.
4. **OFF, включение панели с Desktop 3.** Панель немедленно уезжает на Desktop 1 и пропадает из поля
   зрения — ожидаемое поведение по требованию, не баг.
5. **Точность «Desktop 1».** Первый запуск с Desktop 1; и отдельно — удалить
   `AnchorVirtualDesktopId` из файла настроек, запустить на Desktop 3: при рабочем R2 панель всё равно
   уедет на Desktop 1, при откате на R1 — останется на Desktop 3 (задокументированная слабость
   эвристики).
6. **Удаление якорного стола.** Удалить Desktop 1 в Task View → якорь перезахватывается после
   `SelfHealMinConsecutiveFailures` подряд неудач, приложение не зависает, Explorer не долбится.
7. **Topmost-конкуренция.** Открыть окно видеозвонка/Task Manager с «Always on Top» поверх панели →
   зафиксировать фактическое поведение (ожидаемо: панель остаётся погребена — известное ограничение,
   не дефект этой реализации). *(Неактуально после ADR-020 — панель больше не `Topmost`, этого сценария
   больше нет; см. вместо него manual-verify список ADR-020.)*
8. **Z-order / фокус.** Панель поверх обычных окон (`Topmost`); клик по панели не отнимает фокус у
   активного приложения (`WS_EX_NOACTIVATE`). *(Неактуально/пересмотрено после ADR-020 — `Topmost`
   убран, панель больше не описывается как «поверх обычных окон»; часть про `WS_EX_NOACTIVATE`
   (клик не отнимает фокус) остаётся в силе без изменений — см. вместо первой половины пункта
   manual-verify список ADR-020.)*
9. **Win+D / Show Desktop / Aero Peek / Aero Shake** — зафиксировать фактическое поведение панели
   (как top-level окно она больше не иммунна к ним, в отличие от `WorkerW`-child).
10. **Alt+Tab и Task View.** Панели нет ни в Alt+Tab, ни в панели задач, ни в превью столов Task View —
    проверить отдельно ввиду нового порядка применения стилей (стили ставятся **после** `Show()`, то
    есть окно на один виток UI-потока показано без `TOOLWINDOW`; `ShowInTaskbar="False"` реализуется
    WPF через скрытое owner-окно, а не через `TOOLWINDOW`, поэтому в панели задач окно исключено с
    самого начала, но Alt+Tab стоит перепроверить явно).
11. **Multi-monitor.** Конфигурация, где основной монитор правее вторичного (отрицательный X):
    панель у левого края основного монитора; смена конфигурации мониторов не возвращает панель в
    `WorkerW`.
12. **Fence-панели не изменились.** Перетащить fence под боковую панель: fence остаётся в слое
    рабочего стола, боковая панель — поверх; поведение fence-панелей на виртуальных столах не
    изменилось.
13. **Клик по пустому фону панели** не проваливается к иконкам рабочего стола (окно больше не child
    `WorkerW`).
14. **Drag-and-drop файла в Корзину на панели** работает не хуже прежнего (OLE drop у top-level окна
    ожидается надёжнее, чем у `WorkerW`-child).
15. **ПКМ по иконке** → нативное shell-меню открывается в правильной позиции (координаты `Left/Top`
    теперь экранные — проверить на DPI ≠ 100%).
16. **`IsSupported == false`** (сборка без менеджера столов): панель работает, обе ветки (ON/OFF) —
    no-op, приложение не падает.

## Последствия и риски на будущее

### Положительные

- Чекбокс «Show on all virtual desktops» впервые реально работает — механизм ADR-016 (poll +
  `MoveWindowToDesktop`) применяется к окну, которое API действительно отслеживает.
- OFF-режим впервые даёт наблюдаемый эффект («закрепить на первом столе»), а не унаследованное от
  `WorkerW` «видна везде всегда».
- Fence-панели не тронуты вообще — риск регрессии в самой большой части кодовой базы приложения
  отсутствует by construction (проверено `git diff --name-only`).
- Позиционирование панели (`PositionWindow`) стало корректнее побочно: `Left`/`Top` top-level окна —
  симметричные экранные координаты DIP, тогда как у `WorkerW`-child сеттер и геттер работали в разных
  системах координат. На конфигурации, где основной монитор правее вторичного (отрицательный X),
  старое поведение клало панель на чужой монитор — это исправлено.

### Риски

- **Topmost-конкуренция (см. Trade-off).** Панель может оказаться навсегда погребена под другим
  always-on-top окном без пользовательского способа её вернуть, кроме закрытия того окна. Осознанно не
  устранено кодом.
- **Полноэкранные приложения.** Панель теперь перекрывает полноэкранные не-DirectX приложения/
  презентации/видеозвонки — раньше был позади них. Авто-скрытие — будущий тикет.
- **Реестровый формат R2.** Зонд опирается на эмпирически подтверждённый, но не гарантированный
  контрактом Microsoft формат `VirtualDesktopIDs`/`CurrentVirtualDesktop`. Кросс-валидация детектирует
  расхождение и откатывает на R1, но если будущая сборка Windows изменит семантику одновременно во
  всех проверяемых полях, кросс-валидация может ложно пройти. Митигация — как и раньше, полностью
  тихая деградация, ничего не падает.
- **Экран без виртуальных столов вовсе или `IsSupported == false`.** Обе ветки — no-op, поведение
  идентично «функция выключена»; проверено тестами, не проверено вручную на такой конфигурации.
- **Наследованный риск ADR-016 остаётся в силе:** `TryMoveWindowToDesktop() == true` — это «вызов
  принят», не «окно реально переехало»; вызывающий код обязан относиться к этому именно так (уже
  соблюдается через проверку эффекта + circuit breaker).
