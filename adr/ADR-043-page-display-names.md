# ADR-043: Отображаемые имена страниц (schema v6)

**Статус:** Accepted (2026-09-29)

---

Источник — бэклог 1.x (`docs/ROADMAP.md` → «Бэклог 1.x: UX-полировка»), пункт «Переименование страниц»,
и мастер-план [docs/PLANS/page-display-names.md](../docs/PLANS/page-display-names.md) (WP-1 persistence,
WP-2 `PageManager`, WP-3 UI). Ветка `rc/0.8.0` (от `v0.7.0`). Реализация: `dotnet-services-engineer`
(WP-1+WP-2) → `wpf-ui-builder` (WP-3) ∥ `tdd-test-engineer` → `code-quality-reviewer` ∥
`fences-ux-parity-reviewer` → этот документ. Коммиты `037a325` (WP-1/WP-2, schema v6 + `IPageManager`
rename-контракт), `f039db9` (page rename UI, wave 1), `4e7268b`/`904ef4d` (review-фиксы wave 2/3).

## Контекст

До этой задачи страница была только строковым `pageId` (`PagesStateDto.Ids`, `PanelStateDto.PageId`) —
никакого отдельного отображаемого имени не было, пользователь видел в UI сырой идентификатор (для
пользовательских страниц — обычно `"Page 2"`-подобный литерал, для GUID-страниц — сам GUID).

**Решение пользователя (2026-09-29, окончательное, не переспрашивалось):** у страницы должен быть
стабильный `id` и отдельное отображаемое `name` — так же, как у панели (`PanelStateDto.Id` + `Title`).
Это явное разрешение расширить замороженный контур persistence (CLAUDE.md, раздел «Настройки и
persistence — ЗАМОРОЖЕНЫ»), выданное в объёме, ограниченном ниже.

## Решение

### 1. `StateEnvelope.CurrentSchemaVersion`: 5 → 6

Единственное разрешённое расширение контура. Всё остальное (`IAppSettings`/`AppSettings`/
`Settings.settings`/`user.config`, `UserConfigFolderMigration`, `JsonApplicationStateStore` (лестница
восстановления, атомарная запись, `.bak`, карантин, advisory lock), `StateMigrationRunner`,
`StateRestoreCommand`, `LegacySettingsImporter`, `LayoutSnapshotService`, формат `panels`/
`layoutSnapshots`/`systemIconsPanel`, семантика `RequestSave`/`SaveNow`) — без диффа.

### 2. Формат `pages` в v6 — массив объектов «как панели», не параллельная карта имён

```json
"pages": {
  "items": [
    { "id": "default" },
    { "id": "work", "name": "work" },
    { "id": "3f2a9c0e5b7d4e1a9c3b2d1e0f4a5b6c", "name": "Проекты" }
  ],
  "currentPageId": "default"
}
```

- `items[].id` — стабильный идентификатор, обязателен, никогда не меняется.
- `items[].name` — опционален: **ключ отсутствует** (не `null`) у unnamed `"default"`; для любой другой
  страницы отсутствие ключа — признак повреждения, на загрузке лечится `name = id`.
- `ids` в v6 не пишется — единственный источник правды `items`.

**Alternatives considered:**
- **B. Параллельная карта `names: {id: name}`.** Отклонено: два источника правды (осиротевшие ключи при
  удалении страницы), и, что решающее, ключи словаря — данные пользователя, а не схема:
  `SchemaContractTests.CollectKeyPaths` собрал бы `pages.names.work` как «путь схемы» и сломал
  контрактный тест.
- **B'. Параллельный массив `names` по индексу.** Отклонено: связь по индексу хрупка — рассинхрон одного
  массива без другого молча путает имена.
- **C. Переименовать сам `id`.** Отклонено пользователем явно. Потребовало бы перезаписи `pageId` во
  всех `panels[]` **и** во всех `layoutSnapshots[].panels[]` при каждом переименовании (снапшоты, снятые
  до rename, потеряли бы связь), и вернуло бы id в статус переводимой строки — конфликт с ADR-032 D-5
  («данные, не код»).
- **Формальная неаддитивность варианта A принята осознанно.** Аддитивность (сохранение старого ключа
  рядом с новым) бесполезна здесь в принципе: старая сборка (v0.7.0) видит `schemaVersion: 6 > 5` и
  уходит в rung 7 (`NewerSchema`, ADR-024 D-7) **до** чтения любого payload-ключа — независимо от того,
  остался ли `ids`. Критерий — «миграция без потерь и идемпотентна», а не «аддитивна на уровне ключа», и
  вариант A ему удовлетворяет.

### 3. `V5ToV6Migration` — `JsonObject`-only, копирует всё, кроме `pages`, целиком

В отличие от `V4ToV5Migration` (явный allow-list из четырёх ключей), `V5ToV6Migration` копирует **все**
top-level ключи payload, кроме `pages`, через `JsonNode.DeepClone()` — на этом шаге схемы менять больше
нечего, а allow-list рисковал бы молча выбросить незнакомый ключ. `panels[].pageId` и
`layoutSnapshots[].panels[].pageId` — побайтно без изменений (id стабильны, ни одна миграция их не
трогает).

Правило по элементу `pages.ids[]`: `"default"` (ordinal) → `{"id":"default"}` (без `name` вовсе — так
unnamed default продолжает локализоваться в точности как раньше); любой другой id `s` → `{"id":s,
"name":s}` — пользователь видит **буквально ту же строку**, что видел до апгрейда, теперь как данные
страницы, а не единственное, что её подписывает. Не-строка/`null` — пропускается. Идемпотентна:
если `pages` уже несёт `items` — объект копируется как есть, кроме совместно присутствующего legacy
`ids` (который в v6 никогда не должен сосуществовать с `items`). Дубликаты id миграция не санирует —
это задача маппера (`PagesStateMapper.FromDto`), а не второе место с шансом разойтись с первым.

### 4. Доменная модель и маппинг (`DesktopOrganizer.UI`)

- `PageDescriptor(string Id, string? Name)` — record, неизменяемый снимок.
- `PagesStateMapper.FromDto`/`ToDto` — санитизация на загрузке: `null`-элементы и пустой `Id` — пропуск;
  дубли id — первый выигрывает; `Name` для не-`default` страницы, пришедший `null`/whitespace, лечится в
  `Name = Id`; пустой список после фильтра → одинокая `default`; `currentPageId` blank → `default`.
  Длину/уникальность имён на загрузке **не** проверяет (это данные пользователя; валидация — только на
  rename).
- `IApplicationStateService.PageIds` заменён на `Pages : IReadOnlyList<PageDescriptor>` (один источник
  правды вместо строкового списка).

### 5. `IPageManager` — аддитивный контракт

```csharp
IReadOnlyList<string> Pages { get; }                       // без изменений: упорядоченные id
IReadOnlyList<PageDescriptor> PageDescriptors { get; }      // NEW: тот же порядок, с именами
event Action? PagesChanged;                                 // NEW: состав/порядок/имена (add/remove/rename)
string AddNewPage();                                        // NEW: GUID id + уникальное локализованное имя
string? GetPageName(string pageId);                         // NEW
PageRenameResult ValidatePageName(string pageId, string? newName);  // NEW: чистая проверка
PageRenameResult RenamePage(string pageId, string? newName);        // NEW
```

`PageChanged` (существующее событие) продолжает означать смену **текущей** страницы; `RenamePage` его не
поднимает. `PagesChanged` — новое, одно событие на любое изменение списка (добавление/удаление/
переименование), без аргументов — подписчик перечитывает `PageDescriptors`. Явный задел под трей
(ADR-044): подписчик там появился в этой же волне бэклога, но контракт был спроектирован здесь.

`AddNewPage()`: id — непрозрачный `Guid.NewGuid().ToString("N")` (не «Page N» — иначе снова сольются
переводимое имя и id); имя — локализованный `Page_NewName_Format`, уникализируемый инкрементом; имя
резолвится **в момент создания** и дальше живёт как данные (следствие ADR-032 D-5 — см. amendment ниже).

### 6. `PageNameRules` — единые правила переименования (`PageManagerService.RenamePage`)

Порядок проверок (первый провал — результат): `pageId` неизвестен → `NotFound`; `trim`; пустая строка —
для `"default"` сброс к `null` (`Renamed`/`Unchanged`), для остальных → `Empty`; управляющие символы →
`InvalidCharacters`; длина > **40** UTF-16 code units → `TooLong`; совпадение (OrdinalIgnoreCase) с
**эффективным** отображаемым именем любой *другой* страницы → `Duplicate` (эффективное имя unnamed
`default` — его текущая локализация, `ILocalizationService.GetString`); ordinal-равенство текущему имени
→ `Unchanged` без записи. Иначе — запись, `Save()` (→ синхронный `SaveNow`, структурное изменение, ADR-024
D-12), `PagesChanged`, `Renamed`.

**Известное ограничение (R-7, принято осознанно):** уникальность проверяется против *текущей* локализации
`default`. Переименовать страницу в «Main» в англоязычном UI, затем переключить язык на русский, где
`default` локализуется в «Основная», не создаёт коллизию задним числом — то же «данные на языке создания»,
что и ADR-032 D-5.

### 7. UI — единственная точка ввода: раздел «Страницы» окна настроек

`PagesSection.xaml`: строка страницы — `TextBlock` ↔ `TextBox`, вход — кнопка «Переименовать» / двойной
клик по имени / F2. Коммит-дисциплина воспроизводит уже принятый в проекте паттерн
(`RenameEditBehavior`/`PanelTitleRenameBehavior`, ADR-013 Решение 6), но с явно зафиксированной
асимметрией между Enter и потерей фокуса, найденной и закреплённой в ревью (wave 1):

- **Enter с ошибкой валидации** → `PageItemViewModel.RenameError` устанавливается, **редактор остаётся
  открытым** с введённым (невалидным) текстом — пользователь может исправить на месте.
- **Потеря фокуса / скрытие окна с ошибкой** → редактирование **закрывается** (сохранённый текст
  восстанавливается), но текст ошибки **сохраняется** видимым — пользователь не остаётся с открытым
  редактором, который блокирует переключение на другую строку, но и не теряет объяснение, почему правка
  не применилась.
- Начало редактирования другой строки коммитит предыдущую (через ту же lost-focus-дисциплину — не более
  одной строки в режиме правки одновременно).
- Никогда `MessageBox` — ошибка всегда inline-хинт (ADR-013 Решение 6, тот же принцип).

`PageDisplayNames.Resolve(id, name, culture)` (`UI/Localization`) — единственный способ получить текст
страницы: `!IsNullOrWhiteSpace(name) ? name : (id == "default" ? Page_Default_DisplayName(culture) : id)`.
Использован везде, где раньше показывался сырой id: раздел «Страницы», селектор страницы в «Панелях»,
меню «Переместить на страницу». `PageDisplayNameConverter` резолвит и `PageDescriptor`/`PageDisplayInfo`
(биндинг по `Display`, чтобы INPC-обновление сработало при rename), и по-прежнему `string` (обратная
совместимость мест, ещё не переведённых на новый тип).

### 8. Откат на сборку ≤0.7.0 — известный, документированный, не устранённый риск

- v0.7.0 открывает v6-файл → rung 7 `NewerSchema` (ADR-024 D-7): пустая read-only сессия, файл **не
  перезаписывается**. Для пользователя это выглядит как «все панели пропали» — ровно сценарий инцидента
  2026-09-24 (см. CLAUDE.md) — но данные физически целы, и возврат на 0.8.0+ немедленно всё возвращает.
- Восстановление данных *на* 0.7.0 — только вручную: скопировать `State\application-state.premigration-v5.json`
  поверх `State\application-state.json` при закрытом приложении. Это состояние на момент апгрейда;
  изменения 0.8.0 (включая переименованные страницы) при этом теряются. Автоматического понижающего
  конвертера нет и не планируется (ADR-024 D-7: вниз не мигрируем).
- **Расхождение с брифом, зафиксированное как факт, а не решение:** бриф ожидал файл
  `application-state.premigration-v6.json`; по факту существующего механизма
  (`StateStorePaths.PreMigrationBackupPath(fromSchemaVersion)`) бэкап миграции v5→v6 называется
  **`application-state.premigration-v5.json`** — по исходной версии. Механизм **не изменён** (запрет
  трогать что-либо в контуре store, кроме самой схемы `pages`) — задокументировано здесь как объяснение
  расхождения, не как новое решение.
- **Известный риск R-2:** если на машине пользователя остался `application-state.premigration-v5.json` от
  инцидента 2026-09-24, `WritePreMigrationBackupIfMissing` увидит `File.Exists` и **пропустит** запись —
  свежим premigration-снимком на момент апгрейда до 0.8.0 окажется устаревший файл пятидневной давности.
  Решено **вариантом A** (код store не меняется): manual-verify шаг перед первым запуском 0.8.0 —
  переименовать/удалить старый файл. Варианты B (именовать по целевой версии) и C (timestamp-суффикс при
  коллизии) отклонены — оба меняют семантику `WritePreMigrationBackupIfMissing`, что выходит за рамки
  выданного пользователем разрешения.

## Изменения существующих ADR

- **[ADR-024](ADR-024-versioned-json-persistence.md)** — добавляет пятую ступень лестницы миграций
  (v5→v6); rung 7 «`NewerSchema`» подтверждён без изменений; premigration-бэкап именуется по исходной
  версии (см. п.8 выше) — см. amendment 2026-09-29 в самом ADR-024.
- **[ADR-032](ADR-032-ui-localization.md)** — D-5/CN-2 расширяются: имя страницы теперь отдельное
  поле-данные (не сам id), и `Page_NewName_Format` для новой страницы локализуется **в момент создания**,
  а не показывается как сырой код повторно при каждой смене языка — см. amendment 2026-09-29 в ADR-032.

## Последствия

### Позитивные
- Страницы и панели теперь используют одну и ту же концептуальную форму (стабильный `id` + отдельное
  отображаемое имя) — меньше специальных случаев в остальном коде и в будущих фичах (трей, ADR-044).
- Существующее состояние v5 мигрирует без единой потери данных: то, что видел пользователь до апгрейда
  (голый id), видно и после — просто теперь как явно редактируемые данные.
- Задел под ADR-044 (`PageDescriptors`/`PagesChanged`) спроектирован здесь, а не задним числом.

### Известные ограничения
- Откат на сборку ≤0.7.0 показывает пустой рабочий стол на текущей сборке (п.8) — задокументировано в
  CHANGELOG/README, не устранено технически (по конструкции ADR-024 D-7, не по недосмотру).
- R-2 (устаревший `premigration-v5.json` от прошлого инцидента) закрывается ручным шагом manual verify,
  не кодом.
- R-7 (уникальность имени `default` зависит от текущего языка UI) — принято, как и в ADR-032 D-5.
- Трей-переименование страниц не реализовано (WinForms `ContextMenuStrip` не даёт inline-ввода) — при
  необходимости открывает раздел «Страницы» окна настроек, не отдельный ввод в трее.

## Manual verify (Win10/Win11) — не блокер

- Первый запуск 0.8.0 поверх существующего v5-состояния: все панели/страницы на месте;
  `application-state.json` → `schemaVersion: 6`, `pages.items`; создан свежий
  `application-state.premigration-v5.json` (если старый файл от инцидента 2026-09-24 не остался — см.
  R-2 выше, шаг M-0).
- «Страницы»: переименование кнопкой/двойным кликом/F2; Enter с ошибкой оставляет редактор открытым;
  потеря фокуса с ошибкой закрывает редактор, но текст ошибки виден; Esc отменяет.
- Unnamed `default` переключается с языком UI; после явного переименования — нет; пустой ввод возвращает
  к локализованному имени.
- «Панели»: селектор страницы и меню «Переместить на страницу» показывают имена, не id.
- Откат (на Dev-корне): запуск 0.7.0 → пустая read-only сессия, файл не тронут; снова 0.8.0 → всё на
  месте.
