# ADR-045: Копирование панели на другую страницу как независимый клон

**Статус:** Accepted (2026-09-29)

---

Источник — бэклог 1.x, пункт 8 «Скопировать панель на другую страницу (полный клон)» (`docs/ROADMAP.md`,
поставлено 2026-09-29), мастер-план [docs/PLANS/backlog-1x-master-plan.md](../docs/PLANS/backlog-1x-master-plan.md)
§8. Опирается на контракты ADR-043 (`PageDescriptors`, `PageDisplayNames`), не пересматривает их. Ветка
`rc/0.8.0`. Пакеты: 8a storage (`dotnet-services-engineer`), 8b клонирование в `WindowManager`
(`dotnet-services-engineer`), 8c команда/UI/RESX (`wpf-ui-builder`). Тесты — `tdd-test-engineer`. Прошло
три раунда `code-quality-reviewer`/`fences-ux-parity-reviewer` (находки H-1, M-A/M-B/M-C/M-E, L-3/L-4 —
зафиксированы ниже как часть итогового решения). Коммиты `e17be22` (базовая реализация, wave 1),
`4e7268b` (упрощённый вызов из трея-подменю страниц + review-фиксы wave 2), `904ef4d` (review-фикс
итерация 3: неблокирующий статус страницы, общий `SurfaceOptionsEditor`).

## Контекст

Требование пользователя: рядом с существующим «Переместить на страницу» (`MovePanelToPage` — та же
панель переезжает целиком) нужна независимая копия — «Скопировать на страницу»: **полная независимая
копия панели на момент копирования**. После копирования обе панели должны жить независимо: изменение или
удаление одной не должно задевать другую, включая файлы, физически перемещённые в управляемое хранилище
приложения (managed storage).

Управляемое хранилище устроено **поэлементно, не попанельно**: `PanelItems\{itemGuid}\{name}` плюс один
корневой манифест `PanelItems\.manifest.json` (managed path → original path) — каталога
`PanelItems\<panelGuid>\` не существует в принципе. Значит «дублировать в новый каталог панели» на
практике означает: **каждый** managed-элемент копируется в свой собственный новый
`PanelItems\{newItemGuid}\`, с новой записью манифеста.

## Решение

### 1. `IPanelItemStorageService.CopyManaged`/`DiscardCopies` — единственное новое прямое удаление в сервисе

```csharp
ManagedCopyResult CopyManaged(string storedPath);
// ManagedCopyResult(ManagedCopyOutcome Outcome, string? CopyPath)
// ManagedCopyOutcome { Copied, NotManaged, SourceMissing, TooLarge, InsufficientSpace, Failed }

void DiscardCopies(IReadOnlyList<string> copyPaths);
```

Файл → `File.Copy`; каталог → рекурсивное копирование (общий корень хранилища, тот же том — существующие
лимиты `MaxDirectoryImportBytes`/`MaxDirectoryImportFileCount` переиспользуются). Порядок: копия в новый
каталог → запись манифеста (write-through); если запись манифеста не удалась — копия удаляется (оригинал
цел), результат `Failed`. Предпроверка свободного места на томе (`DriveInfo.AvailableFreeSpace`, запас
5%) перед копированием — `InsufficientSpace`, если недостаточно.

**Исходный путь копии = исходный путь источника (то же `original path`).** Следствия, зафиксированные
здесь осознанно, а не как побочный дефект:
- `Restore`/`--restore-panel-items` вернут **обе** копии на одно и то же исходное место — вторая получит
  суффикс `(2)` (существующая Explorer-логика присвоения имени при коллизии).
- `TryFindManagedPath` для такого original становится неоднозначным и возвращает явный отказ
  (`false`) — тот же принцип «явный отказ вместо угадывания», уже применяемый кросс-панельной логикой
  `WindowManager.ResolveStalePanelPaths`/`GetManagedPathsClaimedByOtherPanels`, которая эту неоднозначность
  уже умеет обрабатывать без изменений.

`DiscardCopies` — намеренно узкий: удаляет **только** каталоги, созданные текущей операцией клонирования
(верифицируется по форме пути и тому, что запись манифеста была сделана этим же вызовом `CopyManaged`), и
только их записи манифеста. Это не общий механизм удаления пользовательского контента.

**Amendment [ADR-035](ADR-035-panel-deletion-recycle-bin.md):** откат незавершённого клонирования удаляет
только собственные, только что созданные копии клона — напрямую, минуя Корзину. Это не пересматривает
основное правило ADR-035 («пользовательский контент — только через Корзину, никогда hard-delete»): копия,
которую откатывает `DiscardCopies`, никогда не была видна пользователю как часть какой-либо панели — она
существовала долями секунды, только внутри незавершённой транзакции клонирования.

### 2. `IWindowManager.ClonePanelToPage` — транзакционно: либо клон целиком, либо ничего

```csharp
PanelCloneResult ClonePanelToPage(ChildWindowModel source, string pageId);
// PanelCloneResult(PanelCloneOutcome Outcome, ChildWindowModel? Clone, int SkippedMissingItems)
// PanelCloneOutcome { Cloned, UnknownPage, TooLarge, InsufficientSpace, CopyFailed }
```

Алгоритм: (1) `pageId` неизвестна → `UnknownPage`. (2) `SyncToModel` **только источника**
(`SyncEachIsolated` на одно окно) — клон стартует от того, что реально на экране, не от устаревшего
in-memory снимка. (3) Заголовок клона резолвится **до** копирования любого элемента (чистая in-memory
работа, не может сама по себе оставить осиротевшую копию, если бросит исключение) — `PanelCloneTitles.Resolve`:
без коллизии на целевой странице (`trim`, OrdinalIgnoreCase) — тот же заголовок; при коллизии —
«{0} — копия», затем «{0} — копия ({1})», n = 2, 3, … Для копии на **ту же** страницу коллизия
гарантирована (там же живёт источник). (4) Для каждого элемента `source.FilePaths`: managed и файл
существует → `CopyManaged`; managed, но файла нет → элемент **пропускается** (`SkippedMissingItems++`,
никогда не задваивается ссылка на один managed-путь между двумя панелями — иначе удаление одной удалило
бы файл другой); не managed (внешняя ссылка/ярлык на месте) → копируется как запись (тот же путь —
пользовательский файл, панель его не трогает при удалении); любой отказ `CopyManaged` → `DiscardCopies`
уже созданного, панель не создаётся.

Модель клона строится чистой функцией **`PanelCloneBuilder.Build`** (`UI/State`, internal static) через
`PanelStateMapper.ToDto(source)` → мутация DTO (`Id = Guid.NewGuid()`, `PageId`, `Title`,
`Content.FilePaths`) → `PanelStateMapper.FromDto(dto)`. Так каждое персистентное поле — сегодняшнее и
любое будущее — копируется автоматически через тот же маппер, которым `WindowManager` уже пишет/читает
панель на диск, без отдельного «списка полей клона», рискующего разойтись с маппером.
`ChildWindowModel.FileItems` (runtime-проекция `FilePaths`, никогда не маппится) намеренно не копируется —
клон получает свежую пустую коллекцию и заполняет её сам, как любая панель, только что загруженная с
диска. `SourceFolderPath` копируется как есть — Folder Portal копирует **привязку** к папке, не файлы;
у клона свой собственный `FileWatcher`, который `ChildWindowViewModel` подключает по `SourceFolderPath`
точно так же, как для любой другой панели.

Геометрия: копия на **другую** страницу получает ту же позицию/размер/монитор, что источник, без смещения.
Копия на **ту же** страницу смещается — `PanelCloneGeometry.Offset`: `LegacyFreeform` → +`IAppSettings.GridSize`
по X и Y (при `GridSize <= 1` — 24 DIP фиксированно); `GridAligned` → +1 `WorkspaceGridMetrics.UnitSize`
по X и Y (спаны не меняются). Результат клампится в рабочую область монитора существующим
`ClampIntoMonitor`; если после клампа позиция совпала с источником — смещение уходит в обратную сторону.

`CreateChildWindowCore` регистрирует окно напрямую (не публичный `CreateChildWindow`, который поднял бы
`OnChildWindowAdded` немедленно) — **H-1/M-B fix (code review):** событие `OnChildWindowAdded` поднимается
**последним** шагом внутри `try`, строго после того, как окно зарегистрировано, залогировано (`PanelCloned`,
opaque `panelId`, `skippedMissingItems` — приватность соблюдена, заголовок никогда не логируется) и
**сохранено** (`SaveWindowsStateNow()` — структурное изменение, ADR-024 D-12, синхронно, а не в дебаунс-окно).
Так исключение на любом промежуточном шаге не может оставить подписчиков (в первую очередь
`MainWindowViewModel.Panels`) держащими «призрачную» запись о клоне, который метод тут же откатывает в
`catch`.

**Откат при сбое (M-A/H-1 fix):** в `catch` сначала **безусловно** `DiscardCopies` уже созданных копий —
не зависит от того, что происходит с окном ниже (которое трогает WPF/native-ресурсы и само может
бросить); только затем, если окно успело зарегистрироваться, оно удаляется из `_childWindows` напрямую
(не через `RemoveChildWindow(releaseManagedItems: true)`, который увёл бы только что отброшенные копии в
Корзину и безусловно поднял бы `OnChildWindowRemoved`, даже для панели, о которой никто не узнавал через
`OnChildWindowAdded`); `Window.Close()` — в собственном `try/catch` с логированием
(`PanelCloneCloseFailed`), чтобы сбой закрытия окна не прервал уже выполненную очистку копий;
`OnChildWindowRemoved` поднимается только если `OnChildWindowAdded` успел прозвучать выше.
`GetManagedPathsClaimedByOtherPanels` (существующий heal-механизм ADR-009) **учитывает клон уже во время
создания** — включая панели ещё в процессе загрузки батча (`M-C fix`), так что self-heal одной панели не
принимает managed-путь клона, ещё не полностью зарегистрированного, за «ничей».

### 3. `IPanelCloneFlow`/`IBusyIndicator` — общий флоу для двух точек входа

Два места вызывают клонирование: раздел «Панели» окна настроек (`MainWindowViewModel.CopyPanelToPageCommand`)
и собственное контекстное меню заголовка панели (`ChildWindowViewModel.CopyPanelToPageCommand`) — **новое
в этой задаче**, изначально в объёме плана не заявленное (план §8.4 предполагал только меню окна
настроек), добавлено по ходу реализации как второй, более прямой путь. Оба вызывают не
`IWindowManager.ClonePanelToPage` напрямую, а общий `IPanelCloneFlow.CopyToPage(source, pageId,
onUnknownPage)`:

- показывает busy-индикацию (`IBusyIndicator`, реализация — курсор ожидания мыши,
  `MouseWaitCursorBusyIndicator`) на время синхронного вызова — копирование может быть медленным
  (большие managed-файлы), follow-up на будущее — сделать его асинхронным;
- `Cloned` возвращается вызывающему как есть — выбор клона/обновление списка панелей у двух точек входа
  разное, флоу этим не занимается;
- `UnknownPage` (целевая страница исчезла между открытием меню и кликом) — тихий колбэк `onUnknownPage`,
  без уведомления пользователя (зеркалит существующий тихий ресинк `MainWindowViewModel.OnPagesChanged`);
- любой другой отказ (`TooLarge`/`InsufficientSpace`/`CopyFailed`) — локализованное уведомление через
  `IConfirmationService.Notify`;
- `SkippedMissingItems` **никогда не показывается пользователю** — только логируется внутри
  `WindowManager.ClonePanelToPage` (осознанное решение: не отвлекать пользователя количеством
  отсутствовавших файлов, которых он и так не мог видеть на исходной панели).

**H-1 fix (найден в ревью):** до этого фикса только вызов из окна настроек показывал busy-курсор и
уведомление об отказе — вызов из меню заголовка панели отбрасывал результат `ClonePanelToPage` целиком,
и `TooLarge`/`InsufficientSpace`/`CopyFailed` там проходили полностью незаметно. `IPanelCloneFlow` —
единственное место, где живёт эта пара (busy-курсор + уведомление), поэтому обе точки входа теперь ведут
себя одинаково.

### 4. Уведомление об успехе — неблокирующая строка статуса, не модальный диалог (M-E fix)

Изначальная реализация показывала успех копирования модальным `MessageBox`-подобным подтверждением —
найдено ревью как избыточно навязчивое для рутинного, часто повторяемого действия. Заменено на
**неблокирующую** `MainWindowViewModel.PanelPageStatusMessage` — короткую строку в разделе «Панели»
(«Скопировано на «{страница}»» / аналогично для «Перемещено на…», тот же механизм переиспользован для
`MovePanelToPage`), которая сама очищается при следующем структурном изменении списка панелей.
`IWindowManager.OnChildWindowPageChanged` — новое событие, поднимаемое и при перемещении, и при
успешном клонировании, на которое подписан `MainWindowViewModel` для синхронизации `Panels`
(`OnPanelPageChanged`) независимо от источника изменения.

### 5. Два входа: меню заголовка панели и раздел «Панели»

- **Меню заголовка панели** (`ChildWindow.xaml`, `ChildWindowViewModel.CopyPanelToPageCommand`) —
  подменю со списком страниц (как «Переместить на страницу», которое там уже было). Копирование отсюда
  **не** показывает строку статуса (панель, на которую смотрит пользователь, продолжает быть у него на
  экране — обратная связь не нужна тем же способом, что в окне настроек).
- **Раздел «Панели» окна настроек** (`PanelsSection.xaml`) — кнопка «Копировать на страницу ▾» рядом с
  «Переместить на страницу ▾», то же устройство (`ContextMenu` с `ItemsSource` по страницам,
  `Header`/`CommandParameter` на `Display`/`Id` — контракты ADR-043). **Текущая страница разрешена** как
  цель — в отличие от «Переместить», где перемещение на ту же страницу было бы no-op.

## Последствия

### Позитивные
- Полный, честный паритет с ожиданием пользователя «независимая копия»: managed-файлы физически
  продублированы, удаление одной панели никогда не задевает другую.
- Транзакционность (либо клон целиком, либо откат до нуля) исключает класс «наполовину скопированная
  панель» или «осиротевшая managed-копия без панели».
- Формат состояния не меняется вовсе — клон - это обычный дополнительный `PanelStateDto`, `git diff` по
  `State/Dto`/`Storage/` пуст.
- Folder Portal копируется по духу «портал = привязка», не «портал = снимок файлов» — второй watcher на
  ту же папку работает независимо, оба видят живые изменения.

### Известные ограничения (Known limitations)
- **Удвоение места на диске** для больших managed-панелей — смягчено лимитами и предпроверкой
  свободного места, не устранено архитектурно (осознанная цена независимости копий).
- **Неоднозначный манифест** (две записи с одним и тем же original path) — задокументированное,
  тестируемое поведение `TryFindManagedPath`/`Restore`, не дефект.
- **Устаревшие снапшоты раскладки не знают о клоне.** Если снапшот, снятый до создания клона, потом
  восстанавливается, панель-клон (созданная после снимка) удаляется как «лишняя» без `Release()` —
  её managed-копии становятся сиротами. Это существующее поведение `LayoutSnapshotService.Restore` для
  **любой** панели, созданной после снимка, не специфичное для клонов — явно зафиксировано здесь, чтобы
  не быть открытым заново как «баг клона».
- **Синхронное копирование на UI-потоке** (с курсором ожидания) — приемлемо в рамках лимитов размера,
  но не идеал для очень больших наборов; явный follow-up, не блокер.
- Два независимых Folder Portal-watcher'а на одну и ту же папку — допустимо, панели полностью независимы
  друг от друга по конструкции.

## Manual verify (Win10/Win11) — не блокер

- Копия панели с managed-файлами на другую страницу: элементы на месте, в `PanelItems\` появились новые
  GUID-каталоги; удаление клона отправляет в Корзину только его собственные копии, источник цел.
- Копия на текущую страницу: видимое смещение на шаг сетки, заголовок «… — копия», повторная копия — «…
  — копия (2)».
- Копия Folder Portal: обе панели показывают содержимое папки; файл, добавленный в папку после
  копирования, появляется в обеих.
- Оба входа (меню заголовка панели, раздел «Панели») дают одинаковый результат при ошибке (`TooLarge`/
  `InsufficientSpace`) — уведомление показывается в обоих случаях, не только из окна настроек.
- Перезапуск приложения — клон и его элементы на месте.
