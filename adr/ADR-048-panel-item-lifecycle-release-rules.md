# ADR-048: Panel item lifecycle — release rules (консолидация)

**Статус:** Accepted (2026-10-09, ADR-audit WP-E) — консолидация действующих правил; **новых решений нет**, поведение кода не меняется — Amended 2026-10-09 (ADR-audit final pass: сценарий 4 — восстановление снапшота возвращает managed-элементы панелей вне снапшота, ADR-004; сценарий 9 — сбой перечисления = невосстановленный элемент, ADR-041); Amended 2026-10-10 (решение пользователя «Move остаётся», ADR-009 Amendment 7: сценарий 11 — ручной поиск и возврат осиротевших файлов; Q2 закрыт; подсказка OneDrive отсылает к drag-out, сценарий 7).

## Контекст

Судьба файла, который пользователь перетащил в панель, описана в семи ADR, и каждый следующий частично
пересматривал предыдущий: ADR-009 ввёл Move-семантику (файл физически переезжает в managed storage), ADR-010
развёл «закрыть» и «удалить», ADR-035 заменил hard-delete Корзиной, ADR-036 добавил drag-out, ADR-040 убрал
команду «Убрать из панели» и перехватил «Удалить» в shell-меню, ADR-041 добавил возврат файлов при
деинсталляции, ADR-045 — клонирование. Таблица вызывающих мест в ADR-010 устарела (после ADR-035). Аудит
ADR 2026-09-29 показал, что действующие правила приходится собирать из семи документов, а две политики
«вернуть файл на исходное место» (ADR-009 Решения 4–5 и ADR-041) расходятся. Этот ADR — **единый свод**;
в старых ADR добавлена ссылка «действующий свод — ADR-048». Все утверждения ниже сверены с кодом
(`WindowManager`, `PageManagerService`, `LayoutSnapshotService`, `MainWindowViewModel`, `ChildWindowViewModel`,
`PanelItemStorageService`, `PanelItemsUninstallRestorer`).

## Общая модель хранилища

- Managed storage — `PanelItems\{itemGuid}\{name}` в корне хранилища (`AppStorageRoot`: Release —
  `%LOCALAPPDATA%\DesktopOrganizer`, Debug — `DesktopOrganizer.Dev`, ADR-024) **поэлементно, не попанельно**;
  каталога панели не существует. Один корневой manifest `PanelItems\.manifest.json`
  (`managed path → original path`, атомарная запись, авторитетный in-memory кеш с write-through, ADR-012).
- Manifest — внутренняя деталь `PanelItemStorageService`; оригинальный путь не хранится ни в `FileItem`, ни в
  `ChildWindowModel.FilePaths` (ADR-009 Решение 2). Нет записи / manifest недоверенный → `RestoreOutcome.OriginalPathUnknown`.
- **Вход в хранилище:** `MoveIn`/`MoveInDirectory` (same-volume — атомарный `Move`; cross-volume —
  copy-verify-then-delete; для папок cap 2 ГиБ / 20 000 файлов). Сверх cap → `null`, панель ссылается на
  оригинал напрямую, без Move (ADR-009 Решение 6). Folder Portal ничего не перемещает (читает ФС).
- Панель ссылается на элемент по полному пути в `ChildWindowModel.FilePaths`; `IsManaged(path)` отличает
  managed-элементы от прямых ссылок. Прямая ссылка (не managed) при любом сценарии ниже **не трогается**.

## Действующие правила по сценариям

| # | Сценарий | Что происходит с managed-файлами | Реализация |
|---|---|---|---|
| 1 | **Закрытие окна панели** (завершение приложения, `ChildWindow.OnClosing`/`Dispose`) | Ничего. Файлы остаются в хранилище, панель восстановится при перезапуске. Release в `Dispose`/`OnClosing` **запрещён** (стёр бы данные при каждом выходе) | `WindowManager.RemoveChildWindow(Guid)` ≡ `releaseManagedItems: false` (в `src/` вызывающих нет) |
| 2 | **Удалить одну панель** («Удалить панель…» в настройках) | Один batch `ReleaseToRecycleBin` всех managed-путей панели **прямо из хранилища** (`PanelItems\<guid>\…` → Корзина). Все ушли → панель закрывается; остался хоть один → панель **остаётся**, из неё снимаются только реально ушедшие, `PanelRemovalResult.Blocked(remaining)` (fail-visibly, all-or-kept). Hard-delete нигде нет | `MainWindowViewModel.RemovePanel` → `RemoveChildWindow(id, releaseManagedItems: true)` → `ReleaseManagedItemsIfRequested`/`ReleaseToRecycleBin`. Перед этим `IConfirmationService.Confirm` (текст зависит от наличия managed-файлов) |
| 3 | **Удалить страницу** | **Сама** собирает managed-пути **всех** панелей страницы и делает **один** batch `ReleaseToRecycleBin` **до** удаления панелей. Остался хоть один → страница и **все** её панели остаются, ушедшие снимаются (`RemoveItemsFromPanels`), показывается `Notify` (`Recycle_Failed_Message_Format`), `RemovePage` возвращает `false`. Все ушли → панели удаляются с `releaseManagedItems: false` (уже в Корзине), `deferSave: true`, затем одно `SaveWindowsStateNow()` | `PageManagerService.RemovePage` |
| 4 | **Восстановление снапшота раскладки** | Никогда не release (ни Корзина, ни hard-delete): текущие панели закрываются с `releaseManagedItems: false` и пересоздаются из JSON с **теми же** managed-путями (`true` здесь = потеря данных, критический баг ADR-010, найденный до мержа). **Но** managed-элементы панелей, которых **нет в снапшоте**, до закрытия **возвращаются на исходное место** (`IPanelItemStorageService.Restore`, политика R, семантика «закрыть» ADR-010) — иначе они осиротели бы в скрытом хранилище. Folder Portal пропускается. Не вернулся элемент → fail-visibly: путь сливается в пересозданную панель-двойника (по исходному `Id`), иначе панель **остаётся**, из неё изымаются остальные элементы; статус `Critical` (N не вернулось) или `Success` (N вернулось). Двойник ищется по in-memory словарю `liveId → snapshotOriginalId` (не персистится; работает и при повторном restore того же снимка). Пересоздание панелей изолировано `try/catch` на модель, `SaveWindowsStateNow` и отчёт — в `finally`; managed-пути упавшей модели считаются невозвращёнными (`Critical`). В read-only сессии (`IsWritable == false`) файлы не возвращаются, и подтверждение restore этого не обещает (Amendment 2026-10-09) | `LayoutSnapshotService.Restore` → `IPanelItemStorageService.Restore` для панелей вне снапшота, затем `RemoveChildWindow(id, false, deferSave: true)`; `WindowManager.RemoveItemsFromPanels`; [ADR-004](ADR-004-phase5-pages-snapshots-multimonitor.md) Amendment 2026-10-09 |
| 5 | **«Удалить» одного managed-элемента в нативном shell-меню** | Перехвачено (`interceptDelete`, только `!IsPortal && IsManaged`). `RecycleManagedItem`: если оригинал **доверенный** и на фиксированном локальном диске → `Restore` на исходное место (воссоздаёт родителя, коллизия → `name (2).ext`, **политика R**), затем Корзина **оттуда** → «Восстановить» из Корзины вернёт файл в видимое место. Иначе (legacy без original, недоверенный manifest, съёмный/сетевой диск, restore не удался) — Корзина **на месте** из хранилища (`ReleaseToRecycleBin`). Не ушёл (отмена, отказ от nuke-warning) → файл возвращается в хранилище (`MoveIn*`, `ManagedRecycleKind.Kept`), элемент следует за новым путём. Shift не обходит Корзину | `ChildWindowViewModel.ShowShellContextMenu` → `DeleteManagedItem` → `IPanelItemStorageService.RecycleManagedItem` |
| 6 | **«Удалить» не-managed элемента** | Не перехватывается: shell удаляет как в Проводнике | `ShowShellContextMenu` |
| 7 | **Drag-out элемента** (на рабочий стол/в Проводник/в другую панель) | Файл **не** восстанавливается и не удаляется приложением. В другую панель — `TryClaim`, ссылка переносится, `Restore` не вызывается; наружу — после независимых проверок существования (0/500/2000 мс, `MovedOutVerifier`) вызывается `ForgetMovedOut` (**только** запись manifest и пустой GUID-каталог). Порталы drag-out отклоняют | `IPanelItemDragOutSession`, `ChildWindowViewModel.RemoveMovedOutItem`/`RemoveTransferredItem` |
| 8 | **Клонирование панели на страницу** | Каждый managed-элемент копируется `CopyManaged` в **собственный** `PanelItems\{newGuid}\` с **тем же** original path; отсутствующий источник пропускается (никогда не дублируется ссылка на один managed-путь). Откат при сбое: `DiscardCopies` удаляет **только** свежие копии этой операции **напрямую, минуя Корзину** (узкое исключение из «никогда hard-delete», ADR-035), окно-клон снимается из `_childWindows` и закрывается напрямую — не через `RemoveChildWindow(true)` | `WindowManager.ClonePanelToPage` |
| 9 | **Деинсталляция** (`--restore-panel-items`, `[UninstallRun]`) | `PanelItemsUninstallRestorer.RestoreAll`: каждый managed-элемент возвращается на исходное место **или** на рабочий стол (**политика U**), orphan'ы (нет записи manifest) — на рабочий стол; temp-мусор manifest удаляется; `PanelItems` удаляется целиком только при 0 сбоев; **сбой перечисления каталога (не удалось даже прочитать список) считается невосстановленным элементом** — корень не удаляется, код 7 (ADR-041 Amendment 2026-10-09). Коды выхода 0/6/7/8 | `Program.RunRestorePanelItems` |
| 10 | **Переименование / внешние изменения** (Cut→Paste, архиватор, «Создать ярлык») | Не release: `RenameManaged`, `ReconcileExternalChange` (rename/delete detection, sibling adoption, 40 тиков) | `ChildWindowViewModel.ReconcileAfterShellCommand` |
| 11 | **Осиротевший файл** (запись manifest `PanelItems\<guid>\…`, на которую не ссылается ни одна панель: удаление панели в read-only сессии, сбой `Restore`, файл, вернувшийся из Корзины в хранилище, старые инциденты) | **Ничего автоматически.** Пользователь запускает «Найти файлы без панели» (Настройки → Резервное копирование): `IManagedStorageOrphanScanner.Scan` (только чтение, фон) по `IPanelItemStorageService.GetManifestEntries()`; запись «используется», если на неё указывает путь живой панели любой страницы, панели снапшота, путь внутри перемещённой папки либо **исходный путь** записи. «Вернуть» → `IPanelItemStorageService.Restore` (**политика R**, с повторной проверкой, что файл не стал используемым); «Открыть папку». Ничего не удаляется, hard-delete нет. В read-only сессии сканирование и возврат отключены | `ManagedStorageOrphansViewModel`, `ManagedStorageOrphanScanner`; [ADR-009](ADR-009-drag-drop-move-semantics.md) Amendment 7 (O2) |

Подсказка при drop из облачной папки (ADR-009 Amendment 7, O1) не является отдельным сценарием release: она сообщает, что файл
перемещён в хранилище, и отсылает к **сценарию 7** (перетащить файл из панели обратно в папку). **Удаление панели файл
не возвращает** (сценарий 2: Корзина прямо из хранилища).

Инвариант вызывающих мест `RemoveChildWindow` (обновлённая редакция Решения 1 ADR-010): `releaseManagedItems: true`
допустим **только** для перманентного удаления **одной** панели; массовые вызовы (страница) сами делают batch-recycle
и передают `false`; восстановление снапшота и откат клона **никогда** не освобождают managed-файлы.

## Две политики «вернуть на исходное место» (зафиксированы как есть)

| Аспект | **Политика R** — `PanelItemStorageService.Restore` (ADR-009 Решения 4–5) | **Политика U** — `PanelItemsUninstallRestorer.ResolveTarget` (ADR-041) |
|---|---|---|
| Где действует | Внутри `RecycleManagedItem` (сценарий 5) и при восстановлении снапшота для элементов панелей вне снапшота (`LayoutSnapshotService.Restore`, сценарий 4; в обоих случаях вызывающий проверяет `IsManaged`, в сценарии 4 — ещё `IsWritable`). Отдельного пользовательского действия «вернуть» нет | Только при деинсталляции (сценарий 9) |
| Родительский каталог | **Воссоздаётся** (`Directory.CreateDirectory`) | Должен **существовать**, иначе — рабочий стол |
| Коллизия имени | Первое свободное имя Explorer-стиля **в исходной папке** (`name (2).ext`, без перезаписи) | Точный целевой путь занят → **рабочий стол** под коллизионно-свободным именем |
| Fallback на рабочий стол | **Нет** (намеренно: «файл появился не там, откуда взят» хуже воссозданной папки; Services не знает о «Desktop») | **Есть**: оригинал недоступен/не на фиксированном диске/orphan → рабочий стол |
| Условие «фиксированный локальный диск» | Проверяется в `RecycleManagedItem` **до** вызова `Restore`; сам `Restore` его не проверяет | Проверяется в `ResolveTarget` (`DriveType.Fixed`) |
| Если не получилось | `RestoreOutcome.Failed`/`OriginalPathUnknown` → Корзина на месте (сценарий 5); копия остаётся в хранилище | Элемент остаётся в хранилище, код выхода 7, `PanelItems` не удаляется |
| Cross-volume | copy-verify-then-delete | copy-verify-then-delete; read-only источник, не удалённый после проверенной копии, считается **восстановленным** |

Расхождение не регрессия: политики писались для разных контекстов (интерактивное действие vs headless-деинсталляция,
где потеря файла хуже «неожиданного» места). Единая политика — **открытый вопрос** (см. ниже), код не менялся.

## Известные ограничения

1. **Панель/страница → Корзина идёт из хранилища.** Файл, восстановленный из Корзины Проводником после удаления панели
   или страницы (сценарии 2–3), возвращается в `PanelItems\<guid>\`, а не на панель и не на исходное место;
   никакого UI для повторной привязки нет. Закрыто только для одиночного «Удалить» (сценарий 5) — и только на пути
   «restore, затем recycle»; fallback «Корзина на месте» (legacy, съёмный/сетевой диск, сбой restore) воспроизводит
   то же ограничение.
2. `FOF_WANTNUKEWARNING` может показать диалог оболочки (Yes/No) на элементе, слишком большом для Корзины; пути длиннее
   `MAX_PATH` не поддерживаются `SHFileOperation` и попадают в `Remaining` (видимый отказ, не потеря).
3. Клон (сценарий 8) разделяет original path с источником: `Restore` возвращает обе копии на одно место (вторая — `(2)`),
   `TryFindManagedPath` для такого original однозначного ответа не даёт (явный отказ, не угадывание).
4. Проверка drag-out наружу — эвристика (окно 2 с); медленный внешний диск может не успеть.
5. Частичный сбой деинсталляции (код 7) без автоматического ретрая: `PanelItems` и manifest остаются.
6. Если `Restore` упал (сбой ФС), managed-копия остаётся в хранилище без активной ссылки («осиротевшая»); её очистка
   отдельной задачей не решена (долг ADR-009). *Обновлено 2026-10-10:* такой файл можно найти и вернуть вручную
(сценарий 11); автоматической очистки по-прежнему нет.
7. Не-managed элемент, файл которого исчез, остаётся «серым» дольше, чем managed (унаследованное поведение liveness,
   ADR-046 «Известные ограничения»).

## Открытые вопросы

- **Q1 — две политики restore.** A: оставить как есть (разные контексты). B: ввести общий `IManagedItemRestorePolicy` с
  fallback на рабочий стол и в интерактивном пути. C: убрать fallback на рабочий стол и в деинсталляторе (воссоздавать родителя).
  Рекомендация — A до явного решения пользователя. (Отдельный пункт: условие «фиксированный диск» живёт в двух местах.)
- **Q2 — Move vs «ссылка без перемещения».** Move (ADR-009 Решение 1) порождает весь этот ADR; режим «ссылка» (как у
  Fences — иконки остаются на столе) убрал бы release/restore целиком. Решение пользователя —
  `docs/ROADMAP.md`, «Решения, ожидающие пользователя», п. 2. **Закрыт 2026-10-10: Move остаётся**, режим «ссылка» не
  вводится (ADR-009 Amendment 7); для осиротевших файлов добавлен ручной поиск/возврат (сценарий 11).
- **Q3 — recycle панели/страницы после restore?** По аналогии со сценарием 5 можно восстанавливать на исходное место
  перед Корзиной, закрыв ограничение 1; отклонено в ADR-035 как слишком большое поведенческое изменение (файлы
  появляются в непредсказуемых местах рабочего стола). Не пересматривается без пользователя.

## Последствия

- Одна точка входа для ревью любого изменения, затрагивающего `RemoveChildWindow`, `PageManagerService.RemovePage`,
  `RecycleManagedItem`, drag-out, клонирование и деинсталляцию.
- Старые ADR сохраняют историю решений; в их шапках — ссылка на этот свод. Таблица вызывающих мест в ADR-010 исправлена
  (Amendment 2026-10-09).
- Persistence не затронута: формат manifest и `application-state.json` без изменений (замороженный контур ADR-024).
