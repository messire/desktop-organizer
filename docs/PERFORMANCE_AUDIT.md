# Аудит: память, скорость, отказоустойчивость

**Дата аудита:** 2026-07-27
**Тип на момент аудита:** только анализ, без изменений кода (см. запрос — «просто найди места, ничего менять не надо»).
**Цель:** список конкретных мест в коде, которые стоит доработать для снижения потребления памяти,
роста скорости и повышения отказоустойчивости, перед тем как приложение будет активно использоваться.

## Статус реализации: аудит закрыт (2026-08-15)

**Все 11 находок ниже реализованы.** Список сохранён как исторический контекст (что было найдено и
почему), но он больше не описывает текущее состояние кода "как есть" — он описывает состояние **до**
Фазы 7.

- **Мастер-план:** [docs/PLANS/phase-7-performance-hardening.md](PLANS/phase-7-performance-hardening.md)
  сгруппировал 11 находок в 6 независимых по файлам блока (A–F), каждый прошёл конвейер
  реализация → тесты → code-quality-ревью (один фикс-цикл на волну) → fences-ux-parity-ревью
  (без блокирующих находок).
- **Архитектурные решения:** [ADR-012](../adr/ADR-012-performance-and-resilience-hardening.md) —
  двухуровневая политика persistence (дебаунс vs синхронный flush), вынос чистой машины состояний из
  нативного хука (расширение прецедента ADR-011), инвариант `Freeze()` для `ImageSource` из
  Services-слоя, авторитетный in-memory кеш манифеста `PanelItemStorageService`.
- **ROADMAP:** [docs/ROADMAP.md](ROADMAP.md), «Фаза 7. Производительность, память и отказоустойчивость» —
  отмечена закрытой, все 6 блоков `[x]`.
- **Билд/тесты:** зелёные, 324/330 passed (6 failed — предсуществующие, не относятся к этой фазе).
- **Не проверено:** ни один из блоков A–F не прогнан вживую на Windows (среда разработки ограничена
  `dotnet build`/`dotnet test`) — см. полный список manual verify в мастер-плане Фазы 7 и в ROADMAP.
- **Известные оставленные вне scope риски** (задокументированы, не блокируют закрытие аудита, см.
  ADR-012 «Последствия» и ROADMAP «Сквозные задачи»): отсутствие single-instance guard между процессами
  (блок C/F); сброс скролла/выделения списка при `Reset`-уведомлении (блок D, не регрессия); дефект
  резолва `linters/linter.ruleset` (`MSB3884`), обнаруженный по пути, но не относящийся к этой фазе.

## Исходный список находок (исторический контекст, состояние на 2026-07-27, до Фазы 7)

Ничего из перечисленного ниже не было исправлено **на момент этого аудита** — см. раздел выше про
фактическую реализацию всех 11 пунктов в Фазе 7 (2026-08-15).

---

## 1. Память

1. **`src/DesktopOrganizer.Services/Providers/IconProvider.cs:16`** — `_iconCache`
   (`ConcurrentDictionary<string, ImageSource>`) растёt неограниченно: ключ — полный путь файла,
   записи никогда не удаляются (даже после удаления файла, закрытия панели, ресинка Folder Portal).
   При долгой сессии с активными Folder Portals или частой сменой файлов в панелях — неограниченный
   рост потребления памяти.

2. **`src/DesktopOrganizer.UI/ViewModels/ChildWindowViewModel.cs:269-282`** (`LoadFromModel`)
   подписывается `Model.PropertyChanged += OnModelPropertyChanged`, но `Dispose()` (строки 420-428)
   эту подписку не снимает. `ChildWindowModel` переживает свою ViewModel (хранится в списках
   состояния/снапшотах) — закрытая/удалённая ViewModel остаётся живой через делегат события, пока
   жив её `Model`.

3. **`src/DesktopOrganizer.Services/Tools/NotifyIconAdapter.cs:19`** — `_notifyIcon.Icon = new
   Icon(iconPath)` не освобождает предыдущий `Icon` (нативный GDI-хэндл) при повторном вызове
   `SetIcon`. Сейчас вызывается один раз при старте (низкий риск), но при появлении смены иконки
   трея по состоянию — потечёт.

4. **`src/DesktopOrganizer.UI/Converters/HexBrushConverter.cs:16`**,
   **`src/DesktopOrganizer.UI/Converters/ColorOpacityBrushConverter.cs:34`** — создают новый
   `SolidColorBrush` на каждый вызов конвертера и не вызывают `.Freeze()`. При частых обновлениях
   биндинга (цвет/прозрачность панели) — лишние аллокации и неоптимальный рендер.

## 2. Скорость

5. **`src/DesktopOrganizer.UI/ViewModels/BaseViewModel.cs:59-66`** (`AddFiles`) — проверка дубликата
   через `_allItems.Any(...)` — O(n) на каждый добавляемый файл. `ReplaceAll` (строки 99-103) чистит
   список и вызывает `AddFiles` для всех путей разом → O(n²) при полном ресинке. Прямой удар по
   Folder Portal / «Захвату иконок рабочего стола» при большом количестве файлов (сотни/тысячи) —
   плюс на каждый файл дёргается `IconProvider.GetIcon` (нативный shell-вызов).

6. **`src/DesktopOrganizer.UI/ViewModels/BaseViewModel.cs:110-115`** (`OnSourceChanged`) —
   `FileItems.Clear()` + поштучный `Add()` в `ObservableCollection` → N отдельных
   `CollectionChanged`-уведомлений вместо одного batch/reset. Для крупных портал-папок — лишние
   перерисовки UI.

7. **`src/DesktopOrganizer.Services/Tools/PanelItemStorageService.cs`**
   (`WriteManifestEntry`/`ReadManifestEntry`/`RemoveManifestEntry`, строки 494-520) — каждая операция
   читает и перезаписывает **весь** JSON-манифест целиком с диска. При drag&drop нескольких файлов
   разом (`ChildWindowViewModel.AddDroppedFiles`, цикл по `sources`) манифест перечитывается/
   переписывается по разу на каждый файл — нет ни кеша в памяти, ни батчинга на всю операцию drop.

8. **`src/DesktopOrganizer.UI/Services/WindowManager.cs:182-193`** (`SaveWindowsState`) — полная
   JSON-сериализация всех панелей + `Settings.Default.Save()` (запись всего user.config) на каждое
   мелкое действие (ресайз, ремув файла, свитч вида, смена фильтра) без дебаунса. При многих открытых
   панелях/частых действиях — лишняя дисковая запись на каждое действие.

## 3. Отказоустойчивость

9. **`src/DesktopOrganizer.Services/Tools/DesktopGestureService.cs:58-102`** (`HookCallback`) — весь
   метод **не обёрнут в try/catch**. Это глобальный `WH_MOUSE_LL`-хук: события
   `DesktopDoubleClicked`/`LassoCompleted` (строки 116, 125) вызывают подписчиков синхронно прямо в
   теле хука. Любое исключение у подписчика (например, при создании панели) улетит наружу
   необработанным прямо из системного хука — ровно тот класс риска, который сам ROADMAP описывает как
   «ошибка в колбэке хука тормозит ввод системы». Это единственное место без defensive try/catch, хотя
   весь остальной нативный код проекта (`MonitorService`, `SystemShellService`, `NativeApi`)
   последовательно его использует.

10. **`src/DesktopOrganizer.UI/Services/WindowManager.cs:196-215`** (`LoadWindowsState`) — ловит
    только `JsonException`. Если у одной сохранённой панели в списке `CreateChildWindow` бросит любое
    другое исключение (например, из `ResolveMonitorPlacement` или DI) — падает вся загрузка окон, т.е.
    один битый элемент состояния может не дать приложению стартовать. Нет per-item изоляции (в отличие
    от `FileItem.Exists`, который специально спроектирован не ронять загрузку на битых путях).

11. **`src/DesktopOrganizer.UI/Services/WindowManager.cs:182-193`** (`SaveWindowsState`) — вызывается
    из множества мест без try/catch вокруг сериализации/`Settings.Save()`. Сбой записи (диск полон,
    нет прав, залоченный config) вылетит необработанным на самом обычном действии пользователя
    (двигаешь панель — падает).

## Как читать этот список

Пункты не упорядочены по приоритету. Наиболее «дешёвые в исправлении и заметные по эффекту»:
пункт 4 (`.Freeze()` на брашах), пункт 2 (отписка от `PropertyChanged`), пункт 9 (try/catch вокруг
хука). Наиболее «архитектурные»: пункты 5-6 (O(n²) в `BaseViewModel`) и пункт 7 (манифест
перечитывается целиком на каждую операцию) — эти стоит брать через `fences-feature-planner`, а не
точечной правкой.

**Это описание больше не соответствует текущему коду** — все 11 пунктов реализованы в Фазе 7
(2026-08-15). См. «Статус реализации» в начале документа для таблицы находка → блок/файл/ADR.
