# План: панели не накладываются друг на друга при перетаскивании (anti-overlap, «твёрдая стена»)

Источник: пользовательский запрос от 2026-09-01 (скриншот с перекрывающимися панелями `personal` / `work`)
+ уточнение решения самим пользователем (выбран вариант «жёсткая блокировка на границе»).
Ветка: `polishing/ui-1`. Это **не** пункт ROADMAP-фазы, а отдельная поведенческая фича, независимая от
батча `docs/PLANS/ui-polishing-1.md` (пересечение по файлам: только `ChildWindow.xaml.cs`, разные методы).

**Scope: M** — один проект (`DesktopOrganizer.UI`), три точки: новый чистый helper в `UI/Models`,
один новый метод в `UI/Services/IWindowManager` + реализация, ~30 строк в `Views/ChildWindow.xaml.cs`.

## 1. Требование (что именно просили)

- Во время перетаскивания панели за заголовок она **физически не может** пересечь границу другой
  панели: движение останавливается у её края.
- Это **не** снаппинг к ближайшему свободному месту и **не** раздвигание соседей (не tiling-менеджер).
  Модель — «твёрдая стена» / AABB collision response из 2D-игр.
- Курсор мыши имеет право «убежать» от панели: панель просто не долетает до пересечения, оставаясь у
  стены, пока курсор не вернётся.
- Оси независимы: упёршись в соседа слева-справа, панель обязана продолжать свободно ехать вверх-вниз
  (скольжение вдоль стены), и наоборот.

Отсюда сразу два не-требования, зафиксированных явно:
- **НЕ** трогаем восстановление сохранённых позиций (см. §4, правило R1);
- **НЕ** двигаем и **НЕ** ужимаем соседние панели ни при каких обстоятельствах.

## 3. Решение

### 3.1. D1 — чистая математика в отдельном helper'е `PanelCollision` (`UI/Models`)

Новый статический класс `src/DesktopOrganizer.UI/Models/PanelCollision.cs` — третий вычислительный
helper рядом с `GridMetrics` (ADR-005) и `GridSnap` (ADR-011): без `DependencyObject`, без диспетчера,
без P/Invoke; единственная внешняя зависимость — структура `System.Windows.Rect` (WindowsBase, plain
struct, доступна в тестовом проекте: `UseWPF=true` задан в корневом `Directory.Build.props`).

Публичная поверхность:

```csharp
public static class PanelCollision
{
    /// <summary>Строгое пересечение с допуском: касание ребром (a.Right == b.Left) НЕ пересечение.</summary>
    public static bool Overlaps(Rect a, Rect b);

    /// <summary>AABB collision response: движение current → proposed, обрезанное о препятствия.</summary>
    public static Rect ClampAgainstObstacles(Rect current, double proposedLeft, double proposedTop, IReadOnlyList<Rect> obstacles);
}
```

**Почему сигнатура не `ClampAgainstObstacles(Rect proposed, IEnumerable<Rect> obstacles)`, как в
формулировке задачи.** Двух-аргументной версии не хватает информации, и это не стилистика, а два
функциональных дефекта:
1. **Нет направления движения.** Зная только `proposed`, при пересечении невозможно решить, к какому
   ребру препятствия прижиматься (влево или вправо) — приходится гадать по «минимальному выталкиванию»,
   что даёт классический артефакт: панель, глубоко вошедшую в соседа за один быстрый кадр, выплюнет с
   противоположной стороны. Прежняя позиция `current` задаёт знак `dx`/`dy` однозначно.
2. **Нет базы для «амнистии» уже существующих пересечений** (правило R1, §4): без `current` нельзя
   отличить «панель уже стояла внутри соседа» от «панель только что въехала».

`IReadOnlyList<Rect>` (а не `IEnumerable<Rect>`) — сознательно: обход по индексу в `for` не создаёт
боксированного энумератора на каждый кадр (см. §5).

### 3.2. D2 — алгоритм: раздельное разрешение по осям + swept-тест

Обозначения: `Right = X + W`, `Bottom = Y + H`; всё в WPF DIP, в глобальных координатах.

```
Overlaps(a, b) :=
    Min(a.Right, b.Right) - Max(a.X, b.X) > Eps
 && Min(a.Bottom, b.Bottom) - Max(a.Y, b.Y) > Eps        // Eps = 0.5 DIP

ClampAgainstObstacles(current, proposedLeft, proposedTop, obstacles):
    w = current.Width;  h = current.Height
    if (w <= 0 || h <= 0 || obstacles.Count == 0)
        return new Rect(proposedLeft, proposedTop, w, h)          // нечего разрешать

    // ---------- ось X ----------
    newLeft = proposedLeft
    dx = proposedLeft - current.X
    if (dx != 0):
        sweepX = Rect(Min(current.X, proposedLeft), current.Y, Abs(dx) + w, h)
        foreach o in obstacles:
            if (Overlaps(current, o)) continue          // R1: препятствие уже перекрыто → «призрак»
            if (!Overlaps(sweepX, o))  continue         // на пути не стоит
            newLeft = dx > 0 ? Min(newLeft, o.X - w)    // упёрлись левым ребром соседа
                             : Max(newLeft, o.Right)    // упёрлись правым ребром соседа
        newLeft = dx > 0 ? Max(newLeft, current.X) : Min(newLeft, current.X)   // никогда не назад

    // ---------- ось Y (уже с разрешённым X) ----------
    afterX = Rect(newLeft, current.Y, w, h)
    newTop = proposedTop
    dy = proposedTop - current.Y
    if (dy != 0):
        sweepY = Rect(newLeft, Min(current.Y, proposedTop), w, Abs(dy) + h)
        foreach o in obstacles:
            if (Overlaps(afterX, o)) continue
            if (!Overlaps(sweepY, o)) continue
            newTop = dy > 0 ? Min(newTop, o.Y - h)
                            : Max(newTop, o.Bottom)
        newTop = dy > 0 ? Max(newTop, current.Y) : Min(newTop, current.Y)

    return Rect(newLeft, newTop, w, h)
```

Свойства, которые обязаны быть покрыты тестами (§7):

- **Независимость осей.** X-шаг тестирует прямоугольник в строке `current.Y`, Y-шаг — в колонке
  `newLeft`. Упор в соседа слева не мешает ехать вниз → скольжение вдоль стены (требование §1).
- **Отсутствие тоннелирования.** Swept-прямоугольник (объединение старого и нового положения вдоль
  одной оси) ловит препятствие, которое за один кадр перепрыгнули бы целиком при резком рывке мыши.
  Стоимость — те же O(n), лишний `Rect` на стеке.
- **Движение только вперёд.** При `dx > 0` из `Overlaps(sweepX, o) && !Overlaps(current, o)` следует,
  что по Y `current` и `o` перекрываются (у `sweepX` та же Y-полоса), значит по X они **не**
  перекрываются, значит `o.X >= current.Right > current.X`, значит `o.X - w >= current.X`. Клампинг
  математически не может отбросить панель назад; финальные `Max/Min` — дешёвая страховка от
  накопленной погрешности `double`, а не содержательный шаг.
- **Отсутствие дрожания.** После клампа `newLeft = o.X - w` перекрытие ровно `0`, что при строгом
  `> Eps` не считается пересечением. На следующем кадре то же препятствие снова «твёрдое», позиция не
  осциллирует. Позиция панели остаётся **чистой функцией** (курсор, набор препятствий) — без
  накопления состояния между кадрами, поэтому «убежавший» курсор при возврате подхватывает панель
  ровно 1:1, без резинки и без сдвига.
- **Асимметрия X-раньше-Y принята сознательно.** При диагональном заходе на препятствие результат
  зависит от порядка осей (панель проедет вправо и остановится сверху от соседа, а не наоборот).
  Оба варианта визуально корректны; фиксируем детерминированный X→Y и документируем в XML-doc.

### 3.3. D3 — источник препятствий: снимок live-геометрии **один раз на жест**

`ChildWindowModel.Position/Size` для этого **непригодны**: это `int`-снимок, обновляемый из
`OnLocationChanged`/`OnRenderSizeChanged` с усечением (`(int)Left`), и для свёрнутой (rolled-up)
панели `Size` намеренно хранит **развёрнутую** высоту (`OnRenderSizeChanged:350–355`) — препятствие
получилось бы выше, чем видит пользователь. Берём live-значения окна.

Новый член `IWindowManager` (`src/DesktopOrganizer.UI/Services/IWindowManager.cs`):

```csharp
/// <summary>
/// Заполняет <paramref name="buffer"/> актуальными экранными прямоугольниками всех живых видимых
/// панелей, кроме <paramref name="excludingId"/>. Буфер принадлежит вызывающему и переиспользуется
/// между жестами — метод сам вызывает Clear(). Аллокаций не делает.
/// </summary>
void CollectOtherPanelBounds(Guid excludingId, IList<Rect> buffer);
```

Реализация в `WindowManager` — обход `_childWindows.Values` с фильтрами:

```csharp
buffer.Clear();
foreach (var (window, model) in _childWindows.Values)
{
    if (model.Id == excludingId) continue;              // сама перетаскиваемая панель
    if (!window.IsVisible) continue;                    // скрытая (другая страница / IsVisible=false)
    var w = window.ActualWidth  > 0 ? window.ActualWidth  : window.Width;
    var h = window.ActualHeight > 0 ? window.ActualHeight : window.Height;
    if (double.IsNaN(window.Left) || double.IsNaN(window.Top) || double.IsNaN(w) || double.IsNaN(h)) continue;
    if (w <= 0 || h <= 0) continue;                     // ещё не измерена / вырожденная
    buffer.Add(new Rect(window.Left, window.Top, w, h));
}
```

**Снимок делается один раз, в `TitleBar_MouseLeftButtonDown`**, а не на каждый `MouseMove`. Обоснование
корректности: во время жеста мышь захвачена (`CaptureMouse()`), поэтому другая панель не может быть в
этот момент перетащена, отресайзена, свёрнута, создана или удалена — все эти действия требуют мыши.
Асинхронных источников изменения геометрии панели в проекте нет (`FileSystemWatcher` портала меняет
только содержимое списка, `IMonitorService.MonitorsChanged` → `OnMonitorsChanged` теоретически может
подвинуть окна при переключении монитора посреди драга — это принято как исчезающе редкий случай, в
худшем варианте один жест отработает по устаревшему снимку; следующий жест уже по актуальному).

Поля в `ChildWindow`:
```csharp
// Снимок препятствий на текущий жест перетаскивания (см. docs/PLANS/panel-anti-overlap.md §3.3).
// Переиспользуется между жестами, чтобы TitleBar_MouseMove не аллоцировал ничего на кадр.
private readonly List<Rect> _dragObstacles = [];
```
Заполняется в `TitleBar_MouseLeftButtonDown` (после успешного `CaptureMouse()`), очищается в `EndDrag`.

### 3.4. D4 — какие окна являются препятствиями (и какие нет)

| Окно | Препятствие? | Почему |
|---|---|---|
| Другая видимая fence-панель (`ChildWindow`) | **Да** | суть фичи |
| Панель на другой странице / `IsVisible = false` | **Нет** | фильтр `window.IsVisible`. Правило «блокирует ровно то, что пользователь видит»; иначе на экране появлялись бы невидимые мёртвые зоны |
| Свёрнутая (rolled-up) панель | **Да, по фактической высоте заголовка** | `ActualHeight`. Следствие: под свёрнутой панелью можно припарковать другую, и после разворачивания они перекроются — это принято (раздвигать соседей запрещено требованием) |
| Боковая панель `SystemIconsPanelWindow` | **Нет** (в этом батче) | не участвует в fence-раскладке, сама не перетаскивается, может скрываться/показываться → блокировка о неё дала бы мигающую мёртвую зону у края экрана. Вынесено в бэклог §9.2 |
| `MainWindow` (окно настроек) | **Нет** | обычное активируемое окно поверх десктопа, не элемент раскладки |
| Края монитора / рабочая область | **Нет** (вне scope) | границей монитора драг не ограничивается и сейчас; за возврат уехавших панелей отвечает `WindowManager.ClampIntoMonitor` при смене конфигурации мониторов |

### 3.5. D5 — порядок относительно `GridSnap` / `SnapToGrid()`: клампинг всегда последний

**Живой драг** (`TitleBar_MouseMove`) — конвейер:

```
raw (курсор)  →  GridSnap.Snap(raw)  →  PanelCollision.ClampAgainstObstacles(...)  →  Left/Top
```

Клампинг **после** магнита и **не** переснаппливается обратно. Причины:
- магнит к сетке может утянуть панель внутрь соседа на величину до `GridSnapDistance` (12 px по
  умолчанию) — если клампить до магнита, стена дырявая;
- позиция «впритык к соседу» намеренно оказывается вне сетки: панели становятся визуально смежными
  (ребро в ребро), а это ровно то, чего ждут от Fences-подобной раскладки. Приоритет «стена > сетка».

**Mouse-up** (`SnapToGrid()`, вызывается из `EndDrag` и из `Resize_DragCompleted`): снап обязан
**уважать** анти-оверлап, иначе в момент отпускания кнопки панель прыгнет на 1–12 px внутрь соседа —
то есть весь жест был честным, а результат нет. Реализация — не полноценный клампинг, а условный снап
по каждой оси: применить `GridSnap.SnapAxis`, и если получившийся прямоугольник пересекает
препятствие, которого до снапа не пересекал, — откатить **эту** ось к до-снаповому значению.

```csharp
private void SnapToGrid()
{
    var grid = _appSettings.GridSize;
    if (grid <= 1) return;

    var threshold = _appSettings.GridSnapDistance;
    var w = ActualWidth; var h = ActualHeight;
    var before = new Rect(Left, Top, w, h);

    var snappedLeft = GridSnap.SnapAxis(Left, grid, threshold);
    if (!PanelCollision.CreatesNewOverlap(before, new Rect(snappedLeft, Top, w, h), _dragObstacles))
        Left = snappedLeft;

    var afterX = new Rect(Left, Top, w, h);
    var snappedTop = GridSnap.SnapAxis(Top, grid, threshold);
    if (!PanelCollision.CreatesNewOverlap(afterX, new Rect(Left, snappedTop, w, h), _dragObstacles))
        Top = snappedTop;
}
```

`CreatesNewOverlap(Rect before, Rect after, IReadOnlyList<Rect> obstacles)` — третий (и последний)
публичный член `PanelCollision`: `true`, если существует препятствие, которое пересекает `after` и не
пересекало `before`. Формулировка «новое пересечение» (а не «любое») сохраняет правило R1: панель,
уже стоящую внутри соседа с прошлой сессии, снап к сетке не парализует.

⚠️ **Отдельно про вызов `SnapToGrid()` из `Resize_DragCompleted`:** там `_dragObstacles` пуст (жест
драга не начинался), `CreatesNewOverlap` вернёт `false` для любой оси, и снап отработает ровно так,
как сегодня. Это осознанное следствие решения §3.6 «ресайз в этот батч не входит», а не недосмотр —
реализующий агент **обязан** оставить в коде комментарий именно с такой формулировкой, чтобы будущий
ревьюер не «починил» это случайно.

### 3.6. D6 — ресайз (`Resize_DragDelta`) в этот батч **не входит**

Обоснование (не «забыли», а взвешенный trade-off):
1. Пользователь спрашивал только про перетаскивание; жёсткая стена на ресайзе — отдельное UX-решение
   (кто «выигрывает», если ресайз упирается: стоп по размеру или стоп с переходом в min-size).
2. Ресайз клампится по **размеру**, а размер уже квантуется другой системой из батча `ui-polishing-1`
   (`GridMetrics.Quantize`, `_stepX/_stepY`, `MinPanelSize`, компенсация `FileListHPadding`).
   Клампленная о соседа ширина почти всегда **не** кратна ячейке → либо ломается квантизация (панель
   перестаёт попадать в колонки иконок), либо ломается стена (округление вверх снова наезжает на
   соседа). Разрешение этого конфликта требует собственного набора тестов и собственного решения о
   приоритете — смешивать две системы клампинга в одном батче рискованно.
3. Драг и ресайз ортогональны в коде: общий у них только `SnapToGrid()`, чьё поведение зафиксировано
   выше явным правилом.

Вынесено в бэклог §9.1 с эскизом решения.

## 4. Edge-cases и правила (обязательные к реализации)

- **R1 — уже существующие пересечения не «чинятся» (ключевое правило).** Загрузка состояния
  (`WindowManager.LoadWindowsState`), восстановление снапшота (`LayoutSnapshotService.Restore`),
  `ClampIntoMonitor`, создание панели — **ни одна** из этих точек не трогается фичей. Пересечения,
  легальные до этой фичи, остаются на своих местах после обновления версии. Механика на уровне
  алгоритма: препятствие, которое **уже** пересекает текущее положение панели, на этот кадр
  «призрачно» (`if (Overlaps(current, o)) continue`) — панель можно вытащить наружу, а как только она
  вышла (перекрытие ≤ `Eps`), препятствие становится твёрдым и обратно не пускает.
- **R2 — вложенность.** Панель целиком внутри другой (или наоборот) — частный случай R1: вытаскивается
  свободно в любую сторону, назад не возвращается.
- **R3 — пустой набор препятствий.** Одна панель на экране / все остальные скрыты → `obstacles.Count == 0`
  → ранний выход, поведение драга байт-в-байт как сегодня.
- **R4 — вырожденная геометрия.** `NaN`/`0` в `Left/Top/ActualWidth/ActualHeight` (окно ещё не
  измерено) → препятствие пропускается при сборе; у самой перетаскиваемой панели `w <= 0 || h <= 0`
  → клампинг пропускается целиком.
- **R5 — потеря захвата мыши** (Alt+Tab, системный диалог): `TitleBar_LostMouseCapture` → `EndDrag` →
  `_dragObstacles.Clear()`. Никакого «залипшего» снимка между жестами.
- **R6 — усечение до `int` при персистенции.** `OnLocationChanged` пишет `(int)Left` — позиция «впритык»
  с дробной частью может при следующей загрузке дать перекрытие до 1 px. Это ниже `Eps = 0.5`? Нет,
  ровно до 1 px, поэтому формально возможно микро-перекрытие после перезапуска; оно амнистируется
  правилом R1 и визуально неотличимо. **Менять тип `ChildWindowModel.Position` в этой фиче
  запрещено** — это persistence-формат, не стоит 1 px.
- **R7 — мультимонитор.** Никакой фильтрации по монитору: `IMonitorService` в алгоритме не участвует
  вообще. Все прямоугольники берутся из `Window.Left/Top` — единое глобальное DIP-пространство, поэтому
  панели на разных мониторах (в т.ч. при мониторах «со сдвигом», где виртуальные области соседствуют
  нестандартно) сравниваются корректно, а панели на физически разнесённых мониторах просто никогда не
  пересекаются и клампинг для них — no-op.
- **R8 — смешанный DPI (риск, см. §8).** Под per-monitor DPI awareness `Window.Width/ActualWidth` окна
  выражены в DIP этого окна, а `Left/Top` — в общем координатном пространстве; на двух мониторах с
  разным масштабом (100% + 150%) прямоугольник препятствия может быть на несколько процентов «не той»
  ширины. Влияет только на точность прилегания у границы мониторов, не на корректность.
  Митигация (только если проявится на ручной проверке): пересчитать размер препятствия в DIP
  перетаскиваемого окна через `VisualTreeHelper.GetDpi(obstacleWindow)` при сборе снимка. В базовую
  реализацию **не** включать — см. урок про device-пиксели vs DIU в ADR-011.

## 5. Производительность (горячий путь `TitleBar_MouseMove`)

- **Сколько панелей.** Жёсткого лимита на число панелей в коде нет (`_childWindows` — обычный
  словарь; создание — вручную, лассо-жестом или из меню). Реалистичный порядок — единицы-десятки.
- **Стоимость кадра.** До двух проходов по `List<Rect>` (X-шаг и Y-шаг), внутри — сравнения `double`.
  При 30 панелях это ~60 итераций на событие мыши (~125 Гц) — доли микросекунды, оптимизация
  (пространственный индекс, broad-phase, сортировка по X) **не нужна и запрещена** как
  преждевременная. Если когда-нибудь понадобится — точка расширения одна, `ClampAgainstObstacles`.
- **Ноль аллокаций в горячем пути** — обязательное требование, обеспечивается тремя решениями:
  1. снимок препятствий собирается один раз на жест (§3.3), а не на кадр;
  2. буфер `List<Rect>` — переиспользуемое поле, `Clear()` вместо нового списка;
  3. параметр объявлен как `IReadOnlyList<Rect>` и обходится `for` по индексу — `foreach` по
     интерфейсу боксировал бы энумератор `List<Rect>` в куче на каждый вызов. `Rect` — `struct`,
     сам массив/список не копируется. LINQ в `PanelCollision` **запрещён**.
- **Никаких `Dispatcher.Invoke`/таймеров/анимаций** — клампинг синхронный внутри обработчика.

## 7. Тесты

Файл `tests/DesktopOrganizer.Tests/Unit/Models/PanelCollisionTests.cs`, `[Trait(UnitTests, "UI")]`,
по образцу `GridSnapTests` (чистая математика; сам мышиный цикл — manual verify).

`Overlaps`:
1. Пересекающиеся прямоугольники → `true`.
2. Касание ребром (`a.Right == b.X`) → `false` (иначе прилипшая панель заблокирует сама себя).
3. Перекрытие меньше `Eps` (0.2 px) → `false`.
4. Совпадение только по одной оси (полосы не пересекаются по другой) → `false`.

`ClampAgainstObstacles` — блокировка:
5. Движение вправо в соседа → `Left == obstacle.X - width`, `Top == proposedTop`.
6. Движение влево в соседа → `Left == obstacle.Right`.
7. Движение вниз / вверх — симметричные случаи по Y.
8. **Независимость осей:** упор по X при одновременном движении вниз → X склампен, Y равен
   предложенному (скольжение вдоль стены).
9. **Курсор убежал:** `proposedLeft` на 500 px за препятствием → результат ровно у стены (а не внутри
   и не «отброшен назад»).
10. **Возврат курсора:** из позиции «у стены» предложение уехать назад применяется 1:1, без остатка.
11. **Анти-тоннелирование:** прыжок за один кадр через препятствие целиком (`|dx| > obstacle.Width + w`)
    → останов у ближнего ребра.
12. **Два препятствия на пути** → выбирается ближайшее (`Min` по направлению движения).
13. Препятствие в стороне (не в полосе движения) → предложение применяется без изменений.
14. `obstacles` пуст → предложение применяется без изменений.
15. Нулевая дельта по оси → эта ось не трогается (в т.ч. когда по ней уже есть перекрытие).

`ClampAgainstObstacles` — правило R1 (амнистия):
16. `current` уже пересекает препятствие, движение **наружу** → не блокируется.
17. То же, движение **глубже внутрь** → тоже не блокируется (препятствие «призрачно», пока перекрыто).
18. Панель полностью внутри препятствия → выезд в любую сторону свободен.
19. Двухшаговый сценарий: выехали наружу (шаг 1) → попытка въехать обратно (шаг 2) блокируется.
20. Вырожденный `current` (`Width = 0`) → предложение применяется без изменений (защита R4).

`CreatesNewOverlap`:
21. Снап, вносящий новое пересечение → `true`.
22. Снап, не вносящий пересечения → `false`.
23. Пересечение было и до, и после (R1) → `false` (снап не парализован).
24. Пустой список препятствий → `false`.

**Регресс существующих наборов:** `GridSnapTests`, `GridMetricsTests`, `ChildWindowReorderGeometryTests`,
`ChildWindowViewModelTests` должны остаться зелёными без правок. Моки `IWindowManager` в трёх тестовых
файлах не требуют изменений (Moq сам реализует новый член).

## 8. Риски и ручная проверка

**Риски:**
- **R8 (mixed-DPI, §4)** — единственный содержательный риск; не блокирующий, митигация описана.
- Нативных участков нет; `WS_EX_NOACTIVATE`/WorkerW-встраивание не затрагивается — фича живёт целиком
  в managed-слое поверх `Window.Left/Top`.
- Поведенческая регрессия «панель не двигается»: единственная возможная причина — сломанное правило
  R1 (препятствие не амнистировано) при уже перекрытых панелях после обновления. Именно поэтому
  тесты 16–19 обязательны.

**Manual verify (Win10/Win11)** — добавить в чек-лист `docs/ROADMAP.md`:
1. Две панели рядом: подвести одну вплотную к другой — останов у ребра, зазора нет, дрожания нет.
2. Продолжать вести курсор «сквозь» соседа на 300+ px — панель стоит у стены; вернуть курсор — панель
   подхватывается ровно под курсором, без рывка и без накопленного сдвига.
3. Упереться в соседа сбоку и вести мышь вниз — панель скользит вдоль его ребра (проверка
   независимости осей).
4. Резкий быстрый рывок мышью через узкую панель — не проскакивает насквозь (анти-тоннелирование).
5. Отпустить кнопку у самой стены при включённом `GridSize`/`GridSnapDistance` — панель **не** прыгает
   внутрь соседа на mouse-up.
6. Панель, свёрнутая в заголовок, — блокирует только по высоте заголовка.
7. Панель на другой странице (`IPageManager`) — не блокирует.
8. Первый запуск новой версии с уже перекрытыми сохранёнными панелями — позиции не изменились;
   верхнюю панель можно вытащить наружу; обратно въехать нельзя.
9. Мультимонитор: перетаскивание между мониторами не блокируется на пустом месте; панели на разных
   мониторах не «магнитятся» друг к другу; HiDPI 125%/150% (риск R8).
10. Ресайз панели по-прежнему работает как в `ui-polishing-1` (квантизация по колонкам), в соседа
    залезать по-прежнему может — ожидаемо в этом батче (§3.6).

## 9. Бэклог (осознанно вне этого батча)

**9.1. Анти-оверлап при ресайзе.** Эскиз: в `Resize_DragDelta` после квантизации размера сравнить
результирующий прямоугольник с тем же снимком препятствий (собирать в `Resize_DragStarted`) и обрезать
**растущую** сторону до ребра соседа, затем откатить размер вниз до ближайшего целого шага
(`GridMetrics.Quantize` вниз, floor вместо round), но не ниже `MinPanelSize`. Требует отдельного
решения о приоритете «шаг сетки vs плотное прилегание» и собственных тестов.

**9.2. Боковая панель как препятствие.** Если по факту эксплуатации мешает — включить
`SystemIconsPanelWindow` в набор препятствий только пока она видима. Требует доступа к её окну из
`WindowManager` (сейчас его нет) и решения, что делать с уже стоящими под ней панелями.

**9.3. Раздвигание/уплотнение соседей (push-apart, tiling).** Явно отвергнуто пользователем.
Фиксируется здесь, чтобы будущий агент не «улучшил» стену до тайлинга.

**9.4. Магнит к рёбрам соседей** (притягивание с зазором 0 в пределах порога, как у сетки). Логичное
продолжение стены и дешёвое в реализации (`GridSnap`-подобный порог по рёбрам препятствий), но это
уже новое UX-поведение — отдельный запрос.

## 12. CLARIFICATION_NEEDED (один вопрос, не блокирующий старт реализации)

**Вопрос: нужен ли пользователю способ обойти блокировку?**
Требование сформулировано как безусловное («твёрдая стена»), но Stardock Fences допускает свободное
наложение панелей, и без обходного пути пользователь не сможет, например, временно положить панель
поверх другой.

- **A (рекомендуется, заложено в план).** Поведение всегда включено, настройки и обхода нет. Минимум
  поверхности, ровно то, что просили. Код структурируется так, чтобы включение варианта B позже стоило
  одного `if` в `TitleBar_MouseMove`.
- **B.** Настройка `PreventPanelOverlap` (bool, default `true`) в «Автозапуск и рабочий стол», рядом с
  `GridSize`/`GridSnapDistance` — те же шесть точек persistence, что и у `GridSnapDistance` (ADR-011,
  Решение 3). Стоимость: +1 настройка, +1 английская строка UI.
- **C.** Модификатор-байпас: удержание `Alt` во время драга временно отключает стену (проверка
  `Keyboard.Modifiers` прямо в `TitleBar_MouseMove`, состояние не хранится). Не требует UI, но
  недискаверабельно без подсказки.

Реализацию **начинать по варианту A** — B и C надстраиваются поверх без переделки алгоритма.
