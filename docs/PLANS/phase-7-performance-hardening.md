## Блок A — Кисти конвертеров: `Freeze()` + ограниченный кеш

**Пункт аудита 4.** `HexBrushConverter.cs:16`, `ColorOpacityBrushConverter.cs:34` — новый
`SolidColorBrush` на каждый вызов, без `.Freeze()`.

### Scope (S)

**Входит:**
- `HexBrushConverter.Convert`: возвращать **замороженную** (`Freeze()`) кисть; переиспользовать
  инстанс для одинакового входа через кеш `hex → SolidColorBrush`.
- `ColorOpacityBrushConverter.Convert`: то же, ключ кеша — пара `(нормализованный hex, byte alpha)`
  (альфа уже квантуется в байт — значит ключ конечен и стабилен).
- **Кеш обязан быть ограниченным.** Цвет вводится пользователем в `TextBox` в окне настроек: каждое
  нажатие клавиши — новый (в т.ч. невалидный) hex, то есть новый ключ. Неограниченный кеш здесь —
  это ровно та же утечка, что и пункт 1, только в UI-слое. Ограничение: константа (предлагается
  `MaxCachedBrushes = 64`); при переполнении — простейшая стратегия (полная очистка кеша или LRU;
  для 64 записей достаточно очистки, но решение за исполнителем + ревью).
- Нормализация ключа: `hex.Trim()` + `ToUpperInvariant()` — иначе `#ddd` и `#DDD` дают две записи.
- `ConvertBack` в `HexBrushConverter` — **не менять** (поведение и сигнатура сохраняются).
- Невалидный hex → по-прежнему `Brushes.Transparent` (он и так заморожен фреймворком).

**Не входит:** изменение XAML-биндингов, отказ от `MultiBinding` в `ChildWindow.xaml`, любые
визуальные изменения.

### Definition of Done

1. Обе кисти, возвращаемые конвертерами, имеют `IsFrozen == true`.
2. Повторный `Convert` с тем же входом возвращает **тот же** инстанс (`Assert.Same`).
3. Кеш не превышает константного размера при подаче > N различных hex-строк (тест подаёт 500 разных значений).
4. Невалидный hex → `Brushes.Transparent`; `ConvertBack` поведенчески не изменился.
5. Ключ кеша нечувствителен к регистру и пробелам (`" #ddd "` и `"#DDD"` → один инстанс).
6. Альфа для `ColorOpacityBrushConverter` считается как раньше (`Math.Round(opacity * 255)`, клампинг 0..1) — тест на границы 0.0 / 0.5 / 1.0.
7. `dotnet build` + `dotnet test` зелёные, StyleCop без новых предупреждений.

### Артефакты

- Изменить: `src/DesktopOrganizer.UI/Converters/HexBrushConverter.cs`, `src/DesktopOrganizer.UI/Converters/ColorOpacityBrushConverter.cs`.
- Создать: `tests/DesktopOrganizer.Tests/Unit/Converters/BrushConverterTests.cs`
  (образец подхода — существующий `Unit/ContentFilter/EnumEqualsConverterTests.cs`).

### Тесты (tdd-test-engineer)

Чистая логика, WPF-типы в тест-процессе уже используются — хост-приложение не нужно.
Кейсы: заморозка, идентичность инстанса, граница кеша, нормализация ключа, невалидный вход,
таблица альфа-значений, `values.Length < 2` → `Transparent`.

### Риски

- **Кеш без ограничения = новая утечка** (см. Scope) — главный риск блока, обязателен тест DoD-3.
- Замороженная кисть неизменяема: если где-то в будущем понадобится анимировать цвет кисти —
  сломается. Сейчас таких мест нет (цвет меняется пересозданием кисти через биндинг). Зафиксировать в ADR-012.
- Потокобезопасность: конвертеры вызываются с UI-потока, но кеш сделать `lock`/`ConcurrentDictionary`
  (замороженные кисти безопасны для чтения из любого потока).

**Manual verify (Win10/Win11):** цвет фона/текста панели и слайдер прозрачности применяются вживую при
редактировании hex в окне настроек; ввод мусора в поле цвета не роняет UI и не «залипает» на прошлом цвете.

## Блок B — Защита колбэка глобального хука

**Пункт аудита 9.** `DesktopGestureService.cs:58-102` (`HookCallback`) — глобальный `WH_MOUSE_LL`
без `try/catch`; исключение подписчика улетает наружу из системного хука.

### Scope (S, нативный)

**Входит (обязательно):**
- Всё тело `HookCallback` — внутри `try/catch (Exception)`; лог в `Console.Error` (как во всём
  остальном нативном коде проекта: `MonitorService`, `SystemShellService`, `NativeApi`).
- **`CallNextHookEx` вызывается всегда**, в том числе на пути исключения. Целевая форма:
  ```
  if (nCode < 0) return CallNextHookEx(...);
  var swallow = false;
  try { swallow = ProcessMessage(wParam, lParam); }
  catch (Exception ex) { log; swallow = false; }
  var next = CallNextHookEx(...);
  return swallow ? (IntPtr)1 : next;
  ```
  При исключении **никогда не глотать** событие (`swallow = false`) — иначе баг подписчика превращается
  в «пропавший правый клик» по всей системе.
- **Сброс состояния жеста ДО вызова подписчиков.** Сейчас в ветке `WmRButtonUp` сначала
  `RaiseLasso(...)`, и только потом `_rightDown = false; _rightDragging = false;`. Исключение внутри
  подписчика оставляет машину состояний «залипшей» в `_rightDown == true` — следующий правый клик
  ведёт себя неправильно. Переставить: сначала сброс полей, потом raise. (В `HandleLeftDown`
  `_lastLeftDownTime = 0` уже стоит до `Invoke` — там всё корректно, не трогать.)
- Отдельный `try/catch` вокруг самого `Invoke` подписчиков (`DesktopDoubleClicked`, `LassoCompleted`) —
  чтобы падение подписчика не влияло на решение о `swallow` и на возврат из хука.
- Вынести `switch` из колбэка в приватный `ProcessMessage(...)` → колбэк остаётся минимальным,
  как требует инвариант проекта («колбэк хука — минимум работы + try/catch»).

**Входит (опционально, только если экстракция остаётся чисто механической):**
- Вынести машину состояний жестов в чистый класс без P/Invoke — по образцу `UI/Models/GridSnap.cs`
  (прецедент из ADR-011): `DesktopGestureStateMachine` принимает `(message, x, y, tickCount, doubleClickTime,
  isDesktopPoint, isEmptyDesktopPoint)` и возвращает решение `{ Swallow, RaiseDoubleClick, RaiseLasso(rect) }`.
  Это единственный способ покрыть жесты юнит-тестами в среде без Windows-GUI.
  **Если экстракция начинает менять поведение — остановиться, оставить обязательную часть, а экстракцию
  вынести в бэклог отдельным пунктом.** Не рисковать нативным поведением ради тестов.

**Не входит:** смена типа хука, `LowLevelHooksTimeout`, переезд хука на отдельный поток, изменение
порогов `DragThreshold`/`DoubleClickSlop`.

### Definition of Done

1. Ни один путь выхода из `HookCallback` не может выбросить исключение наружу.
2. `CallNextHookEx` вызывается на **всех** путях, включая исключение; при исключении `swallow == false`.
3. Исключение подписчика логируется и **не** оставляет `_rightDown`/`_rightDragging` во взведённом состоянии.
4. Happy-path не изменился: завершённое правое перетаскивание по-прежнему подавляет контекстное меню
   десктопа; двойной клик по пустому месту по-прежнему поднимает `DesktopDoubleClicked`.
5. Хук остаётся установленным после исключения (не отваливается, `Dispose` по-прежнему снимает).
6. Если сделана опциональная экстракция — машина состояний покрыта тестами: порог драга (Чебышёв > 8),
   слоп двойного клика (≤ 4), окно `GetDoubleClickTime`, «тройной клик не считается вторым двойным»,
   сброс состояния на `RButtonUp`.
7. `dotnet build` + `dotnet test` зелёные.

### Артефакты

- Изменить: `src/DesktopOrganizer.Services/Tools/DesktopGestureService.cs`.
- Опц. создать: `src/DesktopOrganizer.Services/Tools/DesktopGestureStateMachine.cs` +
  `tests/DesktopOrganizer.Tests/Unit/Tools/DesktopGestureStateMachineTests.cs`.

### Риски

- **🔴 Нативный, непроверяемый в этой среде.** Любая ошибка в хуке = подтормаживание ввода всей системы.
  Изменения должны быть минимальными и очевидными при чтении.
- Экстракция машины состояний — соблазн отрефакторить больше, чем нужно. Жёсткая граница: без P/Invoke
  в новом классе, поведение 1:1.
- `Marshal.PtrToStructure` на `lParam` теперь тоже под `try/catch` — при мусорном `lParam` вернём
  `CallNextHookEx` вместо падения (это и есть цель).

**Manual verify (Win10/Win11) — обязательно:**
- Лассо правой кнопкой по пустому десктопу → создаётся панель, контекстное меню НЕ появляется.
- Обычный правый клик (без драга) → контекстное меню десктопа появляется как обычно.
- Двойной клик по пустому десктопу → иконки скрываются/показываются.
- Искусственно бросающий подписчик (временный `throw` в обработчике `LassoCompleted`) → приложение
  не падает, ввод системы не тормозит, следующий жест обрабатывается корректно.
- Отсутствие подтормаживаний курсора при длительной сессии.

## Блок C — Persistence панелей: дебаунс, try/catch, per-item изоляция

**Пункты аудита 8, 11, 10.** Все три — в `UI/Services/WindowManager.cs`, два из них (8 и 11) — в одном
методе `SaveWindowsState`. Делаются строго вместе.

### Scope (M)

**C1 — `SaveWindowsState` не должен падать (пункт 11).**
- Обернуть `SyncToModel` + сериализацию + `Settings.Default.Save()` в `try/catch (Exception)`, лог в
  `Console.Error`, не пробрасывать. Обоснование: метод дёргается из 10 мест (`App.xaml.cs` ×2,
  `MainWindowViewModel`, `ChildWindow.xaml.cs` ×5, `LayoutSnapshotService`, `WindowManager` ×2) на самых
  обычных действиях (двигаешь панель — падает приложение при залоченном `user.config`).

**C2 — Дебаунс записи (пункт 8). Двухуровневая политика:**
- «Частые» вызовы (перемещение, ресайз, roll-up, смена вида/фильтра, удаление файла из панели,
  `OnMonitorsChanged`) → `SaveWindowsState()` только **планирует** запись; повторные вызовы внутри окна
  дебаунса схлопываются в одну. Предлагаемое окно — **500 мс** (значение вынести в константу).
- «Структурные» изменения (создание/удаление панели, удаление страницы, restore снапшота, выход из
  приложения) → синхронная запись немедленно. Новый метод в `IWindowManager`:
  `void SaveWindowsStateNow()` (или `FlushPendingState()`), вызываемый из
  `App.OnExit`, `RemoveChildWindow`, `LayoutSnapshotService.Restore`, `MainWindowViewModel` (удаление панели).
- **Критично:** `App.OnExit` сейчас вызывает `WindowManager.SaveWindowsState()` перед
  `_serviceProvider.Dispose()` (`App.xaml.cs:61`). После введения дебаунса этот вызов **обязан** стать
  синхронным flush, иначе последние действия пользователя теряются при выходе. То же для
  `CreateLassoPanel` (`App.xaml.cs:133`).
- **Потоковая аффинность:** `SaveWindowsState` вызывает `window.SyncToModel()` по живым WPF-окнам →
  таймер дебаунса обязан тикать на UI-потоке (`DispatcherTimer`), а не на пуле. Если
  `Application.Current` == `null` (тесты, headless, поздний shutdown) — деградировать до немедленной
  синхронной записи.
- Дополнительно (дёшево): пропускать запись, если сериализованный JSON идентичен уже сохранённому
  (сравнение строки/хеша) — убирает запись в `user.config` вообще, когда ничего не поменялось.

**C3 — Per-item изоляция загрузки (пункт 10).**
- `LoadWindowsState`: десериализация — в своём `try/catch` (ловить `JsonException` **и** любое другое
  исключение), затем цикл создания панелей, где **каждая** панель создаётся в собственном
  `try/catch`: битая панель логируется и пропускается, остальные грузятся.
- Убрать текущий `_childWindows.Clear()` в `catch (JsonException)` — он не откатывает уже созданные
  окна (они остаются открытыми, но теряются из словаря), то есть делает хуже, чем ничего.

**C4 — (опционально, но настоятельно рекомендуется) бэкап битого состояния.**
Сейчас после провала загрузки первое же автосохранение перезаписывает `ChildWindowsState` пустым/
урезанным списком — раскладка пользователя теряется безвозвратно. С учётом C2/C3 это становится
вероятнее (загрузилось 3 панели из 10 → через 500 мс сохранилось 3). Мера: перед первой перезаписью
после неполной загрузки сохранить исходный JSON в
`%LocalAppData%\DesktopOrganizer\ChildWindowsState.corrupt-<yyyyMMdd-HHmmss>.json`.
Формально выходит за букву аудита, но относится к тому же классу отказа; помечено опциональным —
решение принимает оркестратор/ревью.

**Не входит:** переезд с `Properties.Settings` на собственный JSON-файл (отдельное архитектурное
решение, не в этой фазе); асинхронное сохранение.

### Definition of Done

1. `SaveWindowsState` не пробрасывает исключений ни при сериализации, ни при `Settings.Save()`; сбой логируется.
2. Серия из N частых вызовов внутри окна дебаунса приводит ровно к 1 записи (тест на выделенном чистом планировщике).
3. Структурные изменения и `App.OnExit` пишут синхронно — состояние после выхода полное (нет потери последнего действия).
4. `IWindowManager` расширен методом немедленного сохранения; все «структурные» вызовы переведены на него; `App.xaml.cs` обновлён.
5. При `Application.Current == null` сохранение выполняется немедленно (нет тихой потери состояния в тестах/headless).
6. Одна битая панель в сохранённом состоянии пропускается с логом, остальные грузятся — тест с фабрикой, бросающей на 2-м из 3 элементов.
7. Не-`JsonException` при десериализации не роняет старт приложения.
8. (Если взят C4) битый payload сохраняется в бэкап-файл до первой перезаписи.
9. Существующие `WindowManagerTests` проходят без правок; `dotnet build` + `dotnet test` зелёные.

- Изменить: `src/DesktopOrganizer.UI/Services/WindowManager.cs`, `src/DesktopOrganizer.UI/Services/IWindowManager.cs`,
  `src/DesktopOrganizer.UI/App.xaml.cs`, точечно `src/DesktopOrganizer.UI/Services/LayoutSnapshotService.cs`,
  `src/DesktopOrganizer.UI/ViewModels/MainWindowViewModel.cs` (перевод на немедленный вариант).

  `src/DesktopOrganizer.UI/Services/SaveScheduler.cs`), где логика «схлопывания» отделена от таймера:
  таймер инжектируется/абстрагируется, чтобы тест мог триггерить тик вручную.

## Блок E — Память в Services: кеш иконок и GDI-хэндл трея

**Пункты аудита 1, 3.** Два независимых файла, оба — Services, оба про память → один проход, одно ревью.

### Scope E1 — ограниченный кеш иконок (пункт 1, основной объём, M)

Сейчас `_iconCache` (`ConcurrentDictionary<string, ImageSource>`) растёт неограниченно: ключ — полный
путь, записи не удаляются никогда — ни при удалении файла, ни при закрытии панели, ни при ресинке портала.

**Рекомендуемое решение: LRU с жёсткой границей + проверка свежести по времени модификации.**
- Ёмкость — константа (предложение: **1024** записей; обоснование: типичный портал «Рабочий стол» —
  десятки-сотни элементов, 1024 покрывает несколько крупных панелей и не даёт кешу расти бесконечно).
  Вынести `internal const` + `internal` конструктор с явной ёмкостью для тестов — приём уже принят в
  проекте (`PanelItemStorageService(string storageRoot)` — `internal` ради тестов).
- Реализация: `Dictionary` + `LinkedList` под `lock` (вместо `ConcurrentDictionary`; вызовы идут
  преимущественно с UI-потока, `lock` дешевле и делает LRU-порядок корректным).
- В записи кеша хранить `LastWriteTimeUtc` файла; при попадании — сверять: изменился файл → перечитать
  иконку. Дополнительного IO почти нет: `GetIcon` и так делает `File.Exists`/`Directory.Exists`.
- **`IIconProvider` не менять** — никаких `Invalidate`/`Clear` в публичном контракте. Обоснование:
  вытеснение по LRU + проверка свежести закрывают оба сценария из аудита (удалённый файл, закрытая
  панель) без связывания UI-слоя с деталями кеширования. Это ключевое решение блока — в ADR-012.
- Попутно (дёшево, тот же файл/сосед): `PlaceholderIcon` — сейчас **property**, создающая новый
  bitmap на каждое обращение (а обращений столько же, сколько промахов). Сделать лениво создаваемым
  единственным замороженным инстансом.
- Попутно (опционально): `IconFactory.CreateBitmap(handle)` не вызывает `Freeze()`, хотя
  `NativeApi.cs:128` для аналогичного случая вызывает. Заморозка даёт кросс-потоковую безопасность и
  более дешёвый рендер. Риск низкий (иконки нигде не мутируются), но это чужой файл — брать, только
  если ревью согласно; иначе — в бэклог.

**Рассмотренные альтернативы (в ADR-012):** (i) `WeakReference<ImageSource>` — элегантно (иконка живёт,
пока на неё ссылается хоть один `FileItem`), но словарь мёртвых ключей всё равно нужно подметать;
(ii) явный `Invalidate(path)` из UI при удалении файла/закрытии панели — протекает абстракция и требует
дисциплины на всех call site; (iii) кеш по расширению файла, а не по пути — резко меньше записей, но
ломает иконки ярлыков/exe с собственными иконками.

### Scope E2 — освобождение `Icon` в трее (пункт 3, S)

- `NotifyIconAdapter` хранит текущий `Icon` в поле; `SetIcon` создаёт новый, присваивает

1. Кеш иконок никогда не превышает `MaxCachedIcons` записей (тест: 3×ёмкость разных путей).
2. Порядок вытеснения — LRU (тест: обращение к старой записи «омолаживает» её и вытесняет другую).

## Блок F — Манифест `PanelItemStorageService`: кеш в памяти вместо чтения файла целиком

**Пункт аудита 7.** `PanelItemStorageService.cs:494-520` — `WriteManifestEntry`/`ReadManifestEntry`/
`RemoveManifestEntry` читают и перезаписывают весь JSON-манифест на каждую операцию; при drop нескольких
файлов (`ChildWindowViewModel.AddDroppedFiles`, цикл по `sources`) — по разу на файл.

### Scope (M)

**Рекомендуемое решение (Вариант A): авторитетный кеш манифеста в памяти + write-through.**
- Ленивая загрузка манифеста с диска **один раз** на экземпляр сервиса (сервис — синглтон в DI),
  под существующим `_manifestLock`. Дальше словарь в памяти — источник правды для
  `ReadManifestEntry`/`IsManaged`-логики.
- `WriteManifestEntry`/`RemoveManifestEntry` мутируют кеш и **сразу** пишут файл (write-through).
  Итог для drop 10 файлов: было 10 чтений + 10 записей → стало 1 чтение + 10 записей.
- Формат файла не меняется (`Dictionary<string,string>` JSON) → полная обратная совместимость со
  старыми манифестами. Атомарный swap через temp-файл сохраняется.
- **Попутное исправление окна отказа (F-доп, рекомендуется):** сейчас в `MoveIn` запись в манифест
  идёт **после** `File.Move`/`File.Delete` оригинала (строки 76-90) — падение процесса между ними уже
  сегодня теряет original path, а по ADR-009 потеря записи означает, что «Убрать из панели»
  деградирует в `Release`, то есть **физически удаляет файл вместо возврата на место**. `destPath`
  известен до перемещения → писать запись манифеста **до** деструктивного шага и удалять её в
  `catch`, если перемещение не удалось. Стоимость — ноль, выигрыш — устранение реального сценария
  потери пользовательских данных.

**Отклонённые альтернативы (обязательно записать в ADR-012):**
- **Вариант B — batch-scope** (`IDisposable BeginBatch()` в `IPanelItemStorageService`, оборачивающий
  цикл в `AddDroppedFiles`): даёт одну запись на весь drop, но (1) меняет публичный интерфейс,
  (2) требует правки `ChildWindowViewModel` → второй проход по файлу блока D, (3) расширяет окно, в
  котором оригиналы уже удалены, а манифест ещё не на диске — прямой риск потери данных выше выгоды.
- **Вариант C — append-only журнал + компактизация**: O(1) на запись и сохранение durability, но
  усложняет формат и восстановление; брать только если профилирование покажет, что доминирует именно
  стоимость записи, а не чтения. В бэклог.

**Не входит:** смена места хранения манифеста, шифрование, переезд на SQLite/LiteDB.

### Definition of Done

1. Манифест читается с диска не более одного раза на экземпляр сервиса — тест выполняет ≥ 50 операций
   `MoveIn`/`Restore`/`Release` и проверяет счётчик чтений (`internal` счётчик-инструментация, по
   образцу уже принятых в файле `internal`-членов для тестов).
2. Число записей на одну публичную мутацию ≤ 1.
3. Формат файла не изменился: манифест, созданный предыдущей версией, читается корректно (тест с
   заранее записанным JSON).
4. Все 27 существующих тестов `PanelItemStorageServiceTests` проходят **без правок**;
   `Restore`/`Release`/`IsManaged` поведенчески идентичны.
5. Запись в манифест происходит до деструктивного шага `MoveIn`/`MoveInDirectory`; при неудаче
   перемещения запись удаляется (тест через `internal` перегрузку `forceCrossVolume` и провальный сценарий).
6. Все мутации кеша — под `_manifestLock`; параллельные `MoveIn` из нескольких потоков не теряют
   записей (стресс-тест на 100 параллельных вставок).
7. Поведение при повреждённом манифесте не изменилось: деградация до «нет known original paths»
   (`OriginalPathUnknown`), без падения (существующий контракт ADR-009).
8. `dotnet build` + `dotnet test` зелёные.

### Артефакты

### Риски

- **Кеш и внешние изменения файла:** после первой загрузки правки `.manifest.json` вне процесса не
  подхватываются. Приложение однооконное/однопроцессное — приемлемо; задокументировать в XML-doc.
- Память кеша пропорциональна числу managed-элементов (строка пути ×2 на элемент) — пренебрежимо.

после перезапуска «Убрать из панели» по-прежнему возвращает файл на исходное место (манифест цел);
принудительное завершение процесса сразу после drop → «Убрать из панели» всё равно возвращает файл

## Не входит в Фазу 7 (осознанные не-цели, в бэклог)

Зафиксировано, чтобы реализующие агенты не расползались по scope:

1. **Асинхронная/отложенная загрузка иконок.** Аудит упоминает в пункте 5, что на каждый файл дёргается
   нативный `IconProvider.GetIcon`. Устранение O(n²) (блок D) и кеш (блок E) снижают эффект, но
   синхронный shell-вызов на файл на UI-потоке остаётся. Полноценный фикс — плейсхолдер сразу +
   догрузка иконки в фоне через INPC-свойство `FileItem.Icon` — это отдельная фича уровня **L**
   (меняет `FileItem`, требует маршалинга и отмены при закрытии панели). **Брать отдельным планом.**
2. **Виртуализация wrap-вида.** `Templates.xaml:91` — `ItemsControl` + `WrapPanel`, виртуализации нет
   (в WPF нет штатной виртуализирующей `WrapPanel`; `ListBox` с `WrapPanel` в `ItemsPanel` её тоже
   теряет). Для панели на 1000+ элементов это заметно. Требует стороннего/собственного
   `VirtualizingWrapPanel` — отдельное решение, **в бэклог**.
3. **Переезд persistence с `Properties.Settings` на собственный JSON-файл** — снял бы стоимость
   `Settings.Save()` (запись всего `user.config`) полностью, но это отдельное архитектурное решение,
   затрагивающее все настройки приложения, а не только `ChildWindowsState`.
4. **Per-Monitor-V2 DPI** — уже отмечено открытым вопросом в ROADMAP, к этой фазе не относится.
