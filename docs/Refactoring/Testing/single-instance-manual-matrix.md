# Single Instance + IPC — матрица ручной проверки (M-1…M-13)

Артефакт Фазы 3 (`docs/PLANS/phase-3-single-instance-ipc.md` §6.2, `adr/ADR-023-single-instance-and-ipc.md`).
Здесь — только то, что **невозможно** закрыть `dotnet test`: живой рабочий стол, несколько сессий
Windows, инсталлятор, тайминги реальных процессов. Машинно-проверяемая часть DoD (§6.1 плана) закрыта
наборами `Unit/SingleInstance`, `Unit/Lifecycle`, `Unit/Installer`, `Integration/SingleInstance`.

## Статус выполнения

> **Ни один сценарий этой матрицы не выполнен.** Среда разработки агента не имеет живого Windows-GUI,
> второй пользовательской сессии и установленного инсталлятора — поведение проверено только компиляцией
> и unit/integration-тестами. Все строки ниже находятся в состоянии **«не выполнено»** и требуют прогона
> человеком на Windows 10 и Windows 11 перед закрытием фазы.

Помощник: [`tools/lifecycle/Invoke-SingleInstanceStress.ps1`](../../../tools/lifecycle/Invoke-SingleInstanceStress.ps1)
— 20 запусков с паузой 100 мс, подсчёт живых процессов и сверка кодов выхода вторичных процессов.
Покрывает M-1 (и, с флагом `-KeepRunning`, подготавливает M-2 и M-12).

## Коды выхода `DesktopOrganizer.UI.exe`

| Код | Значение | Решение |
|---|---|---|
| `0` | процесс отработал как primary, либо secondary успешно доставил активацию | — |
| `3` | рукопожатие провалено: primary жив, но не отвечает; второй writable-инстанс сознательно не поднят | D-7 |
| `4` | primary существует, но в другой сессии Windows | D-4 |

## Процедуры и критерии

### M-1 — 20 быстрых повторных запусков

```powershell
./tools/lifecycle/Invoke-SingleInstanceStress.ps1 -ExePath 'installer/publish/win-x64/DesktopOrganizer.UI.exe'
```

Зелёный результат: `Processes: 1`, `Non-zero exit codes: 0`. Скрипт сам печатает `PASS`/`FAIL`.

### M-2 — регресс R-1 (главный риск фазы)

Именно эта строка защищает от дефекта, ради которого фаза вообще начата (§0.1 плана): второй процесс,
дойдя до `App.OnExit`, сериализовал бы **пустую** коллекцию панелей и записал `ChildWindowsState = "[]"`.

1. Создать 2–3 панели, дождаться сохранения, закрыть приложение штатно («Выход» из трея).
2. Прогнать M-1.
3. Закрыть primary, запустить снова.
4. Панели на месте. Дополнительно — глазами проверить
   `%LOCALAPPDATA%\DesktopOrganizer_Url_*\user.config`: `ChildWindowsState` не `[]` и не пуст.

### M-3 — фокус, а не мигание в панели задач (R-13, нативно)

Единственная ручная проверка `INativeApi.AllowSetForegroundWindow`. Свернуть окно настроек (или закрыть
его в трей), кликнуть по ярлыку. Окно должно **получить фокус**, а не просто подсветить кнопку в
taskbar. Если мигает — грант foreground не сработал: проверить, что запуск идёт от пользовательского
клика (процесс, запущенный планировщиком, не владеет правом передавать foreground, и это ожидаемая
деградация, см. XML-doc `INativeApi.AllowSetForegroundWindow`).

### M-4 — активация ничего не меняет (D-8)

Машинная половина уже закрыта тестом `SingleInstanceActivationHandlerTests` (`VerifyNoOtherCalls()` на
`IWindowManager`). Здесь проверяется только то, чего тест не видит: геометрия панелей, прокрутка,
состояние скрытия иконок рабочего стола после активации визуально идентичны состоянию до неё.

### M-5 — abandoned mutex (R-2)

`Stop-Process -Name DesktopOrganizer.UI -Force`, затем обычный запуск. Ожидание: старт как primary без
единого диалога. В логе — `SingleInstancePrimaryAcquired` с `wasAbandoned: true`.

### M-6 — выход + немедленный запуск (R-6)

Выход из трея и, не дожидаясь исчезновения процесса, запуск ярлыка. Запуск не должен «потеряться».
В логе нового primary — `SingleInstancePrimaryAcquired` с `attempts > 1` (первые попытки получили
`DO/1 SHUTTING_DOWN` от уходящего primary и повторили захват владения).

### M-7 — контракт инсталлятора (R-9)

Запустить приложение, запустить `installer/Output/*.exe`. Inno Setup обязан предложить закрыть
приложение — он проверяет **существование** объекта `DesktopOrganizerSingleInstanceMutex`
(`installer/DesktopOrganizer.iss`, `AppMutex=`). Имя менять запрещено; статическая половина контракта
закреплена тестом `InstallerMutexContractTests`.

### M-9 / M-10 — разные пользователи против FUS

Это **две разные** проверки, и они должны давать **разный** результат:

- M-9 (разные пользователи): разные SID → разные `{sidHash}` → разные имена guard-мьютекса и pipe'а →
  два полноценных независимых экземпляра, каждый со своим `%LOCALAPPDATA%`.
- M-10 (один пользователь, две сессии через Fast User Switching): имена совпадают, но mutex — объект
  сессии, поэтому тай-брейкером выступает машинно-глобальный pipe с `maxNumberOfServerInstances: 1`.
  Вторая сессия обязана показать сообщение «already running in another Windows session» и выйти с
  кодом 4. В логе primary при этом ожидается `ActivationRequestReceived` с `sameSession: false`, а в
  процессе второй сессии — degraded-путь D-4 (`ActivationServerUnavailable` c `reason: PipeBusy`,
  затем `SingleInstanceSecondaryDetected`).

> Остаточный риск R-15: до Фазы 4 (файловая блокировка storage root) одновременная запись в storage при
> FUS защищена только этим механизмом.

### M-11 — зависший primary (R-3)

Приостановить процесс primary (Process Explorer → Suspend, либо отладчик с точкой останова). Запустить
ярлык. Ожидание: за **≤3 с** (бюджет рукопожатия D-6) появляется сообщение «is already running but is
not responding», код выхода 3. Второй writable-инстанс не поднимается ни при каких условиях (D-7).

### M-12 — retention логов не вымыт (R-12)

Прогнать M-1 на **Debug**-сборке (там диагностика включена по умолчанию). В
`%LOCALAPPDATA%\DesktopOrganizer\Logs` должен остаться файл сессии primary; 20 вторичных процессов не
должны создать ни одного нового `gestures-*.jsonl` — secondary не резолвит `IDiagnosticsLog` вовсе.
Это единственная проверка, где количество файлов в папке и есть результат.

### M-13 — холодный старт не просел

`tools/perf/Measure-Startup.ps1` до и после фазы; сравнить с
`docs/Refactoring/Testing/performance-baseline-*`. На свободном mutex рукопожатие — это один
`WaitOne(0)` плюс создание pipe-сервера, то есть единицы миллисекунд; заметный рост означает дефект.
