# Фича: Move вместо Copy при переносе файлов/папок в панель

## Контекст (зачем это)

Главная идея приложения — **очистить рабочий стол**. Пользователь переносит ярлык/файл/папку
с рабочего стола в панель и ожидает, что оригинал на десктопе можно спокойно убрать — панель
не должна от него зависеть.

**История бага (2026-07-07, эта сессия):** изначально панель при drag&drop хранила только путь
к оригинальному файлу (ссылку, не копию). Пользователь переносил ярлык в панель, удалял старый
ярлык с рабочего стола (ожидаемый workflow decluttering'а) — и элемент в панели ломался, т.к.
указывал на уже удалённый файл. Баг воспроизводился и для файлов, и для папок.

**Что уже реализовано как первый фикс (Copy) — НЕ переделывать с нуля, а эволюционировать:**

- `src/DesktopOrganizer.Services.Abstractions/IPanelItemStorageService.cs` — интерфейс:
  `Import(sourcePath)` (файл), `ImportDirectory(sourcePath)` (папка, рекурсивно, с safety-cap
  2 ГиБ / 20000 файлов), `Release(storedPath)` (удаляет копию, файл или папку — recursive для
  директорий), `IsManaged(path)` (path lives внутри storage root — защита от удаления чужого).
- `src/DesktopOrganizer.Services/Tools/PanelItemStorageService.cs` — реализация. Storage root:
  `%LocalAppData%\DesktopOrganizer\PanelItems`. Коллизии имён исключены GUID-суффиксом в имени
  файла/папки (`{имя}_{guid}{ext}`). Есть internal-конструктор с параметризуемым `storageRoot`
  для тестов (`InternalsVisibleTo` на `DesktopOrganizer.Tests` уже настроен в `Directory.Build.props`).
- Зарегистрирован в DI: `src/DesktopOrganizer.Services/Configuration/DiConfig.cs`
  (`services.AddSingleton<IPanelItemStorageService, PanelItemStorageService>()`).
- `src/DesktopOrganizer.UI/ViewModels/ChildWindowViewModel.cs`:
  - `AddDroppedFiles(string[] paths)` — новая точка входа для внешнего drop (заменяет прямой
    вызов `AddFiles` только для этого пути); для файлов зовёт `Import`, для папок —
    `ImportDirectory`; при неудаче падает обратно на путь оригинала (как было раньше).
  - `RemoveFileItem` (командой `RemoveFileCommand`, «Убрать из панели») сейчас зовёт
    `_itemStorage.Release(item.Path)` — удаляет managed-копию физически. **Это и предстоит
    поменять** (см. задачу ниже).
  - `AddFiles` (базовый, из `BaseViewModel`) остаётся нетронутым — используется для Folder
    Portals (`OnFolderChanged`) и восстановления состояния при старте (`LoadFromModel`); туда
    Import/Move НЕ должен просачиваться, они обязаны продолжать работать с реальными путями.
- `src/DesktopOrganizer.UI/Views/ChildWindow.xaml.cs`: `OnDrop` зовёт `_viewModel.AddDroppedFiles(files)`
  вместо `AddFiles`; `OnDragOver` уже проверяет `IsPortal` и ставит `e.Effects = DragDropEffects.Copy`
  (нужно поменять на `Move`, см. ниже) при наличии `DataFormats.FileDrop`.
- `src/DesktopOrganizer.Core/Models/FileItem.cs` — параллельный, отдельный фикс: переведён с
  `record` на класс с `INotifyPropertyChanged` + метод `Refresh()`, чтобы `Exists`/`IsDirectory`
  живо обновлялись в UI (поллинг из `ChildWindowViewModel`, таймер 3с). Это подстраховка на
  будущее, не заменяет копирование/перемещение по сути.
- Тесты: `tests/DesktopOrganizer.Tests/Unit/Tools/PanelItemStorageServiceTests.cs` (Import,
  ImportDirectory, Release, IsManaged — по файлам и папкам), `tests/DesktopOrganizer.Tests/Unit/Models/FileItemTests.cs`
  (Refresh/Exists reactivity).
- `docs/ROADMAP.md`, пункт Фазы 1 «Обработка «битых» путей» — уже содержит хронологию этого
  фикса (Copy-версия). **После реализации Move это описание нужно актуализировать.**

## Задача

Поменять поведение с «Copy + пользователь сам потом удаляет оригинал» на **Move**, с тремя
уточнениями, которые уже согласованы с пользователем:

### 1. Move по умолчанию, без блокирующего диалога — «дружественный флоу»

Перенос файла/папки в панель **перемещает** оригинал (не оставляет его на рабочем столе),
но без модального окна-подтверждения на каждый drop (это сломало бы плавность переноса).
Сигнал пользователю, что это именно перемещение, а не копирование — визуальный, штатными
средствами drag&drop: `DragEventArgs.Effects = DragDropEffects.Move` в `OnDragOver`/`OnDrop`
(`ChildWindow.xaml.cs`) — Windows сам покажет курсор «перемещение», это ровно то же самое,
что уже используется в Explorer, никакого кастомного UI изобретать не нужно.

### 2. Перемещение с другого диска — через copy+delete

`Directory.Move` кидает исключение при перемещении между разными томами (разные буквы диска);
`File.Move` в современном .NET кросс-volume обычно работает, но для единообразия и надёжности
трактовать одинаково: **определять** том источника и назначения (`Path.GetPathRoot`,
case-insensitive) и если они разные — делать перемещение как **copy, затем delete оригинала
только после подтверждённого успеха копии**. Если тома совпадают — использовать `File.Move`/
`Directory.Move` напрямую (быстро, атомарно на уровне файловой системы).

**Инвариант безопасности (важно):** оригинал никогда не должен удаляться, пока целевая копия
не подтверждена как полностью и успешно записанная. Если copy упал на середине (для папок —
особенно важно, там несколько файлов) — не трогать оригинал, откатить (удалить) частичную копию
в managed-хранилище, вернуться к referencing-поведению (как сейчас при неудаче `Import`/
`ImportDirectory`) и залогировать ошибку. Ни при каких сбоях пользователь не должен потерять файл.

Safety-cap на размер/число файлов (сейчас 2 ГиБ / 20000 файлов в `ImportDirectory`) имеет смысл
оставлять **только для кросс-volume перемещений** (там реально идёт побайтовое копирование) —
для перемещения в пределах одного тома cap не нужен, `Directory.Move`/`File.Move` там дёшевы
независимо от размера.

### 3. «Убрать из панели» возвращает файл/папку на рабочий стол, а не удаляет насовсем

Сейчас `RemoveFileItem` в `ChildWindowViewModel` зовёт `_itemStorage.Release(item.Path)`, что
**физически удаляет** managed-копию — это было нормально для Copy-семантики (оригинал жив на
десктопе), но для Move-семантики managed-копия — единственный экземпляр файла пользователя.
Удалять её насовсем при простом «убрать из панели» — потеря данных, недопустимо.

Требуется: при удалении элемента из панели, если он находится в managed-хранилище
(`IPanelItemStorageService.IsManaged`), **переместить его обратно** на исходное место
(там, откуда он был перенесён — как правило, рабочий стол), а не удалять.

Открытые вопросы, которые нужно закрыть при реализации (это не мелочи — без них корректно не
собрать):

- **Откуда брать «исходное место» для восстановления?** Сейчас `FileItem`/`ChildWindowModel`
  не хранят original path — только текущий (managed) путь. Нужно либо: (a) добавить
  `OriginalPath`/`RestorePath` в `FileItem` и включить его в персистентную модель
  (`ChildWindowModel.FilePaths` сейчас `List<string>` — потребуется расширить схему, например
  на `List<PanelFileEntry>` с `Path` + `OriginalPath`, либо параллельный словарь), либо (b)
  вести сопоставление `managed path → original path` внутри `PanelItemStorageService` (например,
  manifest-файл в корне storage root), персистентно переживающий перезапуск приложения.
  **Обратная совместимость:** у панелей, сохранённых до этого изменения, original path
  неизвестен — «Убрать из панели» для таких элементов должна деградировать до старого поведения
  (просто удалить/оставить как есть), не падать.
- **Коллизия при восстановлении.** Если на исходном месте на рабочем столе уже лежит другой файл
  с тем же именем (например, пользователь создал новый файл после переноса старого) — не
  перезаписывать; дать восстановленному файлу отличающееся имя (по аналогии с тем, как Explorer
  делает «Копия (2)»).
- **Исходной папки/файла больше не существует** (например, пользователь позже удалил родительскую
  папку на рабочем столе вручную) — восстановление на несуществующий путь: создать недостающие
  родительские директории, либо (если это совсем невозможно/нежелательно) — fallback на
  Desktop root пользователя, с логом. Решить и явно задокументировать выбранное поведение.

## Инварианты и ограничения (из CLAUDE.md)

- Никакого нового P/Invoke здесь не требуется — Move/Copy/Delete идут через штатный
  `System.IO` (`File.Move`, `Directory.Move`, `File.Copy`, `File.Delete`, `Directory.Delete`),
  риск ниже, чем у нативного кода, но цена ошибки — **реальная потеря файлов пользователя**,
  так что тестировать особенно тщательно.
- Слои: интерфейс — `Services.Abstractions`, реализация — `Services/Tools`, вызывающая сторона —
  `UI/ViewModels`. Не размывать эти границы.
- Folder Portals (`SourceFolderPath`) и восстановление состояния при старте (`LoadFromModel`,
  `AddFiles`) остаются полностью в стороне от Move/Copy-логики — трогать только путь живого
  drag&drop (`AddDroppedFiles`) и путь ручного удаления (`RemoveFileCommand`/`RemoveFileItem`).
- Нативный/WPF-код не выполняется вне Windows в текущей среде разработки → пункты, которые
  требуют реального drag&drop или проверки поведения Explorer, отмечать как
  «manual verify (Win10/Win11)». `dotnet build`/`dotnet test` в этой сессии тоже недоступны
  (нет SDK в песочнице) — обязательно прогнать локально/на CI перед мержем.

## Критерии готовности (Definition of Done)

1. Перенос файла или папки с рабочего стола в панель **перемещает** их (оригинал исчезает с
   десктопа) вместо копирования; курсор при drag показывает «перемещение» (`DragDropEffects.Move`).
2. Перемещение между разными дисками реализовано как copy-then-delete-only-after-verified-success;
   в пределах одного диска — прямой `File.Move`/`Directory.Move`.
3. Ни при каком сбое (нехватка места, файл занят другим процессом, обрыв на середине копирования
   папки и т.п.) оригинал не удаляется и не теряется — тест на это обязателен.
4. «Убрать из панели» для managed-элемента перемещает файл/папку обратно на исходное место
   (не удаляет физически); при коллизии имён — не перезаписывает, а даёт отличающееся имя;
   для элементов без сохранённого original path (старые панели) — не падает, деградирует
   безопасно.
5. Safety-cap на размер/кол-во файлов применяется только к кросс-volume перемещениям папок.
6. Регрессионные тесты покрывают: Move в пределах одного тома, Move между томами (через
   copy+delete), откат при сбое копирования, восстановление на исходное место (включая
   коллизию имён и отсутствие original path).
7. `dotnet build` и `dotnet test` зелёные (прогнать локально — недоступно в этой сессии).
8. `docs/ROADMAP.md` (пункт про «Копирование при drag&drop») актуализирован под Move-семантику.
9. Список «manual verify (Win10/Win11)»: реальный drag&drop файла/папки с рабочего стола,
   реальный кросс-volume перенос (например, с диска C: на подключённый диск D:/флешку), реальное
   «Убрать из панели» с проверкой, что файл действительно вернулся на рабочий стол.
